### 接口（新）

- `GET /api/users`
- `POST /api/users` → `{user, password}`（密码只在这次返回）
- `PATCH /api/users/{id}`（`role` / `settings_view` / `is_active`）
- `POST /api/users/{id}/reset-password` → `{password}`

规则：
- 都是普通 `def`；只许调用者用户行自己是管理员（用 API Key 时 Key 也要带 `admin`），认证开不开都这样，RBAC 影子模式也不会放宽。这是评审后的修订：原来认证关闭时人人可管，只读账户能借此把自己提为管理员，而且打开认证后依然有效。
- 不能停用或降级自己（409 `self_change`）；最后一个启用中的管理员不能被停用或降级（409 `last_admin`）。
- 停用会删除这个用户的所有会话、作废他的所有 API Key；重新启用后两者都不会恢复。用命令行 `aiops users disable` 停用的（它只改 `is_active`）也一样。
- 重置密码会删除这个用户的会话。重置的是自己时，保留发起请求的那一个会话，免得新密码还没复制就被送回登录页。
- 每次改动写一条审计，和改动在同一个事务里，从不记密码。
- 身份就是用户行自己的 `is_admin` 和 `permissions`（`auth/roles`），和 `aiops users` 的存法一样。

### E2E 里顺带修好的（都是以前就有的问题）

主人要求「做好前端交互测试，不要有Bug」，所以这轮把 27 个页面在 1440 / 390 / 320 px 下都走了一遍，不只看改到的页面。发现并修好了这些：

- **安全页整页空白**：有一条安全发现的「可达性」是一个对象，S1 的标签把它原样交给 React，整个应用都崩了。现在不是三种状态词的值，一律显示「无法确定」（`lib/reachability`）。
- **离开全景图页时报错**：浏览器窗口尺寸变化的回调在页面离开后还在读已经不存在的元素。
- **手机上整页横向溢出**：资源详情的标签栏（320 px 时多出 120 px）、Agent 指标的卡片标题、技能详情的标题行和一段很长的行内代码。
- **焦点和文字**：
  - 一次性密码对话框关闭后，焦点没有回到原来的按钮。
  - 共用的确认框改成模态的提示对话框：Tab 留在框内，关闭后焦点回到打开它的地方；默认按钮文字跟随界面语言，以前中文界面里写「Cancel」。

### 整个分支评审之后（2026-11-09）

评审结果：没有 Critical，3 个 Important，另有 3 个 Minor 按实际影响重新定级为 Important；全部修复，每一项都先补一个会失败的测试或 E2E 复现。其余 5 个 Minor 记录在案，留到后面处理。

- **用命令行停用的账户，在网页上重新启用后旧 API Key 会复活**：现在重新启用时同样作废旧 Key。
- **认证关闭时可以夺取管理员**：现在两种模式下都只许管理员管理用户（见上面「规则」）。
- **在会话抽屉里删不掉对话**（801–1279 px 和手机）：手写的确认框在抽屉的模态层底下点不到，焦点也被拉回抽屉。改成基于 `@radix-ui/react-dialog` 的 `alertdialog`（项目已有这个依赖），现在可以叠在抽屉上面。在 1024 和 390 px 下从抽屉里删除对话都成功了。
- **加载时闪现**：页面加载完之前，非管理员会看到「用户管理」和「新建用户」闪一下。现在加载完之前一律不显示。
- **一次性密码对话框点外面就关了**，唯一一份密码就没了：现在点外面不会关；关闭时连同请求缓存里的结果一起清掉。
- **手机上的两个筛选下拉框改成 16 px。**

留到后面处理的 5 个 Minor：
- 两个管理员同时停用对方，可能都通过「最后一个管理员」检查；
- 「管理员」有两种判定：`permissions` 里含 admin，或 `is_admin`；
- 只改身份的 PATCH 会清掉只读账户的「可查看设置」（只有 API 调用会遇到）；
- 认证中间件那条路径的断言还没进测试套件；
- 认证关闭时，权限依赖在事件循环里做了一次数据库查询。

### 接口

- `GET /api/ui/attention`：
  - 每项新增 `severity`（问题）、`risk_level`（变更）、`resource {ref, name, type, resource_id}`（只在资源和问题同一账号时给）、`region`、`waiting_on`；
  - 新参数 `reason`（逗号列表，不认识的值返回 422）、`q`（≤ 200 字）、`sort=waiting_longest|newest|severity`；
  - 返回体新增 `counts {reason: n}`：在账户范围和搜索之后、`reason` 过滤之前统计；
  - 「等你」的那类事项（给诊断裁决、重新生成方案）需要写权限（`issue.note`）：只读账户的工作台、顶栏数量和「待我处理」里不会出现它做不了的事。
- `GET /api/health-issues` 返回 `{items, total, next_cursor}`（以前是裸数组；`next_cursor` 是下一页的 offset，最后一页为 null），每行加 `waiting_on`、`waiting_since`；新参数 `view=all|mine|failed|long_wait`。`GET /api/health-issues/view-counts?scope&account_id` 返回四个视图的数量：只按范围和账户统计，所以在不加状态 / 严重度 / 搜索筛选时，等于带同一 `view` 的列表 `total`。详情接口也带两个等待字段。
- `GET /api/changes/{id}` 加 `waiting_on`、`waiting_since`。
- `POST /api/fix-executions/{id}/accept` 和 `POST /api/changes/{id}/resolve-review` 的请求体加可选的 `confirmed_checks`：最多 50 个 `pc-n`，每个都必须是那次执行自己计划里声明的检查，否则 422，什么都不写；不传时和以前一样（CLI `/accept` 不变）。accept 路由改为普通 `def`。
- 「谁在等、从什么时候开始等」只有一份定义：`services/attention.issue_waits` / `change_waits`，attention、问题列表、问题详情、变更详情都用它。
- 新配置 `attention_long_wait_hours`（`config/settings.yaml`，默认 24，≥ 1）。

### 整个分支评审之后（2026-11-09）

评审结果：1 个 Critical、7 个 Important，另有 4 个 Minor 违反了 spec 的全局约束，重新定级为 Important；全部修复。其余 7 个 Minor 记录在案，留到后面处理。每个修复都先补一个会失败的测试，再用 E2E 复测，见 E2E 报告。

- **验收被一个多余的结果卡住（Critical）**：执行里有一条结果点名了计划没声明的检查（比如 `pc-4`），它会变成一个勾选框，而所有框都要勾上，于是每次都把 `pc-4` 发给服务端、被 422 拒绝。这种执行恰恰需要人验收，却只能用 CLI。现在首屏和对话框只列声明过的检查；多余的结果由状态行的原因说明。
- **结果没有 `check_id` 的执行**（2.7.0 以前的记录）首屏一个检查都不显示，现在每个声明的检查一行、标「待核对」。
