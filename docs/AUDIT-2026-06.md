# AgenticOps — Full-Codebase Audit (2026-06)

> Method: 16 parallel subsystem/lens explorers → 144 raw findings → adversarial verification (re-read the actual code to confirm/refute/correct each) → this synthesis. 58 confirmed/partial, 8 refuted as false positives. Commit audited: `c539c38`. The audit workflow was hit by a transient regional API block near the end; ~50 verify calls and the auto-synthesis failed, so this report was reconstructed from the journaled results plus direct re-verification of the top findings.

## 1. Executive summary

**The architecture is fundamentally sound** — the agents-as-tools routing, the account-addressed credential redesign (just shipped), the policy engine, the graph engine, and the file-based memory/skills are well-conceived and the recent credential work is solid. **The serious risks are not in the design but in three operational seams:** (1) **`web/app.py` runs ~81 *synchronous* DB calls inside `async` FastAPI handlers** — under real concurrency this blocks the event loop and is the single biggest production-degradation risk; (2) **the autonomous loop is open, not closed** — `executor` marks issues `resolved` with **no post-execution verification gate** and there is **no reconciliation/drift loop**, so "phantom resolutions" are possible; (3) **a cluster of remaining `boto3` ambient-credential bypasses** in the notify/kb/storage layers and `SessionFactory` partially undercut the fail-closed multi-account guarantee the rest of the system now enforces.

Two genuine **critical bugs**: a `NameError` crash path in the CLI chat REPL, and a hardcoded default admin password seeded on startup. Both are small fixes. The dominant **tech-debt theme** is two mega-files (`web/app.py` 5,392 L, `cli/main.py` 4,915 L) that concentrate risk and slow every change.

Health by subsystem: credentials/providers **A−** (post-redesign, minus the bypasses), graph engine **B+** (correct, some O(n²–n³) hot spots), agents/memory/skills **B+**, tools **B**, web backend **C+** (sync-in-async + size), loop-engineering **C** (open loop), frontend **B**.

### HIGH (confirmed / partial)

**Credentials — remaining ambient-bypass holes (undercuts the new fail-closed design)**
- `notify/notifier.py:304,484` — `SNSNotifier` / `SNSReportNotifier` / `SESNotifier` build `boto3.client("sns"/"ses"/"s3")` with **ambient creds**, not the account resolver. In multi-account/IRSA pods these run on the wrong account silently. → thread `account_name` → `resolve_account_session()`. *(SES sender path already verified working; this is the AWS-client construction path.)*
- `kb/vector_store.py:321`, `storage/backend.py` — KB vectors / report storage use raw `boto3` (ambient). → same fix or document as system-account-only.
- `credentials/session_factory.py:132` — `SessionFactory.get_session(unknown_account)` **falls back to ambient** instead of raising. Contradicts the resolver's fail-closed contract. → raise `AccountResolutionError`.
- `session_factory.py:354` — `SessionFactory._assume_role_session` uses **frozen** STS creds (no auto-refresh), unlike `providers/aws.py` which uses `DeferredRefreshableCredentials`. Long-lived web/graph processes get stale tokens after ~1h. → reuse the refreshable fetcher.

> Note: `SessionFactory` is documented as serving only the Bedrock control plane + test-connection. If that's strictly true these are lower severity — but verify nothing in a business path calls it. (The resolver/provider path itself verified **clean** — no ambient fallback, cache keys correct.)

**Web backend**
- `web/app.py:2168-2261` — RCA/fix-plan triggers spawn raw daemon threads; exceptions are caught-and-logged only, **no task state in DB**, so the UI shows 202 then silence on failure. → `BackgroundTasks` or task-state table + `/…/rca-status`.
- `web/app.py:4407-4561` — SSE chat stream has **no `finally`**; on client disconnect the agent keeps running (drains tokens/CPU). *(partial: agent isn't always cancelled.)* → `try/finally` + explicit agent cancellation on disconnect.
- `web/app.py:2269-2294` — `/api/webhooks/alert` has **no rate limiting**; public-ish ingestion can be flooded. → rate limit + payload cap.
- Auth: several mutating endpoints rely on global middleware rather than per-route `Depends(get_current_user)`; verify no DELETE/PUT is reachable without role check.

**Tools**
- `tools/network_tools.py` (11 sites) + `eks_tools.py` (4 sites) — `json.dumps()` returned **unbounded**; large VPC/EKS topologies overflow the agent context ("内容过大被截断"), degrading reasoning. → wrap in `_truncate(MAX_LIST_RESULT_CHARS)` + per-type limits. *(This is the most likely cause of the "agent loses context mid-analysis" symptom.)*
- `tools/metadata_tools.py:674` — `list_health_issues` builds a `LIKE` pattern from `resource_type` without escaping `%`/`_`. Agent-supplied `%` → full scan / filter bypass. → `.like(val + '%', escape='\\')`.

**Graph engine — performance hot paths (correctness OK)**
- `graph/algorithms.py:447` — `list(nx.simple_cycles(...))` materializes **all** cycles before `[:10]`; pathological routing graphs → OOM/CPU DoS. → bounded generator (`islice`).
- `graph/algorithms.py:683-705` — SPOF loop re-copies/re-traverses the graph per articulation point (~O(n·E)); seconds on 1000+ nodes. *(partial: severity medium not "n³".)* → compute once.
- `graph/engine.py:746-756` — SG-connection inference is a 4-deep nested loop (O(n²)); runs on every enriched-graph request. → index SGs first.
- `graph/store.py:175-179` — `save_graph` deletes only **outgoing** stale edges (`source_id=:nid`), leaving stale **incoming** edges → corrupts blast-radius/RCA. *(confirmed real correctness bug.)* → delete both directions.

**Concurrency / threads (the post-ContextVar-removal sweep found siblings)**
- `services/notification_service.py:75-78` — `batch_mode()` suppression is a **ContextVar that doesn't cross the notify daemon-thread boundary** — the *same class of bug* just removed for credentials. Per-issue notifications leak during Scan/Detect/RCA batches. → pass suppression as an explicit arg to the thread target.
- `notifier.py` (7 sites) + `scan_agent.py:95` — `asyncio.get_event_loop()` called from daemon threads → `RuntimeError: no running event loop`, breaking notifications/scan/auto-RCA. → `new_event_loop()`+`set_event_loop()` (as `feishu_ws.py:426` already does correctly).
- `notify/im_config.py` + `metadata_tools.py:32` — module-level mutable caches (`_cached_data`/`_exclude_cache`) reassigned without locks → mid-request config flips. → `threading.Lock`.
- `models.py:30-38` — SQLite + `NullPool` + `check_same_thread=False` + ~12 daemon writers → write contention/`database is locked` under load. → WAL mode + retry, or document Postgres-for-prod.
- `pipeline_service.py:77-89`, `rca_service.py:59`, `resolution_service.py:41` — daemon threads catch-all and **swallow** exceptions with only a log; no surfacing to the issue/UI. → record failure state on the entity.

**Memory / KB**
- `memory/agent_memory.py:280` — TOCTOU on the size-cap check; two concurrent writers both pass, both write → cap exceeded. → lock the check-write.
- `kb/vector_store.py:346-360` — S3 vector index inconsistency under concurrent upserts (blob persists, index entry lost → orphaned vectors).

**Frontend**
- `lib/chatStream.ts:37-39` — `states` Map grows **unbounded** across sessions (no eviction) → memory leak / OOM on long-lived tabs. → `clear(sessionId)` on session delete + LRU.
- `pages/Chat.tsx` — **no React Error Boundary**; a single bad markdown render (`dangerouslySetInnerHTML` in `MessageList.tsx`) blanks the whole chat tree. *(partial: renderMarkdown itself doesn't throw, but the risk via injected HTML stands.)* → wrap in ErrorBoundary.

## 4. Design / tech-debt themes

1. **Mega-files concentrate risk.** `web/app.py` (5,392 L, ~70 endpoints) and `cli/main.py` (4,915 L) are the top two correctness *and* maintainability liabilities — most criticals live in them, and their size makes every change risky. The 1.0.1 split plan (app.py → routers/, main.py → commands/slash/service/renderers) is still pending and should be prioritized. `notify/notifier.py` (1,605 L) and `tools/metadata_tools.py` (1,493 L) are next.
2. **Sync-in-async is systemic**, not a one-off — it pervades `web/app.py`. Treat as one workstream (a DB-access helper that offloads to a thread), not 81 patches.
3. **Two parallel credential systems.** The new `credentials/resolver.py` (fail-closed) is correct, but `credentials/session_factory.py` (older, ambient-fallback + frozen creds) still exists and is used by some paths. Converge on one.
4. **Legacy dead-ish code still shipping**: `agent/ops_agent.py` (1,063 L, deprecated), `web/memory_service.py` (596 L, deprecated per CLAUDE.md), legacy `Anomaly`/`AwsAccount` tables. Confirm-then-delete to cut confusion and import cost.
5. **No DB migrations.** SQLAlchemy models evolve with ad-hoc `_encrypted`/`_legacy_*` detection. Adopt Alembic before the schema diverges further across local/cloud.
6. **No rate limiting / payload caps** on public-facing webhook + auth endpoints.

## 5. Loop-Engineering maturity & incremental roadmap  ⭐

**Current maturity: an *open* loop with good plumbing but no closure or evaluation.** The pipeline `HealthIssue → RCA → SRE → approve → execute → resolve` is wired with daemon threads + `pipeline_events` (TRC ids — good observability primitive), the 9-state machine enforces transitions, and `invoke_with_retry` handles transient Bedrock errors. **But:**
- **No VerifyGate** — `executor_agent.py:92-96` / `metadata_tools.py:1311` transition to `resolved` **without re-checking that the alarm/metric actually recovered**. → phantom resolutions.
- **No reconciler / drift loop** — once `resolved`, nothing re-checks; if the fix regresses or an external actor reverts it, the system is blind (`resolution_service.py` does a one-shot post-resolution check, not a standing loop).
- **Free-text hand-off** — RCA→SRE→Executor pass prose, not a structured state object; `FixExecution` doesn't capture a machine-readable outcome for learning.
- **No bounded-iteration guard** on the auto-pipeline triggers (`pipeline_service.py:77-90`) and **no circuit breaker / concurrent-trigger dedup** — a flapping alert can spawn overlapping RCA/fix runs.
- **No eval/replay harness** — acknowledged as future work (`MVP-2.0.0-ARCHITECTURE.md:180`).
- **Fragmented retry** — scheduler retries; executor doesn't.

**Staged roadmap (do in this order — each is one focused PR, biggest reliability gain first):**

- **Stage 1 — Close the loop (VerifyGate).** After execute, before `resolved`, run a verification step: re-query the triggering signal (CloudWatch alarm state / the metric / `run_on_host` health check) and only transition to `resolved` on pass; else → `fix_executed`+`needs_attention` and notify. *Files:* `executor_service.py`, `resolution_service.py`, the state machine in `models.py`/`validate_status_transition`. **Highest ROI — kills phantom resolutions.**
- **Stage 2 — Bounded iterations + circuit breaker + dedup.** Add a max-attempts counter per issue (DB column), a per-fingerprint circuit breaker, and de-dup concurrent triggers (the same `_run_auto_*` thread shouldn't start twice for one issue). *Files:* `pipeline_service.py`, `rca_service.py`. Prevents runaway loops + token burn.
- **Stage 3 — Structured inter-agent state.** Replace free-text hand-off with a typed `RCAResult → FixPlan → ExecutionOutcome` object (pydantic) persisted on the entities, so each stage consumes structured input and the outcome is machine-readable. *Files:* `models.py` (FixExecution fields), the three agents' prompts/return contracts. Enables learning + Stage 4.
- **Stage 4 — Standing reconciler loop.** A periodic job (extend `scheduler/`) that re-checks recently-`resolved` issues for regression/drift and re-opens on divergence. Depends on Stage 1's verification primitive.
- **Stage 5 — Eval/replay harness.** Record (issue → RCA → plan → outcome) traces; replay against agent changes in CI to catch quality regressions (the documented "replay eval CI gate"). Depends on Stage 3's structured traces.
