## 读代码查到的（决定了做法）

| 事实 | 所以 |
|---|---|
| `tools/metadata_tools.get_managed_resources` 返回**所有启用账户**里被管理的资源，前 50 行，不说被截掉多少。按账户并行的检测（`checker/engine._check_one_account`）拿的就是它 | 在「绑定了一个账户」的运行里，只给那个账户的行；被截掉时写明「50 / 共 N 行」和每种类型各有多少，模型才知道按类型或区域再查 |
| 已经有现成的账户绑定：`RunContext.bound_account_id`。设了它，凭证解析（`credentials/resolver`）、`providers/base.get_provider`、kubeconfig（`credentials/kube`）在任何别的账户上都**拒绝**。现在只有绑定了账户的对话、变更执行、变更审核在用；检测的线程没有设 | 每个检测线程把自己的账户设成绑定账户。那个线程里的任何工具都碰不到别的账户 |
| **顺带堵上一处跨账户读**：绑定了账户的对话里，`get_managed_resources` 也不看绑定，列得出别的账户的资源 | 同一处改动一起堵上 |
| `create_health_issue`（`_create_health_issue_impl`）给 Signal Gate 的 `SignalInput` 不带 `account_id`。问题的账户只能靠资源 id 在库存里对上：`root`、IAM 用户、账户级的发现对不上，账户就是空的 | 绑定了账户时，`SignalInput.account_id` 填这个账户。`identity_resolver.resolve` 本来就认「信号写明的账户」：资源在这个账户里找，找不到时问题也记在这个账户上 |
| 指纹（fingerprint-v2）里有账户。没有账户时，两个账户里同样的发现（比如两边的 root 都没开 MFA）会合并成一件 | 带上账户之后，它们是两件——这是对的，数量会因此变多一点 |
| `security/incremental_poll.poll_cloudtrail`：一个分页器读完整个窗口里的**每一条**管理事件，本机再筛 17 个高风险事件名。CloudTrail 的分页令牌只有一小时有效 | 改成**每个高风险事件名查一次**（`LookupAttributes: EventName=…`，`StartTime` = 游标）：一次只回这一种事件，一般一页就完。结果和原来一样，读的量从几十万条降到几乎为零，也就不会超过一小时 |
| 知识库的案例搜索是「向量 + 关键词」：关键词直接读文件，向量要先建（`tools/kb_tools._embed_and_index_from_markdown`，Titan 嵌入）。SOP 写进去时本来就不建向量（`write_kb_sop` 只写文件），搜索实际上靠关键词读文件 | 放回文件之后，对 6 个案例逐个调用这个现成函数建向量，不新写命令；3 个 SOP 放回文件就够了 |
| 开发机重新部署会 `git reset --hard`，被移走的 9 个示例文件会自己回来；清理时 `--move-knowledge` 又会把它们移走 | 两个库都按同一个顺序：先清理（连同从昨天的问题来的知识一起移走），再放回 9 个示例并建向量，最后重新扫描 |
| 开发机复原之后照常运行了约 2.5 小时：问题 789 → 920，发了 393 条通知，跑了 5 次用模型的关系图构建，没有起诊断、没有执行 | 这是它平常的样子，这一次清理会一起清掉这些新问题。数字照实写进报告 |

## 阶段

每个阶段：会失败的测试先写 → 实现 → 故意改错检查 → 本地提交。阶段 1、2 做完跑一遍全量测试，再推到 `origin/MVP-2.9.0`。开发机部署要从 `origin` 取代码；你 11-23 说过可以推这个分支。

### 阶段 1（N32）：检测只看、只记自己的账户

- `checker/engine._check_one_account`：`run_context(read_only_run="detect", bound_account_id=acct.id)`。
- `get_managed_resources`：有绑定账户时，只查这个账户的行。被截掉时，结尾加一行：「显示 50 / 共 N 行；按类型：EC2 12, …；用 resource_type 或 region 再查」。没有绑定时行为不变。
- `_create_health_issue_impl`：有绑定账户时，`SignalInput.account_id = str(绑定账户)`。
- 单账户的检测路径（`detect_agent()` 只有一个账户时）不加绑定，行为不变。
- 测试（新文件 `tests/test_detect_account_scope.py`）：
  - 绑定 A 时只看得到 A 的行；不绑定时两个账户都有；
  - 超过 50 行时有「共 N 行」和每种类型的数量，不到 50 行时没有这一行；
  - 绑定 A 时建的问题，资源对不上库存也记在 A 上；不绑定时照旧；
  - 两个账户各自建同样的发现，是两件，不合并；
  - 两个账户并行检测，每个线程读到的绑定账户是自己的；
  - 线程里去拿另一个账户的凭证被拒绝；
  - 绑定了账户的对话里，`get_managed_resources` 看不到别的账户。

### 阶段 2（N33）：CloudTrail 轮询按事件名查

- `poll_cloudtrail`：对 `HIGH_RISK_EVENTS` 里的每一个名字，用 `LookupAttributes=[{AttributeKey: EventName, AttributeValue: 名字}]` 加 `StartTime` 分页查一次。只留下名字对得上的事件（防假数据）。别的不动：游标、失败时保留游标、信号的样子都照旧。
- 测试（改 `tests/test_security_poll.py`）：
  - 每个高风险名字查一次，每次都带 `EventName` 条件和游标时间；
  - 没有一次是不带条件的查询；
  - 名字对不上的事件被丢掉；
  - 原有的三条测试改成适配新的查法，断言的内容不变。

## 我替你定的（不同意就在批准时说）

1. **检测的线程用现成的账户绑定**（`bound_account_id`），不另写一套过滤：它同时让那个线程碰不到别的账户的凭证。
2. **CloudTrail 按事件名查，不按时间分段读**：查的东西和原来一样，量小得多，也不用再管令牌过期。代价是每个区域每次轮询固定 17 次调用，其中多数是空结果。
3. **单账户的检测和没有绑定账户的运行，行为都不变**。
4. **`aiops run schedule` 跑完之后报错**、开发机环境文件的权限，这一次都不改。前一个不影响结果，后一个你没选。
5. **预览副本库和工作区里的知识库不动**。工作区里被移走的 9 个示例文件，在 git 里照旧显示为删除，我不提交。
