## 我做的决定（实现层面）

- **删除用户 = 软删除**：
  - `users` 表加 `deleted_at` 列，删除时同时设 `is_active=False`；
  - 行保留，邮箱的唯一约束就让登录名在所有路径上都不能再用，包括 `aiops users create`；
  - 私有对话和报告的 `owner_user_id` 仍指向一行永远不会给别人的记录；
  - 迁移沿用 `models._ADD_COLUMNS_2_7_0`。
- **删除的拦截范围**：在 spec 写的 `draft` / `needs_clarification` 之外，**发起人还有 `under_review` 的变更请求时也拒绝删除**（审阅者提出）。审核可能把它退回 `needs_clarification`，那时人已经删了，就没人看得到它了。
- **「在等我」放在 `/app/issues?view=waiting`**：选中项记在 `?item=I12|C3`（和原工作台的地址一致），阅读区由 Cases 自己画，问题用 `IssueDetail`，变更用 `ChangeDetailView`。原「待我处理」（`view=mine`）读作 `waiting`。
- **更新密钥**：建新行、同一事务里用 compare-and-set 撤销旧行，不在原行换哈希。每个 Key 的创建时间、最近使用都保持真实；审计两条，互相指向对方。
- **共用的图标按钮**：`components/ui/IconButton`，基于 Radix Tooltip；文字说明和 `aria-label` 用同一个字符串；手机 40 px，桌面 32 px。
- **去掉的东西**：工作台的「分栏 / 紧凑」切换和「更新于 · 刷新」页头，spec 没要，合并后不保留。
- **安全的数字**：按安全页自己的定义算（`security_service` 的 `detected_by`），只数未结的高危和严重。
- **顶栏的数字**：改读同一个 nav-counts 请求，两处永远一致；请求失败时不显示数字，不显示 0。

## Review Focus（测试最可能漏掉、最伤人的五类情况）

1. **打开它的元素没了，焦点丢了**：删用户、删 Key、更新 Key 都会让那一行消失（撤销的 Key 不再列出，更新后的是新 id）。每个 `returnTo` 都要指向还在的元素：页面的「新建」按钮、对话框标题旁的「生成密钥」。E2E 逐个验。
2. **三处数字对不上，或失败显示成 0**：侧栏、顶栏、「在等我」标签共用同一个 query key 和同一个账户来源；请求失败不显示数字；只读账户不显示数字；折叠的「运行管理」保留红色数字。

4. **「在等我」的阅读区和地址**：

   - 处理完提示「已处理 · 下一项」，不是一片空白；
