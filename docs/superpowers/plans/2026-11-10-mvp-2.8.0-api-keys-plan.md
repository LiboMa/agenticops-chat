# MVP-2.8.0 API Key 实施计划：我的 API 密钥、管理员查看、只读 Key 名副其实、前端遗留问题

**目标：** 按主人 2026-11-10 在预览里选的方案（三处都是推荐项），实现以下内容：
- 「我的 API 密钥」页（入口在头像菜单）；
- 管理员在用户管理里查看和撤销别人的 Key；
- 只读 Key 真的只能读；任何 Key 都不能管理 Key / 密码 / 用户，也不能做人的决定；

MCP 服务端是下一步，不在本计划里。

**架构：**
- 安全规则放在已有的三层里：`APIAuthMiddleware` 拒绝只读 Key 的写请求；`actor_from_request` 把只读 Key 标成 `read_only`，并给经由 Key 的 actor 打上 `via_api_key`；`config/rbac.yaml` 加一条 `enforce: always` 的规则，挡住人的决定。
- Key 的业务规则（权限校验、撤销、降级、审计）放进新的 `services/api_keys.py`，两个路由文件只做转发。
- 前端新建 `pages/ApiKeys.tsx`，用户管理页加一个对话框，再修 4 个小问题。

**技术栈：** FastAPI + SQLAlchemy；React 18 + TanStack Query v5 + Radix；vitest；Playwright。不加依赖。

**Spec：** `docs/superpowers/specs/2026-11-10-mvp-2.8.0-api-keys-design.md`（`e5f6ef3`）。上位设计的「全局约束」照旧适用。

## Context

主人要用 API Key 把第三方应用和 Coding Agent 接进来，下一步的 MCP 服务端也会用它认证。现状有三个问题：
- 后端早就能建、列、撤 Key，但网页上没有入口；
- 有一个安全缺口：Key 的权限只在 RBAC 检查时和主人的权限取交集，而 RBAC 默认是影子模式，所以可写用户的「只读」Key 照样能写，用它对话还会跑完整的代理；
- 读写 Key 能批准和执行方案，这违背项目的规定「批准只能是人的动作」。

主人选了：入口放头像菜单；只读账户能建只读 Key；管理员能查看并撤销别人的 Key。另外要「修复前端遗留问题」。

## Review Focus（spec 暗含、最容易伤到人的五类情况）

1. **Key 给自己扩权：** 只读 Key 去建读写 Key；Key 改密码；Key 管用户。都应该是 403 `session_required`。由 T2 测试覆盖。
2. **只读 Key 能写：** 在 RBAC 影子模式下写；用它对话时跑的是完整代理。写应该是 403 `read_only`，对话应该用只读代理。由 T1 测试覆盖。
3. **读写 Key 做人的决定：** 直接调接口去批准、执行、验收、裁决评审；或者在用它发起的对话里，让代理工具代为批准。都应该被拒绝，影子模式下也一样。由 T1 测试覆盖。
4. **降级后 Key 又能写：** 写权限被拿掉时 Key 应该一并降成只读；重新升级后 Key 仍是只读。由 T2 测试覆盖。
5. **一次性 Key 丢失或外泄：** 列表、审计、返回给管理员的数据里都不能有完整的 Key；显示 Key 的对话框点外面不会关，关闭后清掉。由 T2 的审计测试和 T3 的 E2E 覆盖。

### Task 2 — Key 的接口与规则：只能用登录会话管理、权限校验、审计、管理员接口、降级

**Files**

- 改：

  - `src/agenticops/web/routers/auth.py`：`/api/api-keys` 三个接口和改密码接口；

  - `src/agenticops/services/user_admin.py`：降级时调用 `downgrade_keys`；
  - `src/agenticops/auth/viewer.py`：白名单加两项；
  - `src/agenticops/web/schemas.py`：`APIKeyCreatedResponse` 加 `key_prefix`、`created_at`，`UserRow` 加 `active_api_keys: int = 0`。

**Interfaces（产出）**
- `require_session_user(request, *, admin: bool)`（async 依赖）：调用 `require_authenticated_user`，如果这次请求是用 API Key 认证的（`request.state.api_key` 存在，或 Bearer 令牌以 `aiops_` 开头），返回 403 `{detail, code: "session_required"}`。
- `services/api_keys.py`：
  - 函数：
    - `list_keys(user_id) -> list[dict]`：字段 `id, name, key_prefix, permissions, is_active, last_used_at, expires_at, created_at`；
    - `create_key(user, *, name, permissions, expires_days, caller) -> tuple[dict, str]`；
    - `revoke_key(key_id, *, owner_id, caller, by_admin) -> dict`；
    - `downgrade_keys(session, user_id, *, caller)`：把这个用户的读写 Key 降成 `["read"]`，每个 Key 记一条审计；
    - `active_counts() -> dict[int, int]`：有效且未过期的 Key 数，一次分组查询。
  - 出错一律抛 `ApiKeyError(status, code, detail)`：

    | status | code |
    |---|---|
    | 404 | `not_found` |
    | 403 | `scope_exceeds_role`（主人自己没有 write，却要 write） |
    | 422 | `invalid_scope`（只接受 `["read"]` 或 `{read, write}`）、`invalid_name`（strip 后 1–100 字）、`invalid_expiry`（1–3650 或 null） |

  - 审计：`api_key.create` / `api_key.revoke` / `api_key.downgrade`，实体类型 `api_key`。details 记主人 id、名称、前缀、权限、到期时间，以及撤销是本人还是管理员。从不记完整的 Key。审计和改动在同一个事务里。
- 路由：
  - `/api/api-keys` 的 `GET` / `POST` / `DELETE {id}` 改成普通 `def`，依赖 `require_session_user(admin=False)`；`PUT /api/users/me/password` 同样改用它。
  - `/api/users*` 改用 `require_session_user(admin=True)`。
  - 新增 `GET /api/users/{id}/api-keys` 和 `DELETE /api/users/{id}/api-keys/{key_id}`。
  - `GET /api/users` 的每行加 `active_api_keys`。
- 白名单：在 `auth/viewer._ALLOWED` 里加 `("POST", "/api/api-keys")` 和 `("DELETE", rf"/api/api-keys/{_SEG}")`。

**步骤**
1. 写 `tests/test_api_keys_api.py`，用真实用户、真实会话、临时库：
   - 列表、新建、撤销都正常；新建返回完整 Key 一次，列表里只有前缀。
   - 只读账户建 `["read"]` 成功；要 write 返回 403 `scope_exceeds_role`。`["read","admin"]` 和 `["write"]` 返回 422 `invalid_scope`。名称为空返回 422；有效期为 0 或超过 3650 返回 422。
   - 用 Key 发起的请求：`POST /api/api-keys`、`DELETE /api/api-keys/{id}`、`PUT /api/users/me/password`、`GET /api/users` 都返回 403 `session_required`。
   - 撤销后，`validate_api_key` 返回 None。撤销别人的 Key 返回 404。
   - 管理员：能列出别人的 Key，能撤销，审计里记着是管理员撤销的；非管理员返回 403。`GET /api/users` 的 `active_api_keys` 和实际数量一致：已过期和已撤销的不算。
   - 降级：把可写用户改成只读后，他的读写 Key 变成 `["read"]`，并有 `api_key.downgrade` 审计；再升回可写，Key 仍是 `["read"]`。
   - 审计里任何字段都不含完整的 Key。
   - 所有路由都不是协程函数。
2. 运行，确认失败。
