**我的理解**：接着做没做完的部分，不是「验收通过、可以推送」。`MVP-2.9.0` 停在 `c912ad1`，**不推**，等你明说；这一轮的提交都加在它后面，你随时可以只推 `c912ad1`。

**做完之后**：在新界面里，批准之后 5 秒内能撤回；执行中能叫停，叫停之后执行器只能跑这份方案自己的回滚步骤；现场能看到 agent 正在做的每一步，能给正在诊断的 agent 插一句话；诊断没有结果的事会回到人的队列里；方案可以「要求修改」并看到和上一份的差别；全景能回看过去 24 小时。

## 摸底发现的事实（决定了做法）

| 事实 | 影响 |
|---|---|
| 一次执行有三种起法：网页批准后的线程、排队（`POST /execute`、CLI、所有变更）、对话里调执行器。**只有排队的那种在执行期间有记录**（`fix_executions` 一行）、有超时看门狗、能取消 | 叫停和「看到每一步」都需要一张票。三种起法都经过 `agents/executor_agent.executor_agent()`——在这一处开票，一次补齐 |
| 现有的「取消执行」（`POST /api/fix-executions/{id}/cancel`）**只改库里的状态，执行器的线程还在跑**，之后的写命令照样会执行；被取消的修复，问题停在 `fix_executing`，不在任何人的队列里 | 这是现成的安全口子，先补：票一关，执行器的下一条命令就被拒绝 |
| 网页批准起的执行如果没存结果就结束（模型出错），30 分钟内一直读成「执行中」，没有人收尾 | 有了票，结束时对账 |
| 执行器是一个 LLM 工具循环：代码看得到「一次工具调用」，看不到「方案的第 N 步」；一轮里的几条命令默认并发跑 | 步骤按命令去对方案；执行器改成一条一条跑，「这一步做完就停」才是真的 |
| 装着的 Strands 1.64.0 有现成的开关：`BeforeToolCallEvent.cancel_tool`、`BeforeModelCallEvent.cancel`、`SequentialToolExecutor`、每次工具调用前后的事件。仓库里已有一个钩子的先例（`chat/attachments/budget_hook.py`） | 不用自己造机制 |
| 设计稿的撤回是「决定先显示、5 秒后才生效」，对**每一个**决定都一样，只有最后一个能撤回（`proto.js:68-79`，`UNDO_MS = 5000`） | 照设计在前端做：5 秒后才把请求发出去。后端不用改，也没有「撤回一个已经解决的问题」这种做不到的事 |
| 「谁在等」的规则对 `open / investigating / acknowledged` 一律回答「等 RCA agent」，队列只查另外四个状态；诊断失败后问题可能停在 `open`、`investigating` 或 `root_cause_identified` | 规则要多一个输入（上一次诊断失败了、之后没有再开始），前后端各一份 + 共用用例 |
| 方案被退回后重做，是**新的一行、版本从 1 重新算**；被退回的那一行内容还在 | 「和上一版的差别」= 和这件事上一份方案比，不需要新存东西；说法是「和上一份方案（#N）的差别」，不是「v2 → v3」 |
| 没有存过资源健康状态的历史。某个时刻「哪些资源上有未结的问题」可以从问题的开始、结束时间推出来；**那时的严重度、那时挂在哪个资源上，推不出来**（都被原地改写） | 回看只回放「那时有没有未结的问题」，并在页面上写明哪些是那时的、哪些是现在的 |

### N8 每次执行都有一张票（后端；地基）

- **开票**：`executor_agent()` 过了现有的几道闸之后，如果这次运行还没有票（Run Context 里没有 `execution_id`——网页批准的线程、对话），就开一张：一个事务里把方案 `approved → executing`、问题 `fix_approved → fix_executing`（都用现有的 `transition_plan` / `advance_issue`），插入 `FixExecution(status="running", started_at, executed_by=发起者)`，票号放进 Run Context。方案不是 `approved`、或者已经有一张在跑的票 → 拒绝（顺带补上「撤回和线程启动抢跑」的口子）。排队起的运行本来就有票，不变。
- **对账**：`executor_agent()` 的 `finally` 里，自己开的票如果还是 `running`，按「执行器没有留下结果就结束了」关掉。自己开的票也有 `executor_total_timeout` 的看门狗。
- **关票的统一出口**：把 `ExecutorService._close_ticket` 提成模块级函数；对修复方案补上它现在漏掉的两件事——问题 `fix_executing → root_cause_identified`（`issue_state.transition_issue`，带 `expected`），时间线记一条 `execution_completed failed`。
- **票一关就停手**：新钩子 `agents/run_guard.py`（`HookProvider`）。每次工具调用前查这张票：不是 `running` → 命令类工具一律 `cancel_tool`（只放行读和记录结果的工具）；下一次调模型前 `cancel`，让循环结束。这样取消、超时之后执行器真的停。
- **一条一条跑**：执行器用 `SequentialToolExecutor`。
- **顺带的口子**：`DELETE /api/fix-plans/{id}` 在方案执行中时拒绝（409）；`PATCH /api/settings` 把执行器打开时启动轮询；变更的一次执行不再记两条 `execution_completed`。
- **关键文件**：`agents/executor_agent.py`、`agents/run_guard.py`（新）、`services/executor_service.py`、`tools/metadata_tools.py`（`save_execution_result` 已经会就地关票，不用改写法）、`web/app.py`。
- **测试**（新 `tests/test_run_ticket.py`、`tests/test_run_guard.py`）：三种起法都有票；有结果就地关票；没结果对账并把问题放回去；同一份方案第二个执行器被拒绝；票关了以后下一条命令和下一次模型调用被取消（用真的 `strands.Agent` + 按脚本回答的假模型，照 `tests/test_attachment_budget_hook.py` 里 `RecordingModel` 的写法，不碰 Bedrock、不碰云）；删除被拒绝。要改的旧测试：断言「流程的执行期间方案还是 approved」的那几处（`test_auto_fix_pipeline.py`、`test_plan_run_in_flight.py`、`test_plan_cas.py`）。

### N9 叫停并回滚

- **后端**：`fix_executions` 加三列 `stop_requested_at / stop_requested_by / stop_note`（照 `_ADD_COLUMNS_2_7_0` 的写法）。`POST /api/fix-executions/{id}/stop`（普通 `def`；404 → 权限 `plan.execute` → 409；只接受人的会话，不接受 API key；写时间线和审计）。**叫停不关票**——票关了结果就存不进去、回滚也跑不了。
- **叫停之后放行什么**（`run_guard`，代码判定，不是模型自觉）：只读命令、记录结果的工具、以及**和这份方案 `rollback_plan` 里的命令逐字相同的命令**（`change_steps.rollback_steps` + 现有的归一化）。其余命令一律取消，取消的回话告诉模型「有人叫停了：把已经做了的按方案回滚，然后记下结果」。回滚写成一段话、没有命令的方案：什么都放行不了，页面照实说「这份方案的回滚没有写成命令，没有自动回滚」。
- **结果和去向**：存结果时如果票上有叫停——不把诊断判成「有争议」（是人叫停的，不是诊断错了）；修复回到 `root_cause_identified`，以 `execution_failed` / 新的细分 `run_stopped` 回到待决（共用清单加一行，简报还是「执行失败」那一页，换成设计稿的说法「你叫停了这次执行…」）；变更按现有规则结束在 `rolled_back`。叫停时所有步骤其实已经做完 → 结果照常，说「来不及了，照常做完了」。
- **前端（新界面 · 现场）**：执行的那一条上，按住 `A`「按住叫停并回滚」（红色，沿用 `useHold`）；状态「这一步做完就停」「正在回滚」读票上的字段。只读账户不显示。经过页的执行记录写「被 {谁} 叫停」。
- **旧界面**：页面不改；它的「取消」按钮调的还是 `/cancel`，现在是真的。
- **测试**：接口的权限和 409；叫停后回滚命令放行、别的命令取消、只读放行；结果不判诊断有争议；队列里的那一行；前端的状态和文字。

### N10 现场的每一步

- **后端**：新表 `agent_steps`（哪次运行、第几条、种类 `tool / say / you`、工具名、分类、一行摘要、开始、结束、结果、预览）。新钩子 `agents/step_recorder.py`：工具调用前插一行、调用后补上结束和结果，模型中途说的话记前 200 字。摘要和预览用现成的 `chat/tool_steps.summarize_input / result_preview / redact_for_display`。写不进去不影响 agent。挂在 executor、rca、sre 三个 agent 上。`GET /api/ui/activity/steps?item=I12&agent=…&after=…`（普通 `def`；能看这件事的人就能看，不是只有管理员）。每天清理，保留天数是一个新设置 `agent_steps_retention_days`（默认 30，写在 `config/settings.yaml`）。
- **和方案对上**：执行器的一条命令如果和方案某一步的命令相同，就标上是第几步；**哪一步都对不上的命令标「方案之外」**。
- **前端**：现场打开一条，3 秒取一次新的步骤，自动跟到最新（人往上翻就不跟）。设计稿的四种记号：◆ 代码取到的事实（只读工具）、▸ agent 做的动作（会改动的工具）、◇ 模型自己的话、「你」。原来那几句「后端不记录它的每一步」去掉。经过页的执行记录也列这些步骤。
- **测试**：钩子（真 Agent + 假模型）、脱敏、接口、前端的视图模型。

### N11 没人接的事回到人手里；占用补全

- **规则**：一件问题在 `open / investigating / acknowledged`，时间线上最新的一次诊断是失败的（超时、出错、没有留下结果），之后没有再开始、现在也没有 agent 占着 → 等人：`rcaStopped`，主按钮「重新诊断」。从来没诊断过的 `open` 问题**不动**（那几百件要不要等人，是你要另外定的事）。
- **要一起改的地方**：`services/work_phases.issue_phase`（多一个参数）和前端的 `lib/issuePhases.ts`；共用用例 `tests/fixtures/work_item_phase_cases.json`（以及 pytest 那边的键映射）；`services/attention.py`（多查这类问题、新的一行 `review_required / rca_stopped`、「从什么时候开始等」取失败的那一刻）；`attention_brief_kinds.json` 加一行，简报用现有的「重新诊断」那一页，换一句话；`services/activity.py` 里「停住了」的判断提成一个函数，两处共用；旧界面的两条文字（它的「在等我」用的是同一个接口，会跟着多出这类事——这是对的）。
- **占用**：自动诊断开始时占用（`rca_service.trigger_auto_rca`，结束时释放）；`rca_agent` / `sre_agent` 被对话里的 Main 当工具调用时，没人占就占、有人占就拒绝并说明（占用的把手放进 Run Context，已经占着的调用方不会被自己挡住）；占用过了时限但线程还活着 → 不作废，现场显示为超时；放弃时在时间线记一条；一个超时后才回来的旧运行不能抢走人新请的那一个。
- **测试**：共用用例两边都过；队列（含查询次数的上限）；占用的每一种交接。

### N12 插一句话

- **后端**：`POST /api/ui/activity/note {lane, text}`（200 字以内；只对这个进程里正在跑的诊断、出方案、审核）。这句话记成一条 `agent_steps`（种类 `you`、谁写的），挂在占用上；新钩子在 agent **下一次调模型之前**把它加进去，写明「这是跟着这次运行的人补充的信息，不改变你的任务和权限」，并把那一条标成已送到。
- **前端**：现场上 `E` 聚焦输入框，回车发出；那一条标「你」，没送到时写「agent 下一次思考前会读到」，送到了写「agent 读到了」。不写「它会先做这件事」。
- **不做暂停**：暂停要么卡住一个线程和一段模型上下文，要么要把 agent 的状态存下来再恢复；让它做完的代价更小。列在「没做的」里。

### N13 撤回（只有前端）

- 新界面里每一个决定都走同一个出口（`newui/decide/briefs/briefContext.useDecision` 已经是统一入口）：**立刻显示、5 秒后才发请求**；这 5 秒里底部是「{做了什么}，5 秒后生效 · 撤回 `Z`」和一条缩短的线；撤回 = 这个请求根本不发，焦点回到那件事上。新的决定会让上一个立刻发出（只有最后一个能撤回）。
- 关掉或离开页面时，把还没发的那一个立刻发出去（`keepalive`）——人已经做了决定。发出后失败：照现有的失败提示，事情回到队列。
- 文字照实写：5 秒之内服务端什么都还没发生，所以是「5 秒后生效」，不是「已批准」。
- 纯逻辑在 `newui/lib/pending.ts`，用假时钟测。

### N14 要求修改、和上一份的差别、稍后

- **要求修改**：`POST /api/fix-plans/{id}/request-changes {reason}`——一个请求里退回方案并请出方案的 agent 重做（占用、记录照旧）。批准页的 `R` 从「退回方案」改成设计稿的「要求修改」。变更单没有这条路（后端的状态机不允许从 `planned` 回到审核），保持「拒绝」。
- **差别**：`GET /api/fix-plans/{id}/previous-diff`——这件事上一份方案和这一份，用现有的 `change_steps.diff_steps` 按命令比，回答加了、删了、改了、没变的步骤，以及上一份是谁、为什么退回的。批准页在「为什么」和方案之间显示「和上一份方案（#N）的差别」。
- **稍后**：新表 `attention_snoozes`（谁、哪件事、到什么时候）；`POST / DELETE /api/ui/attention/snooze`；队列的每一行带上 `snoozed_until`，新界面把它排到同一严重度的最后、写「稍后再看」；一小时后回到原位。只对自己有效，不改这件事本身。旧界面的列表不变（它不读这个字段）。文字写「1 小时后回到原来的位置」——没有提醒这回事，就不写「提醒你」。

### N15 过去 24 小时

- **后端**：`GET /api/ui/events?hours=24`（信号、agent 的开始和结束、人的决定、变更，各带时间和所属的事，有上限）；`GET /api/galaxy/health?at=<时刻>`（和现在的健康接口同一个形状：那个时刻哪些资源上有未结的问题、哪些已经不见了）。
- **前端**：顶栏的「过去 24 小时」事件带；全景底部的回看条（`[` `]` 上一件 / 下一件事、`P` 回放、`0` 回到现在）。回到过去时页面顶上写明：「哪些资源上有未结的问题按那个时刻算；严重度、问题挂在哪个资源上、连线，都是现在的」，并收起「去处理」和与待决的对应。

## 这一轮不做
