# 在 `new-UI-face` 分支上完成全新界面的设计 —— 计划

> 本文件路径原来放的是「便宜档换成 Haiku 5.5」的计划；那份已提交在 `.worktrees/haiku-5-5` 的 `docs/superpowers/plans/2026-11-10-haiku-5-5-cheap-tier-plan.md`（5c3e87a，仍搁置），这里被本计划覆盖。本计划获批后另存为 `docs/superpowers/plans/2026-11-11-new-ui-face-design-plan.md`。

## Context

**起因。** 11-10 的项目评估给出了一份可点击的全新交互设计稿（`~/Documents/AgenticOps_Project_Review_20261110/ui-prototype.html`）：没有侧栏，三个视角（待决、现场、全景）加一条指令条，把「900 条问题」变成「眼前的几个决定」。它只画了核心的一条线，数据是写死的。你看过之后要求：建一条独立分支 `new-UI-face`，把这份设计**做完**。

**已经做了的。** 分支 `new-UI-face` 已建，工作区 `.worktrees/new-ui-face`，起点是 `MVP-2.8.0` 的最新提交 `d6d3779`（与 `:8000` 在跑的代码相同）。只在本地，没有推送。

**这份计划做什么。** 把设计稿从「一条线」扩成「整个产品」，并写成一份别人能照着实现的设计规范。每个阶段做完先给你预览，你确认后再进下一阶段。

**这份计划不做什么。**
- 不改 `src/` 下的任何产品代码（前端、后端都不动），不加依赖。
- 不动现在的界面，不影响 `MVP-2.8.0` 的验收。
- 不推送。
- 用 React 实现新界面是**下一份计划**，等你验收设计之后再写。这是按你的规矩来：先预览、确认，再动手。

## 「设计完成」的量化标准

1. **覆盖全产品。** 现有 29 个路由，每一个在规范的对照表里都有一行：新界面里的去处，或「并入某处」，或「去掉（理由）」。没有空行。
2. **覆盖每一种要人决定的情况。** 待办接口区分 15 种情形（问题 10 种、变更 5 种，归为 6 类原因：待批准、待验收、待确认、执行失败、未开始、需澄清），每一种都有一页决定简报。问题的 10 个状态、变更的 12 个状态，在「经过」页上都有对应的显示。
3. **每个屏幕四种数据状态**：加载中、失败、空、有数据。原型里有一个开关可以切换着看。
4. **四种身份**：管理员、读写用户、只读用户、未登录。只读用户看不到任何写操作。
5. **每阶段的检查都记录在案**：脚本错误 0；390 / 1024 / 1440 三种宽度无横向溢出；两种主题下正文对比度 ≥ 4.5:1（用脚本算）；每个主要动作都能只用键盘完成；尊重「减少动态效果」；中英文文案都齐。
6. **每个交互都写明后端现状**：已有（写出接口名），或需要新做（写出要做什么）。新增的用户可达能力按项目规矩逐行列出六个面（CLI / Web API / Web UI / Agent 工具 / 定时任务 / 通知），每行写「做」或「非目标」。
7. **全景视角的性能**：1,900 个节点下在这台机器上实测帧率，不低于 30 帧；达不到就写明降级规则。
8. **规范通过一次「施工方检查」**：一位没看过这场对话的审阅者读完规范，能直接写实现计划，不需要回来问。

## 设计规范里写什么

1. 意图和原因；目标、非目标、反目标（哪些情况即使做出来也算失败）。
2. 信息架构：三个视角、指令条、对象页；29 个路由的对照表。
3. 逐屏说明：每屏的用途、内容、状态、动作、键盘。
4. 交互规则：键盘表、焦点、撤回窗口、按住批准、证据速览、自动前进。
5. 视觉系统：色板、字体、间距、动效、图标；昼夜主题。
6. 内容规则：出处标记；诚实的措辞（未知不等于健康、失败不等于空、时间带 UTC）；中英文。
7. 无障碍和响应式的要求。
8. 每个交互对应的后端现状（已有 / 需要新做）和六个面。已知需要新做的四项：撤回窗口、逐句出处、流水线步骤的实时推送与插话、按时间回放资源状态。
9. 从现有界面迁移的办法（建议：新旧并存，新界面先挂在单独的路径下，功能齐了再替换；预览 4 时你定），以及现有代码里可以直接复用的部分（`lib/` 里的状态模型、`hooks/` 里的数据层、`components/workitem/StatusLine` 的逻辑）。
10. 验收标准、风险、留给你的问题。

## 需要你定的三件事

都有默认做法，不拦着开工；你批准计划时可以直接改。

1. **这一轮只做设计、不写产品代码。** 默认：是。
2. **MVP-2.8.0 后面几个阶段（S3–S8，按现在的风格重做安全、定时任务、设置等页面）要不要先停一停。** 如果新界面会替换旧的，这些页面会被做两遍。默认：我不动那边，由你决定；另一个会话照常工作。
3. **分支的起点。** 现在是 `MVP-2.8.0` 的 `d6d3779`（还没推送、等你验收）。那边如果返工，我把这条分支变基过去；只新增文档类文件，不会冲突。默认：就用这个起点。

## 做法上的约定

- 我自己逐阶段做（和 2.8.0 一样的方式），每阶段本地提交，提交信息以 `design(new-ui):` 开头；不提交 `agent-memory/`、`skills/`、`config/settings.yaml`、`dist/`。
- 不推送，等你说。
- 预览时我只打开原型和一张「这次看什么」的清单；你的意见记进 README 的决定记录，改完再进下一阶段。
- 开工时告诉另一个会话这条分支的存在和我只碰的路径。

- **D8**：规范对照表 29 行无空行；15 种待办情形、22 个状态都有出处；一次施工方检查，问题分三类处理（已有答案的补进规范、小事我定并标注、必须你定的一次性提给你）。
