## 阶段

每个阶段：会失败的测试先写 → 实现 → 故意改错检查 → 本地提交。阶段 1、2 做完跑一遍全量测试再推送（开发机部署要从 `origin` 取代码）。

### 阶段 0：准备（什么都不删）

- 告诉白皮书会话：要清副本库，问它截图和录屏做完了没有。没做完就把副本库留到最后。
- 经 SSM 只读地数一遍开发机：问题、诊断、方案、执行、信号、知识库文件、记忆文件各有多少。用的是部署脚本里那条 `run_on_instance` 的路，只读。

### 阶段 1（N31）：检测也只读

- `agents/detect_agent.py` 的 `detect_agent()`：调用模型的那一段设 `RunContext.read_only_run = "detect"`。它是按账户在多个线程里并行跑的，每个线程自己设一次——新线程不继承上下文。
- `services/command_audit.py` `_READ_ONLY_RUNS` 加一条 `"detect"`：拒绝时告诉它，会改动的东西写进问题的描述和建议里。
- 主机命令、技能工具在只读的运行里本来就照 N30 的规则走（`read_only_context()` 见到这个标记就算只读），不用再改。
- 测试：照 `tests/test_read_only_runs.py` 的写法——真的 `detect_agent()`、按脚本回答的模型，模型自己「确认」的写命令不会发出去；每个线程里都读得到标记；跑完标记不会留下。

### 阶段 2：清理命令 `aiops delete issues --all`

放在已有的 `aiops delete` 下面（那里已经有 `delete account`、`delete schedule`），在 `cli/main.py` 里，逻辑单独放在 `services/issue_purge.py`。

- **拒绝的情况**：不带 `--yes`；数据库不是 SQLite（三个库都是）；另一个 AgenticOps 进程正在跑（用现成的排程锁判断）。
- **`--dry-run`**：只列出每张表要删多少行，什么都不改。
- **先在线备份**：用 SQLite 的备份接口整库备份到 `<data_dir>/backups/pre-delete-issues-<UTC>.db`，检查完整性通过才往下做。库是 WAL 模式，只拷文件不是完整备份。
- **一个事务里删**（先子后父）：
  - `agent_steps` 和 `attention_snoozes` 里 `I…` 的行；
  - 问题和修复方案的 `itsm_links`；
  - 修复方案（`plan_kind='fix'`）的执行、方案本身；
  - 全部诊断；
  - 问题的时间线（`pipeline_events` 里挂着问题的行，备注也在其中）；
  - 全部信号；
  - 从问题蒸馏出来的案例记录和 SOP 记录，以及它们的向量；
  - 最后是问题本身。
- **不删**：
  - 对话：只清掉它们和问题的绑定，对话本身留着；
  - 两份审计记录（`audit_logs`、命令账本 `command_audits`）——它们是真实发生过的事的记录；
  - 变更单，以及变更的方案、执行和时间线；
  - 资源清单、关系图、安全快照、报告、账户、用户、定时任务、设置。
- **`--reset-poll-cursors`**：删掉安全轮询的游标，下一次轮询回补 24 小时。
- **`--move-knowledge`**：把从问题来的知识移到备份目录里，不删除，`aiops` 不再读它们。包括：
  - 知识库的案例和 SOP 文件；
  - agent 记忆里写着 `related_issue_id` 的条目和检测 agent 的 `auto_*` 条目。
- 删前、删后各打印一张每表行数的表。
- 测试：
  - 在一个造好数据的临时库上清——该删的删光，该留的一行不少，变更那一边完好；
  - 清完之后新建的问题从 I#1 开始，没有任何旧行挂上来；
  - 不带 `--yes`、别的进程在跑、不是 SQLite 都拒绝，并且一行不改；
  - `--dry-run` 一行不改；
  - 备份文件能打开，行数和清之前一样；
  - 移走的文件都在备份目录里，原处没有了。

### 阶段 4：预览副本库（先演练，等白皮书会话说可以之后）

每个库都是同一套做法。这里先做一遍，确认前后数字对得上：

1. **冻结**：停掉预览，停掉定时任务。用环境变量关掉自动诊断、自动修复、自动批准、执行器、通知（预览的环境文件里本来就关着四项，补上自动诊断）。
2. **清**：先 `aiops delete issues --all --dry-run`，再加上 `--yes --reset-poll-cursors --move-knowledge` 真的清。
3. **起服务**：用同样关着的开关把预览起起来。
4. **重新扫描**，按这个顺序，都经接口在服务进程里跑：
   1. 资源清单；
   2. 关系图（增量构建）；
   3. 安全复盘；
   4. 安全轮询；
   5. 检测 agent（`POST /api/health-check`，只跑一次）。
5. **报告**：清之前的数字；清之后的数字；扫完之后新问题的数量，按来源、严重度、账户分开；扫描花了多少时间和模型费用；被拒绝的命令（只读的运行里不该有不是只读的命令被执行）。
6. **复原**：只复原原来开着的定时任务和开关；预览原来就关着的那几项，照旧关着。

### 阶段 5：本机真实库

- 主检出和别的会话共用，移走那里的文件之前先告诉它们。

## 我替你定的（不同意就在批准时说）

1. **删掉，不是改成「已忽略」**：「已忽略」会把同一指纹的新告警压掉，重新扫描时这些问题回不来。
2. **从旧问题学到的东西，备份后移走，不删除**。这个问题你还没答，我按推荐的做：
   - 移走：案例、SOP、从问题写出来的记忆；
   - 随时能放回；
   - 想留着，批准时说一声，阶段 2–6 就去掉 `--move-knowledge`。
3. **审计记录和命令账本留着**：它们是真实账户上真实发生过的事。代价是编号重用之后，审计页按方案编号筛选时，可能混进旧方案的行。
4. **编号会从 I#1 重新开始**：
   - 旧报告、旧对话、旧通知里写着的 `I#12`，以后会指向另一件新问题；
   - 不想这样，就只能在每张表里留一行「占号」的假问题——我没有这样做。
5. **扫描期间**自动诊断、自动修复、自动批准、执行器、通知都关着。扫完复原成原来的样子，不顺手改。下一步量 RCA 质量时，诊断由我们有意地起。
6. **安全轮询只回补 24 小时**：更早的 GuardDuty / CloudTrail 发现回不来，这是它的设计，不改。

## 六个面

| 面 | 这一步 |
|---|---|
| CLI | **做**：`aiops delete issues --all`，可选 `--dry-run`、`--yes`、`--reset-poll-cursors`、`--move-knowledge` |

## 风险

| 风险 | 应对 |
|---|---|
| 删错、删多 | 每个库清之前都整库在线备份并检查完整性；先 `--dry-run`；一个事务，出错整体回滚；预览先演练，数字对上了再清下一个库 |
| 开发机部署出问题 | 照已经用过多次的部署流程，部署前全备份；出问题按备份退回 2.7.1 |
| 扫描期间有东西去改真实账户 | 执行器、自动修复关着；诊断、出方案、检测都在代码层只读（N30 + N31）；旁边开着账本监视脚本，见到不是「被拒绝」的写命令就停 |
| 消息刷屏 | 通知关着 |
| 费用 | 估计一个库 3–6 美元（检测 agent、合并判断、安全建议、关系图增量），三个库合计约 10–20 美元 |
| 白皮书的截图失效 | 副本库等它说可以再清；我给它留一份清之前的副本库，它要的话可以起在另一个端口上继续截 |
