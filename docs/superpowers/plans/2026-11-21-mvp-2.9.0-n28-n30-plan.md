### N30 诊断和出方案只读（第 15 条）

**零、先堵口子 ②**：`run_on_host` 一开始就检查主机参数——只收实例编号、主机名、IP（可带 `用户@`），不许以 `-` 开头、不许有空白；ssh 的参数里在主机前面加 `--`。对所有 agent 生效。

**一、拒绝（核心）**
- `run_context.py` `RunContext`：新字段 `read_only_run`（`"diagnosis"` / `"plan"`）。不借用只读账户的 `read_only`——那个标记还带着「不许读 Secret」、把拒绝说成「这个账户是只读的」，并影响身份判断。
- `services/command_audit.py` `change_context_refusal`：多一个分支——有这个标记、命令不是只读 → 记一行账本（`refused` / `read_only_run`），回答拒绝的那句话（写明：带 `require_confirmation` 也没用，不要重试；要改的东西写进方案的步骤或诊断的建议）。九个命令工具都经过这里，工具文件不用改。
- `rca_agent()`（`agents/rca_agent.py:513`）和 `sre_agent()`（`agents/sre_agent.py:449`）在调用模型的那一段设上标记。所有入口——流水线的线程、网页上的两个按钮和「要求修改」、对话里 Main 调它们、命令行——都经过这两个函数（评审对着 SDK 的源码确认了：在函数里设的标记，工具线程读得到）。
- 标记不会带进执行：之后起的线程各建新的上下文；`executor_agent()` 自己再把它清掉一次（防以后有人在同一个线程里直接调它）。

**二、不经过命令分类的三个口子**
- 出方案的 agent 不带 `enhanced_task`（`_create_sre_agent` 加一个参数，只有 `sre_agent()` 传；变更审核已经这样；对话里的 Main 和 `sre_query` 不变）。
- `activate_skill`：在这两种运行和变更审核里，**只注册白名单上的工具**——发布的技能里那 13 个只读的（读本机文件 6 个、查链路 4 个、`web_search`、`web_fetch`、列通知渠道）。别的一律不注册，并在回答里说明。草稿技能写了别的路径也一样进不来。
- 主机命令（`run_on_host`、SSH 账户工具）：在这两种运行和变更审核里，用一份单独的规则（和方案标注共用同一个引号扫描，放在 `services/change_steps.py`）。一行算只读要同时满足：
  - 没有重定向到文件、`$(…)`、反引号、`$'…'`、括号、后台 `&`、`#`；
  - 按不在引号里的 `;` `&&` `||` `|` 和换行分段，**每一段**的第一个词要么在「不可能写」的名单上（方案标注已经在用的那一份：`ls cat head tail grep ps df free netstat ping dig docker logs` …），要么是 `echo` / `printf` / `cd` / `true`，要么是下面带护栏的几样；
  - 带护栏的：`journalctl`（不带清理、轮转的选项）、`systemctl` 的查询（`status is-active is-enabled is-failed show list-* cat`）、`ip`（不带 `add del set flush change replace` … 和批处理）、`ss`（不带 `-K` `-D`）、`sysctl`（不带 `-w -p --system`，参数里没有 `=`）、`dpkg -l / -s / -L`、`dpkg-query`、`rpm -q…`（不带 `--pipe`）、`apt-cache policy / show / search`、`sort`（不带 `-o`）、`uniq`（不带文件参数）。
  - 不在上面的——`awk`、`sed`、`find`、`xargs`、`tee`、`env`、`curl`、`wget`、`sudo`、`timeout`、`strace` …——在这三种运行里一律拒绝。`ps aux | grep java`、`df -h; free -m`、`journalctl -u nginx -n 200 | grep error` 照常能跑。
- 口子 ③：给「无害的重定向」那条规则加上结尾边界。

**三、清单跟着补（让诊断还能读）**
- AWS 只读表加 10 行，都是账本上这两个 agent 真的读过的服务：`kafka describe- / list-`、`configservice describe- / list-`、`s3control describe- / list-`、`osis list-`、`emr-serverless list-`、`bedrock-agentcore-control list-`、`efs describe-`。这样那 31 条里 23 条照常能跑；被拒绝的是 6 条 `get-` 和 2 条 `generate-credential-report`。
- 主机的查询不动全局的名单，只在上面那份规则里。

**四、说真话**
- 两个提示词里「读命令自动执行、写命令再调一次确认」那几句改成代码现在做的事（按概念写，不点名某一家云）。
- 一条测试把这两个 agent **建出来之后**工具表里的每一个工具都归了类（只读 / 只写自己的库 / 写自己主机上的记忆和技能草稿 / 受上面检查点管的命令工具）；以后加了工具不归类，测试就红。

## 行为上的变化（要你知道的）

1. 诊断和出方案：不是只读的命令一律拒绝，模型不能再自己「确认」。进 Pod 执行命令（`kubectl exec`）在这两种运行里跑不了。
2. 出方案不再能把任务交给增强后端（Claude Code）；对话里照旧。
3. 这两种运行和变更审核里激活技能，只有只读的工具（没有写本机文件、发通知）。
4. 主机命令在这两种运行和变更审核里按白名单判：比现在严。`awk` / `sed` / `find` / `curl` 这些常用的词在这里跑不了，模型会收到一句写明「能用什么」的拒绝。对话和执行器里的主机命令不变。
5. AWS 只读表多 10 行，对所有用这张表的地方生效：只读账户的对话多了这些读命令；方案里这样的步骤标成「只读」，自动批准的下限也认；扫描任务每小时那条 `efs describe-file-systems` 不再记进命令账本（现在占账本 1,728 行里的 950 行）。
6. kubectl：把 `-n` 写在前面的读命令不再要确认；这样写的方案不再整份「分不了类」（所以可能被自动批准）；只读账户用引号绕过的 `get secret` 被拒绝。
7. 执行器（和对话里的 Main）读已批准的方案时拿到整份：一次多几千个 token。
8. `run_on_host` 拒绝不像主机名的主机参数（所有 agent）。

## 这三条不做（都记进发布说明）

- **对话和执行器里的主机命令**仍然按整行的开头分类（`cat x && systemctl restart y` 在对话里算只读、不问就执行）。把上面那份更严的规则用到所有地方，会改变对话和执行的行为——另起一项，等你定。
- **技能文件能声明任意工具路径、草稿也能激活**：只读的运行里已经用白名单堵上；对话里的 Main 和执行器仍然是原样——另起一项，等你定。
- 第 17 条（带 `file://`、`--endpoint-url`、`--cache-dir` 的读命令）：你定了以后单独做。
- 别的云：`az aks get-credentials`、`gcloud … get-credentials` 算只读却会在本机写一个 kubeconfig；阿里云的命令全部分不了类。现在没有这些账户。
- `get-` 开头的 AWS 命令不放宽；对话里的 `sre_query`、Main、执行器的命令规则不变。
- 把「工具自己拒绝的一步」在步骤记录里标成「被拒绝」：只是显示，要另加一套机制才标得准，这次不做——那一步现在显示成「做完」，内容是拒绝的那句话。
- 不再进集群重跑一次（理由见「验证」）。

| 只读之后诊断变弱（主机上常用的词被拒绝） | 白名单按「不可能写」的那份加账本和技能里真的在用的几样；拒绝的那句话写明能用什么；真模型的 2 + 2 次运行看结果；被拒绝的命令都在账本上（原因 `read_only_run`），之后按账本再补 |
| 白名单或者护栏写错，把会改动的一行放过 | 规则是「不认识的都拒绝」；每条护栏有反例；分段和引号沿用已经测过的扫描；只在这三种运行里生效 |
| 标记漏设在某条入口上 | 两个函数是唯一入口；测试从每条入口各起一次，在工具里读标记 |
| 标记被带进执行器（执行器不该只读） | 之后起的线程各建新的上下文，执行器自己再清一次；有测试 |
| AWS 表里新加的行放进了不该放的 | 只加 `describe-` / `list-`，逐行对过（没有存文件的、没有返回密钥内容的）；拦截名单仍然排在前面 |

## 我替你定的（不同意就在批准时说）

1. **出方案不带增强后端**——不然「出方案只读」对它不成立。要保留的话，这一条写进已知的缺口。
2. **主机命令用白名单加护栏**，变更审核也按这条。这比我上一条消息里说的「每一段都是只读就放行」更严：评审指出运行时那份只读名单里的 `awk`、`sed`、`find`、`xargs`、`strace` 自己就能写文件、执行别的命令，按它放行管道等于没管。代价是这些词在诊断里用不了。
3. **AWS 清单按服务逐行补，不按动词放开**。我上一条消息里提议过「任何服务的 `describe-` / `list-` 都算只读」，评审指出它能被缩写的全局参数骗过去，而且会影响到自动批准和只读账户——收回。
4. **技能工具用白名单**，`web_search` / `web_fetch` 留在里面（诊断要查文档和状态页；它只发 GET，目标不能是内网地址）。
5. **顺手堵三个现成的口子**（ssh 的主机参数、读 Secret 的引号绕过、`/dev/null` 的边界）——都是这次读代码发现的，都在要改的那几个函数里。另外两个更大的（对话里的主机命令、技能的任意工具路径）不在这次做，记进「之后」等你定。
6. 这三条叫 N28–N30，写进 2.9.0 的发布说明和 E2E 报告；「之后」第 15、20、21 条划掉。
