# MVP-2.2.1 — Effort（thinking）策略：后端升级 + 前端可覆盖

> Started: 2026-07-27 · Branch: `MVP-2.2.0` · 依赖：MVP-2.2.0（`agent_*_thinking_budget` + `thinking_request_fields` + RCA 质量三观测点）

## 0. 问题（现状事实）

| 事实 | 位置 | 后果 |
|------|------|------|
| `agent_rca_thinking_budget: 4096` 是**静态常量**，从未被验证 | `config/settings.yaml:104` | critical 生产故障与"EC2 缺标签"拿到相同思考预算 —— 同时错两个方向 |
| `agent_main_thinking_budget: 0` | 同上（默认值） | chat 里的 Opus **完全不思考**，用户无任何手段开启 |
| 唯一开关是 YAML + 重启 | `get_agent_thinking_budget` | 改交互路径会**同时改到自动管线**，两者被锁死 |
| `rca_started` 事件只记 `model_id` | `services/rca_service.py:64` | effort 与 RCA 质量的相关性无法归因 |

**为什么现在做**：2.2.0 刚补齐 `confidence` / `evidence_verified` / `critic_verdict` 三个质量观测点 + `cost_service` 的 token 账。effort 的效果第一次变成**可以从库里查出来的数字**，而不是信仰。这是一次实验，不是一次优化。

## 1. 判据与范围

判据只有一条：**当时有没有人在场做判断**。

| 路径 | 决策 | 理由 |
|------|------|------|
| 后端自动管线（webhook → detect → RCA → SRE） | **只能 Auto**，但从静态常量升级为**升级策略** | 告警凌晨三点进来，没人可选 |
| 前端 chat（+ 未来 CLI） | **Auto 兜底 + 用户可覆盖** | 用户在场、他付钱、只有他知道这次是"看一眼"还是"啃硬骨头" |
| executor | **恒为 0，不在本次范围** | 执行要确定性，不要它"再想想" |

**明确不做**（避免污染可度量性）：
- ❌ blast radius / 图谱影响面作为升级因子 —— 口径模糊，加进去就无法归因是哪个因子起作用。第一版只留两个输入。
- ❌ Settings 页的全局 effort 开关 —— 全局 effort 既不知道任务难度也不知道当前预算，用户设一次就再不改，只会退化成"永远 Deep"（贵）或"永远 Off"（差）。
- ❌ SSE 推送 reasoning 内容到前端（Strands 有 `ReasoningTextStreamEvent`，但那是"展示思考过程"的独立需求，记入 Future）。

## 2. 全局约束（每个任务都必须遵守）

1. **配置值只进 `config/settings.yaml`**，`config.py` 只定义 schema + 加载逻辑（Field default 作为安全网，不作为配置手段）。
2. **Bedrock 边界铁律**：`budget_tokens` 必须 `>= 1024` 且 `< max_tokens`。上界 `preamble.py:229` 已挡；**下界必须在解析时挡**（<1024 → 视为关闭并告警，绝不把非法值送进 Bedrock）。
3. **零破坏面**：`agent_{name}_thinking_budget` 语义不变（0=关）；`effort` 列为 NULL 时行为与今天**逐字节一致**。回滚 = 列留 NULL。
4. **不新增 LLM 调用**。effort 解析是纯函数，无 IO。
5. **`thinking_request_fields` 保持向后兼容签名**（现有 7 处调用点不改）；新能力走新函数。
6. **可度量优先**：每次自动 RCA 必须把实际使用的 budget 与升级原因写进 `rca_started` 事件 detail —— 没有这条，本次迭代的全部意义消失。
7. **只本地 commit，绝不 push**（等主人 E2E + 确认）。

## 3. 任务分解（TDD）

### Task 1 — 配置 schema + 纯函数解析器 ⭐ 先写测试

**测试**（`tests/test_effort_policy.py`）：
- `resolve_thinking_budget("rca", 16384)` → 4096（base，读 YAML）
- `escalate=1` → 8192；`escalate=2` → 12288（step=4096，按 tier 线性）
- 结果被 clamp 在 `max_tokens - 1024` 以下（防越界）
- base=0 时任何 escalate 都返回 0（关就是关，升级不能凭空打开）
- base=512（非法低值）→ 返回 0 + WARNING
- `effort_to_budget("off"|"standard"|"deep", max_tokens)` → `0 | 4096 | 12288`；未知值 → None（视为 Auto）

**实现**：
- `config.py` 新增 3 个 Field：`thinking_escalation_step`(4096)、`thinking_budget_min`(1024)、`thinking_effort_presets`(dict: off/standard/deep)。
- `config/settings.yaml` 写入上述默认值 + 注释说明这是实验参数。
- `agents/preamble.py` 新增 `resolve_thinking_budget(agent_name, max_tokens, *, escalate=0, override=None) -> int` 与 `thinking_fields_for_budget(budget, max_tokens) -> dict|None`；`thinking_request_fields` 改为薄封装（签名不变）。

### Task 2 — RCA 升级策略接线 ⭐

**测试**：
- issue.severity=critical → escalate=1
- issue.metric_data.needs_review=True（上次门控未过）→ escalate=1
- 上一条 RCAResult.critic_verdict="disputed_by_execution" → escalate=1

- 无 issue / DB 异常 → escalate=0（fail-safe，绝不因为归因失败而涨价）

**实现**：

- `services/rca_service.py:64`：`rca_started` 事件 detail 增加 `thinking_budget` + `escalate_reason`（**约束 6**）。

## 5. 实验设计（这才是本次的目的）

上线后跑一周，查这两个数：

```sql
-- effort 与 RCA 质量的相关性（按 thinking_budget 分组）
SELECT json_extract(detail,'$.thinking_budget') AS budget,
       COUNT(*) AS runs,
       AVG(r.confidence) AS avg_conf,
       SUM(r.evidence_verified) * 1.0 / COUNT(*) AS evidence_pass_rate,
       SUM(CASE WHEN r.critic_verdict='refuted' THEN 1 ELSE 0 END) AS refuted
FROM pipeline_events e JOIN rca_results r ON r.health_issue_id = e.health_issue_id
WHERE e.event_type='rca_started' GROUP BY budget;
```

**判读**：若高 budget 组的 `evidence_pass_rate` 与 `avg_conf` 无显著提升 → 说明 thinking 对本场景无效，应把 base 降回 0 并把这个结论写进文档（**负结果也是结果**，比留着一个未验证常量好）。若显著提升 → 考虑把 base 抬高。
