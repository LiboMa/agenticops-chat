## S1 核心信任加固 — 详细计划

> 代码行号以 2.6.1 `1ec53b3` 为准，实施时以 grep 为准。草案经一轮对抗审查（16 条，3 条阻塞），以下已全部吸收。

### S1a 验收逐项绑定（修复「重复结果凑数通过」）

**现状（已复核）**：
- `services/verification.py:85` 只比条数：声明 A、B，上报 [A 通过, A 通过] → `passed`。
- 声明检查是自由 JSON（`{"check","command"}`、字符串、任意 dict，可重复），并且进 `content_hash`，**不能改写**。结果只带可选的自由文本 `check`；执行器提示词要求「按顺序一条一条」（`agents/executor_agent.py:92-94`）。
- **现存 bug**：`get_approved_fix_plan` 把整份方案 JSON 截到 4000 字符（`tools/metadata_tools.py:60`、`:1475`），`steps` 和 `post_checks` 排在 summary 之后。长方案时，执行器拿到的步骤和检查本身就可能不完整。
- 三个归一化函数口径不一：`as_results` 只解码一层，`schemas.py:421-436` 解码三层、纯文本包成一项，工具输出直接给原始列。
- 判决计算了两次：`metadata_tools.py:1583` 一次，`change_service.py:1197` 又一次（后者拿不到执行行）。
- 已批准内容在执行期间不能被改（`PLAN_TRANSITIONS`、PUT 409、`save_fix_plan` 拒绝锁定方案）。唯一会在执行中改哈希的是账户重盖章（`services/identity_resolver.py:408` → `restamp_issue_plans`），`plan_content.approval_drift` 已能识别。

**设计**：
1. **单一归一化**：`verification.declared_checks(post_checks) -> list`，采用与 `schemas.py` 相同的多层解码规则（共享同一 helper）。`evaluate`、`check_ids`、工具输出、API 配对都只经过它。
2. **check_id = 声明位置**：`pc-1 … pc-n`（1 起），纯函数 `check_ids()`。内容在审批后冻结，所以同一次执行内位置稳定；重复的声明检查也各有 id；存储不动。
3. **执行器拿到完整、带 id 的方案**：
   - `get_approved_fix_plan` 输出把执行关键字段放前面（id / plan_kind / steps / 带 `check_id` 的 post_checks / pre_checks / rollback），**不再截断**；
   - 实施时确认 Strands ContextOffloader 的阈值与预览行为，确保关键字段落在预览内；
   - 测试用 6 kB 方案，断言步骤与全部 check_id 完整可见。
4. **`save_execution_result` 写库前校验**（`status=succeeded` 时）：结果必须对声明的每个 `check_id` 恰好一条，不能缺 id、不能有未声明 id、不能重复。不满足就返回 `INVALID: pc-2 missing; report exactly one result per check_id (a check you could not run → status=warning with the reason)`，**不写库**，执行器当场重报。`failed` / `rolled_back` 等非成功状态不校验（判决本来就是失败）。执行器提示词与文档串同步写明形状 `{check_id, status, output}`。
5. **`evaluate` 按 id 一对一绑定**（纵深防御；纯函数；状态集不变）：
   - 任一结果 fail → `failed`；
   - 缺 id / 未声明 id / 重复 id / 声明无结果 → `pending_acceptance`，原因句点名具体 id；
   - 新增参数 `plan_changed`，为真时不能 `passed`；
   - 原有规则保留。
   - **不做位置回退**（位置回退正是这次要堵的洞）。
6. **一次判决**：`save_execution_result` 用 `plan_changed = bool(approval_drift(session, plan))` 算一次 `(verdict, reason)`，把这对结果传给 `change_service.on_execution_result`，不再重算。`_close_ticket`（无结果）路径保持现状。**不新增列，不做迁移。**
7. **API 与 UI**：
   - `FixExecutionResponse` 加 `post_check_binding`：服务端用同一纯函数对该执行自己的方案（`fix_plan_id`）计算，每条为 `{check_id, check, result_status, problem: missing|duplicate|undeclared|null}`；
   - 前端 `ExecutionEvidence` 只负责渲染；`PlanView.tsx` 给 post-check 标 `pc-n`，原因句里的 id 读者能对上；
   - 旧执行没有 id 时显示「未绑定」，原样列出结果。
8. **主 agent 读工具**：`get_plan` / `get_execution_result`（`metadata_tools.py:1157-1185` 的 `plan_dict`）同样附 check_id，避免 agent 看到结果带 id、方案却不带。

**测试（先红后绿）**：
- 9 月反例原样入测 → `pending_acceptance`，原因点名 `pc-2`；
- 缺 id / 未声明 / 重复 / 两条相同声明检查各自有结果 / `plan_changed` / 多层编码的旧 `post_checks` 三处口径一致；
- `save_execution_result` 的 INVALID 不写库、重报后成功；
- 6 kB 方案的完整性；
- 变更路径只判一次；
- 改写依赖「无名结果计数通过」的夹具：`test_execution_verification.py` 真值表 / 形状表、`test_l4_e2e.py`、`test_executor_reconcile.py`、`test_change_pipeline.py`、`test_change_service_execution.py`、`test_auto_fix_pipeline.py`；
- 执行器提示词钉住的短语与 `test_prompt_budget.py` 预算同步；前端渲染 vitest。

**非目标**：独立探针重新观察（Harness Trust Kernel 的 VerifyGate）；`pre_checks` 评判；扩展验证状态集（设计包的 `inconclusive` / `accepted_manual` 对应现有 `pending_acceptance` / `accepted`）。

### S1b 会话归属与可见性

**现状（已复核）**：
- `ChatSession`（`models.py:1104`）没有归属列，7 个 chat 接口（`web/app.py:3780–4300`）都不识别调用者。
- SSE 处理器先读最多 5 个上传、先执行 `/channel`、`/send_to`，之后才做 404 检查（`app.py:4018-4113`）；PATCH 先返回「streaming 409」再查会话（`:3888`），会泄露会话是否存在。
- 列表 N+1 计数（`:3812`）。
- DELETE 不删 `SessionSummary`，SQLite 不强制 FK。
- `/api/reports/from-session` 把会话原文变成全员可见的报告。
- **PARK-S5**：`validate_api_key` 返回 detached User（`auth/service.py:272-298`），给接口加 `Depends(current_actor)` 后，API key 调用会变成 500。
- 认证默认关闭（`api_auth_enabled: false`），此时所有人都是 `web:anonymous`。

**规则**：
0. **先修 PARK-S5**：`validate_api_key` 在会话关闭前 `session.expunge(user)`（同 `validate_session` 的做法，`auth/service.py:199`），并补测试。
1. 新列 `owner_user_id`（Integer，可空）、`visibility`（String(16)，`private` | `workspace`，非空，默认 `workspace`）。迁移沿用 `_ADD_COLUMNS_*` + `_statements_*` 机制；**现存行全部 `workspace`、无主**（行为不变，即设计包的「legacy shared」）。

### S1c 单进程运行 + 事件循环不阻塞

**现状（已复核）**：
- `docker/Dockerfile:102`、`iac/deploy-sg/user_data.sh:157` 用 `--workers 4`，`deploy.sh:212` 强制改成 4；ec2 / ecs / eks / chaos-lab 都继承镜像 CMD。
- 只在单进程内成立的东西：连接器运行锁、Galaxy `_RULE_LOCK`、intake `_intake_lock`、Signal Gate `_gate_lock`（同指纹可建出两个 issue）、web/IM 会话 agent 缓存（相邻两轮落在不同 worker 时上下文分叉，TTL 摘要写 N 份）、`PATCH /api/settings` 只改当前 worker 内存（例如开 `rbac_enforce` 只在 1/4 的 worker 生效），以及 SQLite 启动时 `create_all` 竞争。
- 数据库锁补不了 agent 缓存、IM、设置和启动竞争，所以选**单进程**。
- 单进程的风险是事件循环阻塞：
  - **IM 回调在事件循环上直接跑一整轮 agent**（`web/app.py:4759` `result = agent(agent_input)`，经 `ensure_future` 调度，`:4822/4849/4871/4921`）；
  - 另有多处 `async def` 里做同步网络调用。
- `asyncio.to_thread` 用的是事件循环默认线程池（2 vCPU 时只有 6 个线程），Strands 的每个模型流和同步工具都会长期占一个。

**做法**：
1. **部署统一 `--workers 1`**：`docker/Dockerfile`、`iac/deploy-sg/user_data.sh`、`iac/deploy-sg/deploy.sh`（sed 目标与「Wait for 4 workers」注释）；`iac/eks`、`iac/ecs` 的副本数变量加 Terraform `validation`（= 1），K8s Deployment 改用 `Recreate` 策略（滚动发布会短暂出现两个副本）；同步 `docker/README.md`、`iac/deploy-sg/README.md`。
2. **单实例告警复用调度器 flock**：删掉无文档、无 IaC 引用的 `AIOPS_SCHEDULER_WORKER`（它还会让 shutdown 抛 `UnboundLocalError`，`web/app.py:136/276`）。lifespan 始终尝试取 `data_dir/.scheduler.lock`：拿到就当唯一实例（并启动调度器，与现状一致）；拿不到就打 ERROR「另一个进程正在使用同一 data_dir，内存态保证不跨进程」，只告警不拒启。顺手修 `tests/test_multi_cloud_api.py` 的 mock `data_dir`（改为 `tmp_path`，否则会在仓库根写 `MagicMock/` 目录）。
3. **默认线程池扩容**：lifespan 里 `loop.set_default_executor(ThreadPoolExecutor(max_workers=N))`，N 来自 `config/settings.yaml` 新键 `event_loop_executor_threads`（config.py 只定义 schema）。
4. **把同步网络调用移出事件循环**：处理器整体是同步的，就改成普通 `def`（走 FastAPI / anyio 自己的线程池，不和 Strands 抢）；混合的用 `await asyncio.to_thread`。清单（实施时再 grep `async def` 处理器里的 boto / `get_provider` / `converse` / requests / httpx / subprocess 补全）：
   - IM 回调的 agent 轮次与 `execute_channel` / `execute_send_to`；
   - `/api/health`（STS）；
   - 告警 webhook → `process_signal`（持锁时同步调 L2 Bedrock）；
   - `POST /api/health-issues`（同一路径）；
   - `graph/api.py:64-135`；
   - `routers/changes.py:44` `_call`；
   - `POST /api/skills/generate`、`POST /api/accounts/{id}/test`、`POST /api/reports/generate`、`POST /api/rag/pipeline/{id}`；
   - SSE 里的 `/channel test`、`/send_to`（`chat/channel.py:127` 还在运行中的事件循环里新开 loop）；
   - `_chat_sessions.get_or_create` 的 agent 构建（含 MCP 启动）。

**测试**：
- `httpx.AsyncClient(transport=ASGITransport(app))` 并发两个请求：把 STS / L2 判官 / IM agent 打桩成慢调用，断言另一个请求先返回；
- 第二次进入 lifespan（同一 data_dir）打出 ERROR；
- 断言部署文件里不再出现 `--workers 4`。

**非目标**：
- 连接器 / Galaxy / intake 的 DB 级锁与唯一索引（单进程后只剩「服务器 + 手动跑 CLI connectors」一路，`uq_cloud_resource_acct_prov_rid` 已防重复行）；
- 多副本、粘性路由、设置热重载；
- liveness 探针不再调 STS（属于探针语义，另议；chaos-lab 已改 tcpSocket）；
- IM WS 在 `feishu_ws_enabled=false` 时仍会自启（单独问题，列入已知缺口）。
