# MVP-2.8.0 API Key（MCP 对接的第一部分）+ 前端遗留问题（设计）

2026-11-10。主人的原话：
- 「增加MCP使用的用户API Key来与第三方应用以及Coding Agent做对接」
- 「开始做 MCP 对接 API Key 的部分；同样也是先预览再动手」
- 「在前端给出UI入口，且修复前端遗留问题」

预览（git 忽略的 `.superpowers/brainstorm/…/apikeys-v2.html`）里三处都选了推荐项：
- 入口放在头像菜单；
- 只读账户能建 Key，但只能是只读 Key；
- 管理员能在「用户管理」里看到并撤销别人的 Key。

上位设计的「全局约束」照旧适用：`docs/superpowers/specs/2026-11-08-mvp-2.8.0-workspace-redesign-design.md`。

## 为什么

第三方应用和 Coding Agent（Claude Code、Codex、Kiro 等）要用一个用户的身份调用 AgenticOps。下一步的 MCP 服务端也会用同一种 Key 认证。

后端早就能给自己建、列出、撤销 Key（`/api/api-keys`），但没有网页入口，而且有一个安全缺口：
- Key 的权限只在 RBAC 检查时和用户本人的权限取交集；
- 默认的 RBAC 影子模式下，拒绝了也照样放行；
- 只读状态（中间件拒绝写请求、对话用只读代理）只看用户行自己的权限，不看 Key。

所以今天可写用户建一个「只读」Key，照样能写，用它对话也会跑完整的、能执行变更的代理。只读 Key 必须名副其实，这是这一轮的前提。

成功的样子：
- 每个人能在自己的页面上安全地发、看、撤销 Key；
- 只读 Key 真的只能读；
- 管理员能看到并撤销任何人的 Key；
- 前端那 4 个遗留问题消失。

反目标：
- Key 的权限超过它主人的身份；
- 完整 Key 出现在列表、日志或审计里；
- 撤销以后还能用。

## 1. 我的 API 密钥（新页面）

- **入口**：顶栏头像菜单，在「首页与语言」下面加一项「API 密钥」，打开 `/app/account/api-keys`。所有已登录的人都有，包括只读账户。手机上同样在头像菜单里。
- **页头**：「我的 API 密钥」，加一句说明：「给第三方应用和 Coding Agent 调用 AgenticOps 用。Key 能做的事不会超过你自己的身份；完整的 Key 只在创建时显示一次。」右边是「＋ 新建 API Key」。
- **列表**：每个 Key 一行，768 px 以下变成卡片。
  - 列：名称、前缀（`key_prefix`，后面加「…」）、权限（只读 / 读写）、创建时间、最近使用（UTC，没用过写「从未使用」）、到期（UTC 日期，或「永不过期」）、状态。
  - 状态用文字：有效 / 已过期 / 已撤销。
  - 只有「有效」的 Key 有「撤销」，撤销前先确认。
  - 下面写一句：「撤销立即生效；账户被停用时，它的 Key 一并作废。」
- **新建对话框**：
  - 名称：必填，1–100 字。
  - 权限：只读 / 读写，两个选一个，默认只读。只读账户的「读写」不能选，旁边说明原因。
  - 有效期：30 天 / 90 天 / 1 年 / 永不过期，默认 90 天。
- **只显示一次的 Key**：
  - 显示完整的 Key 和「复制」按钮；
  - 一个 curl 示例：`curl -H "Authorization: Bearer <key>" <本站地址>/api/health-issues?limit=5`；
  - 一句「MCP 服务端做好后，这里会给出 Claude Code / Codex 的配置」。
  - 点外面不会关；关闭按钮写「我已复制，关闭」；关闭后连同请求缓存一起清掉。和用户管理里的一次性密码同一套做法。
- 四种数据状态、16 px 移动端输入框、弹层规则、双语、UTC，都按全局约束。

## 2. 管理员在「用户管理」里看 Key

- 每行多一项「API Key N」，N 是这个人当前有效的 Key 数量；0 个时写「无」。
- 点开是一个对话框，列出这个人的所有 Key：名称、前缀、权限、最近使用、到期、状态。每个有效的 Key 可以撤销，撤销前先确认。
- 管理员不能替别人新建 Key，也看不到完整的 Key。

## 3. 后端

- **改造 `/api/api-keys`**（`web/routers/auth.py`）：
  - 改成普通 `def`；身份用 `web/deps.require_authenticated_user(admin=False)`，两种认证模式下都从 Bearer 令牌认出用户。
  - `GET` 列出自己的 Key。
  - `POST` 建 Key，权限只接受两种：`["read"]` 或 `["read","write"]`。超出自己身份的（只读账户要 write）返回 403，码 `scope_exceeds_role`；其他组合返回 422，码 `invalid_scope`。`expires_days` 取 1–3650 或 null，名称 strip 后 1–100 字。
  - `DELETE /api/api-keys/{id}` 撤销自己的 Key，不是自己的返回 404。
  - 接口的请求体和返回字段保持兼容。
- **只读账户**：在 `auth/viewer` 的写白名单里加上 `POST /api/api-keys` 和 `DELETE /api/api-keys/{id}`。它们只会碰调用者自己的 Key，服务端也只给只读账户发只读 Key。
- **只读 Key 名副其实**（安全前提）：一个请求用 API Key 认证、而这个 Key 的权限里没有 `write` 时，这次请求按只读账户处理：
  - `APIAuthMiddleware` 拒绝它白名单以外的所有写请求，返回 403 `read_only`，不管 `rbac_enforce` 开没开；
  - `actor_from_request` 把这次请求的 actor 标成 `read_only`，所以对话跑只读代理、命令校验也按只读来。
  - 带 `write` 的 Key 和现在一样：权限是主人身份和 Key 的交集。
- **Key 不能管理 Key、密码和用户**（我的决定，审阅者提出）：用 API Key 认证的请求访问下面这些接口，一律返回 403，码 `session_required`，只能用登录会话来做：
  - `/api/api-keys`（建、撤销）；
  - `PUT /api/users/me/password`；
  - `/api/users` 下的任何写操作。

  否则一个泄露的 Key 可以给自己再建一个永不过期的读写 Key，撤销它也挡不住访问。MCP 那一步如果需要 Key 自己轮换，到时再议。
- **人的决定只能人来做**（我的决定，审阅者提出，依据是项目规定「Approve/reject is a HUMAN action — never an agent」，以及主人看过的预览里「读写」的说明「还能像你一样提变更、加备注、发对话」）。用 API Key 认证的请求，不能做下面这些事，读写 Key 也不行：
  - 批准、拒绝或执行方案和变更；
  - 验收一次执行；
  - 裁决变更评审。

  返回 403，码 `human_session_required`。用这个 Key 发起的对话里，代理工具代它去批准也一样被拒绝。做法是：actor 带上「经由 API Key」的标记，在 `authz` 的这几项权限上始终生效，影子模式也不放宽。
- **管理员接口**：`GET /api/users/{id}/api-keys` 和 `DELETE /api/users/{id}/api-keys/{key_id}`，用和 `/api/users` 同一个管理员门槛，认证开不开都一样。`GET /api/users` 的每行多一个 `active_api_keys`（有效且未过期的数量）。
- **身份变化**（我的决定）：用户被降级、失去写权限（`user_admin.update_user`）时，他的读写 Key 一并降成只读，每个 Key 记一条 `api_key.downgrade` 审计。重新升级不会自动恢复，要用就重新建。
- **已有的 Key**（我的决定）：不做迁移，本地库里一个都没有。列表照实显示权限：只读 / 读写 / 读写 + 管理（旧接口建的、带 `admin` 的 Key），照样可以撤销。新建的 Key 永远不带 `admin`。
- **认证关闭时**（我的决定）：Key 照样能建，这样打开认证以后就能用。页面顶部写明：「当前未开启接口认证：请求不需要 Key，Key 的权限限制也不生效。」
- **审计**：新建和撤销各写一条 `audit_logs`（`api_key.create` / `api_key.revoke`），实体类型 `api_key`。记 Key 的主人、名称、前缀、权限、到期时间，撤销时还记是本人还是管理员撤销的。从不记完整的 Key。

## 4. 前端遗留问题（S2 记在案的 4 条）

1. 拒绝方案或执行时的理由对话框（`components/plans/ReasonDialog`）：关闭后焦点回到打开它的按钮，现在落在 `<body>`。
2. 验收时自动生成的理由：「已核对 N 项」只数检查项，不把最后那一项总确认算进去。
3. 待办工作台的决策标签：完整的标签页语义和键盘操作，即 `aria-controls` 指向队列区域、左右方向键切换、Home / End 到首尾。
4. 计划页：只读账户看不到「去验收这次执行」，因为它去了也不能验收。

记在案的另外 8 条是后端问题，这一轮不动。

## 测试

- 单元测试：
  - 权限组合的校验，包括只读账户要 write 返回 403、其他组合 422；
  - 只读 Key 的写请求被拒绝，包括 RBAC 影子模式下；
  - 只读 Key 的 actor 是 `read_only`；
  - 撤销后 401；
  - 管理员看和撤销别人的 Key，非管理员 403；
  - 审计里没有完整的 Key；
  - 路由都是普通 `def`；
  - 前端的状态推算（有效 / 过期 / 撤销）、能不能选「读写」、4 个遗留问题里能写成纯函数的部分。
- E2E（:8001，四种账户，1440 / 390 / 320 px）：
  - 建只读 Key，用 curl 读返回 200、写返回 403；
  - 建读写 Key，能写；
  - 只读账户只能建只读 Key；
  - 撤销后 401；
  - 管理员在用户管理里看到数量，并能撤销别人的 Key；
  - Key 只显示一次、能复制；
  - 4 个遗留问题逐条验证；
  - 控制台没有错误，页面没有整页横向溢出。
