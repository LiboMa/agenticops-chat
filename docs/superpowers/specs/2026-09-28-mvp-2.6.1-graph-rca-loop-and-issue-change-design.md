### 0.1 现状事实（决定设计起点，均已对照代码 / 本地库核实）

图与定位：
1. **Issue 挂不到资源。** 901 条 Issue 里只有 111 条的 `resource_id` 能精确匹配 inventory。`health_issues` 没有 region，
   也没有指向 `cloud_resources` 的外键。`signal_gate._promote`（`services/signal_gate.py:386-399`）用
   `filter_by(resource_id=…).first()` 跨账户取第一条来定账户，匹配不上时退到"唯一启用账户"。
2. **三张图，各自有不同的读者。**
   - Galaxy：`galaxy_builds.rule_graph` / `llm_graph` 整块 JSON。构建 #15 有 1,560 个节点、2,143 条边（规则 1,923 条，LLM 220 条），只有 UI 读它。
   - GraphStore：`graph_nodes` / `graph_edges` 是 0 行。它的读者是 RCA 拓扑注入、策略 blast radius 和 patrol SPOF。
     `start_graph_sync` 没有启动调用，`sync_all()` 只遍历 `bedrock_region`。
   - RCA 的实时 VPC 工具：每次调用现建一张只含网络资源的图，看不到 EC2/RDS/Lambda，也没有 `account` 参数。
3. **拓扑是提示词文本，不能当证据。** `rca_agent.py:193` 的 `_build_topology_context` 把拓扑塞进提示词，
   evidence check 无法 grounding。`graph/context.py` 的上下游方向是反的，而且有测试把这个反向锁住了。
4. **`RCAResult` 没有"根因资源 / 受影响集合 / 传播路径"字段**，质量门也从不检查定位。
5. **`derive_rule_graph` 按裸 `resource_id` 建映射**（`galaxy/rules.py:70`）。库里有 36 组跨账户重复的 `resource_id`，
   后出现的会覆盖先出现的。
6. **规则层的新鲜度和 LLM 阶段绑在一起。** `galaxy/builder.build_graph` 整轮异常时，构建记为 failed，
   读取端只能继续用上一个 completed 构建。
7. **Galaxy 的健康叠加。** 没有 Issue 的节点默认显示 `healthy`，low 严重度也映射成 healthy，dismissed 的 Issue 仍会给节点上色。
8. **inventory 里没有 K8s 工作负载**，类型全是 AWS 的（IAMRole 543、SecurityGroup 214 …）。
   - `providers/kubernetes.py` 已经能列出 Node 和 Deployment；`cloud_resources` 按 `(account_id, provider, resource_id)` 唯一，本来就支持多 provider。
   - 本地库里同一个 EKS 集群有两行：id 140 是 `EKS` 类型，`resource_id` 为名字；id 1178 是 `EKS_Cluster` 类型，`resource_id` 为 ARN。
9. **`run_kubectl` 有两个凭证缺陷**（`skills/execution.py` 的 `_execute_kubectl`）：
   - 子进程不传 env。kubeconfig 里的 `aws eks get-token` 因此使用进程默认凭证，违反凭证铁律第 2 条。
   - `update-kubeconfig` 写入共享的 `~/.kube/config` 并切换 current-context，两个集群并发时命令可能落到错误的集群。
     另外，环境里有 `KUBECONFIG` 时会直接走捷径，跳过账户解析。
10. **chaos lab 的告警都是集群级的。**
    - `alarms/create-alarms.sh` 的告警名形如 `EKS-<cluster>-{NodeCPU-High, NodeMemory-High, PodRestarts-High, RunningPods-Low, APIServer-HighLatency, NodeCount-Low}`。
    - `e2e/scenarios.yaml` 的合成告警里没有 Dimensions，也没有 account。
    - 两个 evidence 场景（coredns-down、service-deleted）根本不发告警。
11. **告警 webhook 没有认证。** `webhook_secret`（`config.py:923`）定义了但从没用到。`api_auth_enabled=false`（默认）时
    `/api/webhooks/alert` 谁都能调。解析器会丢掉告警发生时间、服务名和账户线索。
12. **策略的 blast radius 处于休眠。**
    - `policy_engine.estimate_blast_radius`（`:853`）和 `simulate_fix_impact` 读的都是空的 GraphStore。
    - 因此 `policies.yaml` 的 `blast-radius-escalation`（`:46`，`blast_radius_gte: 3`）和 `impact-severity-escalation`（`:54`）从未触发过。
    - 一旦接上真实数据，这两条规则会立刻开始生效。

Issue / Plan / Change：

13. **审批没有绑定内容。** draft 和 pending_approval 状态的方案在批准前仍可修改，批准记录里没有版本或哈希。
14. **修复执行没有验证环节。**
    - `save_execution_result` 在 `status=="succeeded" and executor_auto_resolve and not is_change` 时直接关 Issue（`tools/metadata_tools.py:1427-1430`），不看 post_checks。
    - Change 一侧没有 post_checks 的方案总是落到 `needs_review`。
    - `needs_review` 的原因只记在 audit 和 event 里，UI 把时间线条目截断到 80 字。
15. **HealthIssue 状态在 18 处直接赋值**，未经过 `validate_status_transition`（`models.py:398`）：
    - `tools/metadata_tools.py`：626（经过校验）、741、745、955、1197、1430、1542、1582；
    - `web/app.py`：1939、2580、5001；
    - `cli/main.py`：976、983、2105、2134、2547；
    - `im/alert_pipeline.py`：233；
    - `services/pipeline_service.py`：192。

    其中：
    - `fix_executing` 从来没有被写过。
    - `mark_fix_failed`（`:1582`）无论当前是什么状态都写回 `fix_approved`，注释说是"留给重试或新方案"。但失败的方案已是终态，
      而 `fix_approved` 的合法出口只有 fix_executing / resolved / dismissed，走不到 `fix_planned`。结果是 Issue 停在"已批准"，
      既不能重试，也不能出新方案。
    - 一旦执行开始时写入 `fix_executing`，这一行就会变成非法转换 `fix_executing → fix_approved`。
    - false-positive 反馈（`web/app.py:5001`）的注释写着 "Dismiss the issue"，实际写入的却是 `resolved`。
16. **`dismissed` 已经存在**（`_ISSUE_TRANSITIONS`：可从 open…fix_executed 转入，可 reopen 到 open），并且在
    `ACTIVE_ISSUE_STATUSES` 里（`signal_gate.py:34`）。这个集合同时服务三处：
    - ② resolution 更新；
    - ③ 精确 fingerprint 合并（合并进 dismissed = 有意压制，正确）；
    - L2 灰区候选（`:246`，把 dismissed 的 Issue 交给 LLM 判合并，不正确）。
17. **Agent 读不到完整方案。**
    - `get_change_request` 只返回步骤数等摘要（`tools/change_tools.py:37`）。
    - `get_fix_plan` 只能按 Issue 查（`metadata_tools.py:1058`）。
    - 没有读取执行结果的工具。
18. **页面命名与内容不符。**
    - "Issues & Plans" 页里没有 plan。
    - "Change Plans" tab 列的其实是变更单。
    - IssueDetail 读的是旧的 anomaly 端点，所以 `trace`、`merged_alerts` 不渲染，Model 显示 `undefined`。
    - `useFixExecutions` 指向一个不存在的端点。
19. **真实数据以安全发现为主。** 787 条未关闭 Issue 里有 751 条来自 `security_poll`；草稿修复方案有 87 份。

### 0.2 决策（每条对应一次用户确认）

1. **范围。** 一份 spec 覆盖两条线。2.6.1 做"连接器契约 + K8s 连接器 + 评测"；Datadog / 观测云 / ServiceNow / MCP 连接器放到 2.6.2。
2. **事实图从 inventory 推导（方案 A）。**
   - 新建规范关系表 `resource_relations`，由 Galaxy 的 L1 规则写入；K8s 实体经连接器进入 `cloud_resources` 后也会自动进图。
   - GraphStore 的持久化路径退役。表不删，`start_graph_sync` 不删。
3. **定位只观察。** critic、置信度门槛、auto-fix 都不变。
4. **执行层以上全部分开。** 修复方案只属于 Issue，实施方案只属于变更单。`fix_plans` 共表和 Executor 门继续作为底层引擎。
   变更单的"方案"就是 ITIL RFC 里冻结下来、可执行的实施部分，不是第二个业务对象。
5. **变更单来源。** Chat、Web 表单、SRE，加一个外部通用入口 `POST /api/changes/intake`（HMAC + 时间戳）。
   ServiceNow / GitHub 专用适配器属于 P2。
6. **问题列表分视图。** 运维事件（默认）/ 安全发现 / 全部。
7. **dismissed。** 用户选的是"新增 dismissed"，核对后发现它已经存在，因此本版的工作是**统一语义**（§3.D.6）：
   - 保留精确 fingerprint 压制；
   - 从灰区候选、未关闭计数和节点上色中排除。
8. **没有 Issue 的节点显示 `unknown`（灰色）**，图例写"无告警 ≠ 健康"。
9. **告警 webhook 用共享令牌，不用 HMAC。** CloudWatch 经 SNS 推送、Alertmanager 都无法计算自定义 HMAC。
   能算签名的来源可以选用 HMAC 头；不配置 `webhook_secret` 时行为不变。
10. **向 GALA 借什么。**

    | 借鉴 | 在本设计中的落点 |
    |---|---|
    | GraphRAG 把图塞进上下文效果最差 | 拓扑从提示词注入改为 RCA 按需调用工具，结果可 grounding |
    | 有边界的扩展 | `get_topology_evidence` 默认 1 跳，按需 2 跳，节点/边有上限 |
    | 诊断包：时间窗 + 1 跳子图 + 精简证据 | 证据包以 Issue 发生时刻为中心取时间窗，列出邻居在窗口内的信号和变更 |
    | 支持证据 + 反证 | location 是 top-3 排序候选，每个候选带 `supporting[]` / `refuting[]` |
    | 统计先验压住 LLM | 候选按确定性规则排序，排序理由写在证据包里 |

    **不借：**
    - 并行多分支调查属于 Harness 阶段 2。
    - 它的准确率数字不能当我们的预期（受控基准，三种遥测齐全，代码未开源）。
    - GALA 从不评测图本身是否正确，这一项由我们的"图召回率"补上。

## 1. 目标与非目标

**目标**：
- **G1 身份锚定。** 每条新 Issue 都锚定到规范资源，或者被显式标为 `ambiguous` / `account_level` / `unanchored`，永远不取模糊匹配的第一条。
- **G2 一份事实。** UI、RCA、策略读同一张有版本的规范关系表，关系方向按类型定义。
- **G3 K8s 进图。** K8s 工作负载经连接器进入 inventory，并用确定性规则连到 EKS / EC2。
- **G4 可验证的定位。** RCA 通过工具取有边界的局部图证据包，输出结构化定位。代码按 fail-closed 校验后落库，人工可以对定位下判定。
- **G5 真值评测。** chaos lab 的 13 个场景都有 ground truth，报告图召回率和 AC@1 / AC@3 / MRR，并做开关对照。
- **G6 图上看得见。** 局部图组件能展示 Issue 点、四种逻辑关系、三层爆炸半径。
- **G7 审批绑定内容，执行后有验证。**
  - 审批绑定方案内容哈希。
  - 执行后做确定性验证，并提供人工验收。
  - Issue 状态只在一处写入。
  - dismissed 语义统一。
  - Agent 能读到方案全文和执行结果。
- **G8 界面整理。** 问题 / 变更 / 审计三块信息架构，IssueDetail 与 ChangeDetail 重排，命名统一。

**非目标**：
- 2.6.2 的内容：
  - Datadog（APM 服务图 / 部署事件）、观测云、ServiceNow CMDB 连接器；
  - MCP 声明式连接器；
  - Chat 声明关系（`declared`）；
  - 外部变更事件表；
  - patrol 拉回的外部告警接入 Signal Gate。
- 迁移到 PostgreSQL / Neo4j；LATS 树搜索；并行多分支调查。
- Chat 输入区与多模态（报告 §2）；Galaxy 的 token 优化。
- 新增 AWS 采集（TargetGroup / RouteTable / NACL / ENI）；安全可达性改接 GraphQueryService；攻击路径画成图。
- `simulate_fix_impact` 改造：它继续读 GraphStore，保持休眠。
- ServiceNow / GitHub 专用适配器和状态回写；告警 webhook 的外部状态回写。

## 3. 组件详细设计

### 3.A 图事实层（计划 A）

#### 3.A.1 IdentityResolver（`services/identity_resolver.py`）

```python
@dataclass(frozen=True)
class Anchor:
    status: str            # anchored | ambiguous | account_level | unanchored
    resource_ref: int | None      # cloud_resources.id
    account_id: int | None        # 解析出的账户（可能是回填的）
    rule: str              # 命中的规则名，写入 anchor_candidates 便于审计
    candidates: list[dict] # [{ref, reason}]；duplicate_of 也记在这里

def resolve(session, *, account_id: int | None, provider: str | None,
            resource_id: str | None, hints: dict | None, alarm_name: str | None) -> Anchor
```

**规则顺序**：限定在账户内，第一个命中的规则决定结果。

1. 精确匹配 `(account_id, resource_id)`。
2. ARN ↔ id 双向：输入是 ARN 时，取其资源段与 inventory 的短 id 比对；inventory 存的是 ARN 时，反过来比对（例如 `EKS_Cluster` 行）。
3. ALB 的 `app/<name>/<hash>` 形式 → 对应的 ELB 行。
4. 名称唯一匹配：`cloud_resources.name` 精确相等，账户内唯一。
5. 账户级模式：`AWS::::Account:…`、`…-root`、CIS 控制项 → `account_level`，`resource_ref` 为空。
6. K8s 线索：
   - `hints.pod` 去掉 ReplicaSet 哈希后缀（`-<rs-hash>-<5>` 或 `-<5>`）后，按 `(cluster, namespace, name)` 在 Deployment / StatefulSet / DaemonSet 中找；
   - 找不到时，找同名的 `K8s_Pod` 行；
   - `hints.namespace` → `K8s_Namespace`；
   - `hints.cluster` → EKS 集群行。
7. 告警名正则（`identity_alarm_name_patterns`，settings.yaml）。命名组 `cluster` 必填，`namespace` 可选。
   默认模式是 `^EKS-(?P<cluster>.+)-[A-Za-z0-9]+-[A-Za-z0-9]+$`，对应 chaos lab 的命名约定 `EKS-<cluster>-<Metric>-<Condition>`：
   贪婪匹配 cluster，只留下最后两段作为指标和条件。
   - 这样 `create-alarms.sh` 的 6 个告警能匹配上，`scenarios.yaml` 里的合成告警 `…-Backend-Unreachable` 也能匹配上。
   - 如果只列 6 个后缀，后者会漏掉。

   解析结果交给规则 6（cluster / namespace）。正则取出的 cluster 名在 inventory 里找不到时，结果为 `unanchored`，不会误锚。

**结果判定**：
- 某条规则命中恰好 1 个物理资源 → `anchored`。
- 命中 ≥ 2 个 → `ambiguous`，全部记入 candidates，`resource_ref` 为空。
- 全部规则都未命中 → `unanchored`。

**同一物理资源的多行**：同账户、同 region（空 region 时从 ARN 取），同名且类型属于同一族
（`identity_type_families`，默认 `{EKS: [EKS, EKS_Cluster]}`）的多行，算作一个物理资源：
- 取 `scanned_at` 最新的一行作为锚点，**不算歧义**；
- 其余行记进 candidates，`reason: duplicate_of`。

例（本地库）：
- id 140（`EKS`，名字）和 id 1178（`EKS_Cluster`，ARN）都是 ap-southeast-1 的 `agenticops-lab`，属于同一个物理资源。
- id 1177 是 us-west-2 的同名集群，是另一个物理资源。所以只给 `agenticops-lab`、不给 region 时，结果是 `ambiguous`。
- chaos lab 集群 `agenticops-chaos-lab`（id 1355，us-east-1）是唯一的。

**不知道账户时**：
- 在所有启用账户里依次跑上述规则。恰好一个物理命中时锚定，并把 `account_id` 回填到 Issue；多个命中时为 `ambiguous`。
- **不再退到"唯一启用账户"去猜。** 只有一个启用账户时，跨账户搜索自然等价于账户内搜索。

**接入点**：
- `signal_gate._promote` 替换 `:386-399`：先调用 `resolve()`，再用 `anchor.account_id` 写 `account_id`。
- fingerprint-v2 在锚定之前就已算好，保持不变。合并进已有 Issue 时不重新锚定。

**HealthIssue 新增列**：
- `resource_ref`（FK `cloud_resources.id`，可空，建索引）；
- `anchor_status`（String(20)）；
- `anchor_candidates`（JSON：`{"rule":…, "candidates":[…]}`）；
- `observed_at`（DateTime，可空：信号源给出的故障发生时刻）。

解析输入里的 hints 写进 `metric_data["hints"]`，合并时不覆盖，供之后重新锚定使用。

**回填和重新锚定**：
- 迁移时对所有现存 Issue 跑一次 `resolve()`，输入取已有的 `resource_id` / `account_id` / `alarm_name`。
- 此后每次构建完成（normal 或 rule-only），对状态属于 `OPEN_ISSUE_STATUSES`（§3.D.6）、且 `anchor_status ∈ {unanchored, ambiguous}` 的 Issue 再跑一次。
- 重新锚定只把状态往 `anchored` / `account_level` 方向推进，不会把已锚定的改回去。

#### 3.A.2 规范关系表与关系注册表

`resource_relations`（新表）：

| 列 | 说明 |
|---|---|
| `id` | PK |
| `build_id` | FK `galaxy_builds.id` |
| `account_id` | 两端必须同账户；跨账户关系不写入（本版没有这种规则） |
| `src_ref` / `dst_ref` | `cloud_resources.id` |
| `relation_type` | 注册表中的类型 |
| `provenance` | `rule` \| `llm`；`observed` / `declared` 为 2.6.2 预留，本版不写 |
| `evidence` | JSON：推导依据（raw_data 路径 + 值，或 LLM 的 evidence 引用） |
| `confidence` | rule 固定为 1.0；llm 取模型给的值 |
| `observed_at` | 推导时刻 |

索引：`(src_ref, relation_type)`、`(dst_ref, relation_type)`、`(build_id)`。

- 只存资源和资源之间的关系。账户、标签分组只用于缩小范围，不参与故障传播，继续留在 Galaxy JSON 里。
- 行数守恒：同一次 build 中，`provenance=rule` 的行数等于 `rule_graph` JSON 里两端都是资源的边数。

**关系注册表**（`graph/relations.py`，纯数据 + 函数）：定义每种类型的故障传播方向。

| relation_type | 例子（src → dst） | 故障传播方向 |
|---|---|---|
| `contains` | subnet → ec2，cluster → namespace → deployment | src（父）→ dst（子） |
| `secured_by` | ec2 → sg | dst（sg）→ src |
| `attached_to` | ebs → ec2 | src（ebs）→ dst |
| `routes_to` | elb → ec2 / service，service → deployment，ingress → service | dst（目标）→ src |
| `manages` | asg → ec2 | 双向 |
| `uses` | lambda → role / kms，deployment → configmap / secret / pvc | dst（被使用者）→ src |
| `restricts` | networkpolicy / pdb → deployment | src → dst |
| `runs_on` | deployment → node | dst（node）→ src |
| `same_as` | k8s node ↔ ec2 | 双向 |
| `references` / `inferred_group` | 仅 LLM | 不传播，只作展示 |

**与现有类型的关系**：
- 现有的 `rules.RELATION_TYPES` 有 7 种：contains / references / member_of / attached_to / secured_by / routes_to / inferred_group。
  规则层目前只产出 contains、secured_by、member_of。
- `member_of` 是资源指向标签分组节点的边，留在 Galaxy JSON 里，不写入 `resource_relations`。
- 新增的 manages / uses / restricts / runs_on / same_as 只由规则产出。
- LLM 提示词允许的类型集合保持现在这 7 种不变。拆成独立的 `LLM_RELATION_TYPES`，LLM 的行为不变。

`upstream(x)` 指 x 依赖的资源，也就是故障会从它们传给 x 的一方，用于找根因候选。
`downstream(x)` 指依赖 x 的资源，用于看影响范围。**过去"入边就是上游"的写法作废。**

#### 3.A.3 Galaxy 构建的改动（`galaxy/rules.py`、`galaxy/builder.py`）

1. **`rid_to_node` 改为按 `(account_id, resource_id)` 建键**（`rules.py:70`）。id 引用只在同账户内解析。
2. **新增 AWS 规则**（全部 `provenance=rule`，依据写进 evidence）：
   - ASG → EC2（`manages`）；ELB → ASG（`routes_to`，只取 ASG 的 `LoadBalancerNames`；`TargetGroupARNs` 需要采集 TargetGroup，属于非目标）；
   - 子网 → RDS（`contains`，取 DB 子网组里的每个子网）；RDS → SG（`secured_by`）；
   - 子网 → ELB（`contains`，取 `AvailabilityZones[].SubnetId`）；ELB → SG（`secured_by`）；
   - Lambda → Role / KMS（`uses`）。

   边一律写成注册表里的 src → dst 方向。raw_data 里缺少字段时，这条规则不产出边。
3. **新增 K8s 规则**（全部 `provenance=rule`）：
   - EKS 集群 `contains` Namespace，Namespace `contains` 命名空间内对象；集群 `contains` Node。
   - Service → 工作负载：selector 匹配 pod template labels（`routes_to`）。Ingress → Service：按 backend 匹配（`routes_to`）。
   - 工作负载 `uses` ConfigMap / Secret / PVC：取 volumes、envFrom、env.valueFrom。引用的对象不存在时，写进该工作负载 raw_data 的 `unresolved_refs`，不生成边。
   - NetworkPolicy / PDB `restricts` 工作负载：按 podSelector / selector 匹配。
   - 工作负载 `runs_on` Node：取汇总进来的 pod 所在节点。
   - K8s Node `same_as` EC2：用 `providerID` 形如 `aws:///<az>/<instance-id>`，取出 instance-id，在同账户 inventory 里找 EC2。
   - ELB `routes_to` Service：Service `status.loadBalancer.ingress[].hostname` 等于 ELB 的 DNSName。
   - `absent_since` 非空的行（§3.B.2）照常参与推导，所以它们的关系保留"最后一次看到"的样子。
4. **规则层和 LLM 层解耦**（报告 §6）：
   - **normal 构建**：`derive_rule_graph` 完成后，立即把规则关系写进 `resource_relations`，并设置 `galaxy_builds.rules_published_at`，然后再进入 LLM 阶段。
     LLM 阶段异常时构建仍记为 failed，但规则行保留且可读。LLM 边在构建 completed 时一起写入。
   - **`build_graph(trigger, full=False, llm=True)` 新增 `llm` 参数。** `llm=False` 是 rule-only 刷新：
     - 重新加载 inventory → 推导 → 写规则关系；
     - 从上一个 completed 构建带过来 LLM 边，只带两端仍存在的；
     - 状态为 completed，token 为 0；
     - **不写** `galaxy_resource_state`。它是 LLM 增量的 diff 基线，所以下一次 normal 构建仍能看到自上次 LLM 处理以来的全部变化。
   - **并发**：rule-only 刷新不占 `status="running"` 行锁（否则会被正在跑 LLM 的 normal 构建挡住）。
     规则推导 + 写入阶段由一把进程内锁串行，normal 构建的规则阶段和 rule-only 刷新共用这把锁。
   - **读取**：
     - GraphQueryService 读 `rules_published_at` 最大的构建；
     - Galaxy 全景 UI 继续读最新的 completed 构建。

     两者可能差一次 rule-only 刷新，这在 `/api/graph/focus` 的 `build_id` 里可见。
   - **清理**：`_prune_old_builds` 同时删除被清理构建的 `resource_relations` 行。定位路径内联保存在 RCAResult 里（§3.C.3），所以展示不依赖已被清理的构建。
5. **重新锚定钩子**：构建完成（normal 或 rule-only）后调用 §3.A.1 的重新锚定。
6. **K8s 类型不参与 LLM 补边。** 12 个 `K8s_*` 类型加 `K8s_Pod` 追加进 `galaxy_llm_exclude_types`（settings.yaml），因为它们的关系已经能确定性地推出来。
7. **内容哈希排除易变字段**（`galaxy/hashing.py`）：K8s 行里汇总的 pod 状态（ready / restarts / 终止原因 / 等待原因 / 节点）不计入哈希，
   避免每轮采集都被判为"有变化"。结构字段（spec、selector、引用）仍计入。

#### 3.A.4 GraphQueryService（`graph/query_service.py`）

```python
def neighborhood(ref: int, *, depth: int = 1, direction: str = "both",   # up | down | both
                 relation_types: list[str] | None = None, node_cap: int = 200,
                 edge_cap: int = 500, include_llm: bool = False) -> Subgraph
def potential_impact(ref: int, *, depth: int = 3) -> Subgraph            # 只往下游，只用 rule（+2.6.2 的 observed）
def observed_impact(ref: int, *, window: tuple[datetime, datetime]) -> Subgraph
```

- **`Subgraph` 的内容**：
  - `nodes[]`：ref、类型、名称、账户、region、`absent`、`hops`；
  - `edges[]`：src、dst、relation_type、provenance、evidence、`direction_label` 取 upstream 或 downstream；
  - `build_id`；
  - `truncated` 和 `truncated_reason`。
- **SQL 次数**：每跳做一次批量查询（边查询 `WHERE src_ref IN (…) OR dst_ref IN (…)`，再批量取节点）。SQL 条数 ≤ 2×depth+1。
- **账户范围**：只返回和起点同账户的节点。
- **默认关系集**：按 issue_type 决定，默认映射写在注册表里：
  - 网络类：contains / secured_by / routes_to / restricts / uses；
  - 计算类：再加 attached_to / manages / runs_on / same_as；
  - 数据库类：contains / secured_by / uses；
  - 其他：全部 rule 关系。
- **修订（2026-10-01，Plan C 终审 I-3）：** 网络类与计算类默认关系集都加上 K8s 规则关系 `restricts`（NetworkPolicy / PDB → 工作负载）与 `uses`（工作负载 → ConfigMap / Secret / PVC）。原表按 AWS 写成，这两种 §3.A 自己定义的 K8s 关系从计算类、网络类 Issue 都走不到，而它们正是配置类和网络策略类故障的根因所在。数据库类与"其他"不变。
- **截断是确定性的**：超出上限时，按候选排序（§3.C.1）保留靠前的节点。有自身信号的节点排在前面，所以异常节点不会被截掉。
- **缓存与健康叠加**：进程内按 `(build_id, 参数)` 缓存拓扑。健康叠加不进缓存，每次现读 Issue 状态。
- **`observed_impact`**：取潜在影响里在时间窗内自己也有 signal（`alert_events`）或未关闭 Issue 的节点。
- **HTTP 入口** `GET /api/graph/focus`：
  - 三选一传入 `issue_id`、`resource_id`（即 `cloud_resources.id`）或 `change_request_id`，起点分别取 Issue 的锚点、资源本身，或变更单已落地的 `target_resources[].db_id`（2.6.0 已有，可以有多个起点，结果取并集）；
  - `node_cap` 可传 1–10000（评测要用大上限），默认 `graph_query_node_cap`；
  - 返回 `Subgraph` 加上健康叠加和三层爆炸半径的计数。

#### 3.B.1 契约（`connectors/base.py`）

```python
@dataclass

    provider: str; resource_type: str; resource_id: str; name: str
    region: str; raw_data: dict; tags: dict; status: str

@dataclass

    ...

@dataclass
```

- `RelationObservation`（Trace / APM / CMDB 关系）**只在这里定义形状**，等 2.6.2 第一个会产生关系观测的连接器出现时再实现。本版不写空代码。

#### 3.B.2 唯一写入口 `ingest()`（`connectors/ingest.py`，确定性）

- **entities**：按 `(account_id, provider, resource_id)` upsert 进 `cloud_resources`，设置 `scanned_at = now`，把 `absent_since` 置空。
- **signals**：逐条调 `process_signal`。
- **缺席判定**：只有当 `completeness[(scope, kind)]` 为真时，才把该 scope + kind 下这次没看到的行标上 `absent_since = now`。
  永不删除。任何部分采集的 kind 一律不动。
- **运行记录**：每次运行写一行 `connector_runs`：
  - 标识：`id, connector, account_id, scope, trigger(schedule|manual|rca)`；
  - 时间：`started_at, finished_at`；
  - 结果：`status(complete|partial|failed), counts(JSON), per_kind(JSON), error`。
- **返回值**：`changed: bool`，表示结构哈希是否有变化，供调度决定是否刷新。
- **AWS 扫描不能动 K8s 行。** 现有 AWS 扫描的旧行处理必须限定在 `provider="aws"`，由测试守住，避免把 `provider="kubernetes"` 的行当成过期。
- **修订（2026-09-30）：** 主人把两件事并入 Plan B（Tasks 9–13）。一是 AWS W2 扫描（`scanner/engine`）在某个种类完整列出之后，也把这次没看到的行标上 `absent_since`，只限 `provider="aws"`，并加一个 `resource-scan` 调度（默认每小时）定时跑这次扫描，标缺席不必等人手动触发。二是所有资源计数和列表统一用同一个"存在"定义（`absent_since IS NULL`），API 与 Dashboard 的数字一致。
- **修订（2026-10-01，P-1，终审 I-1）：** 父→子的存在规则：容器（集群）已被一次完整列出证明不在了，它下面的行也标上 `absent_since`，永不删除，再次看到时恢复。落到 K8s 连接器上，`targets()` 在三个条件同时成立时给这个集群一个墓碑目标：W2 已把某集群的 `EKS`/`EKS_Cluster` 行标为缺席；同一启用 aws 账户里没有同名的在场行；该集群 scope（`<cluster>/` 前缀，与 `ingest()` 同一个 substr 比较）下还有在场的 `provider="kubernetes"` 行。墓碑目标的 `collect()` 不调 kubectl，不解析凭证，报告每个 kind 都完整且为空，于是 `ingest()` 把这些行标为缺席，并照常写一行 `connector_runs`。墓碑目标同样服从 `account=` / `scope=` 过滤。`kubernetes` 账户的集群不在 W2 的列出范围内，所以不算证据；从未见过的集群行同样不算。集群回来后，它的行重新在场，`targets()` 给它普通目标，`mark_seen` 把 K8s 行恢复。
- 推送源（webhook）继续走现有的 alert_processor → 解析器 → `process_signal`，只补字段（§3.B.5），不经过 `ingest()`。

#### 3.B.3 K8s 连接器（`connectors/k8s.py`）

**目标**：
- inventory 中属于启用 AWS 账户的 EKS 集群。`EKS` / `EKS_Cluster` 按 §3.A.1 的物理资源去重，每个物理集群只采一次。
- 加上 `kubernetes` provider 类型的账户。

**采集对象**：共 12 类，存成 `K8s_<Kind>` 类型：
Namespace、Deployment、StatefulSet、DaemonSet、Service、Ingress、Node、ConfigMap、Secret、PersistentVolumeClaim（`K8s_PVC`）、PodDisruptionBudget（`K8s_PDB`）、NetworkPolicy。
- `resource_id`：命名空间内对象为 `<cluster>/<Kind>/<ns>/<name>`，集群级对象为 `<cluster>/<Kind>/<name>`。
- `region`：集群所在 region。
- `provider`：`kubernetes`。
- `account_id`：拥有该集群的账户（EKS 时即那个 AWS 账户）。

**Pod 和 ReplicaSet**：只列出来做汇总，不存成节点，只有一个例外：
- 没有 ownerReferences 的裸 Pod 存成 `K8s_Pod`。resource-stress 场景的 `stress-test` 就是这种。
- 其他 Pod 的状态汇总进所属工作负载的 `raw_data.pod_summary`：`ready/desired`、`restarts`、最近的终止原因（如 OOMKilled）、等待原因（如 ImagePullBackOff、CreateContainerConfigError）、所在节点。

**raw_data 用字段白名单**：
- Secret 只存 name + type。**绝不存 `data` / `stringData`**，由测试守住。
- ConfigMap 只存 key 列表和 data 的 sha256。
- 工作负载存 selector、template labels、volumes、envFrom 和 env 的引用名、replicas、conditions，以及 `unresolved_refs`（由规则推导时写入）。

**完整性**：每类对象单独调用一次 `kubectl get <kind> -A -o json`。成功且没超出字节上限的 kind 标为完整；
失败或超上限的 kind 标为部分，不参与缺席判定。

#### 3.B.4 kubectl 凭证入口（与 `run_kubectl` 共用）

- **新函数** `credentials/kube.py: kubectl_env_for_cluster(account, cluster, region) -> dict`：

  2. 私有 kubeconfig 路径为 `<data_dir>/kube/<account_id>/<region>/<cluster>.kubeconfig`，权限 0600，

  3. 返回 env + `KUBECONFIG=<path>`。kubeconfig 里 `aws eks get-token` 的 exec 插件继承这个 env，所以拿到的也是目标账户凭证。
- **`kubernetes` 账户**：复用 `KubernetesProvider._kubectl_env`。
- **`skills/execution._execute_kubectl` 改用这个入口**：
  - 子进程显式传 env；
  - 删掉"环境里有 `KUBECONFIG` 就直接用"的捷径；
  - 永不读写 `~/.kube/config`，也不切 current-context。
- **失败处理**：凭证解析失败或 kubeconfig 生成失败时显式报错，不退到 ambient。

#### 3.B.5 Webhook 字段补全与令牌校验

- **字段补全**：6 个解析器（datadog / pagerduty / grafana / prometheus / cloudwatch / generic，`integrations/parsers.py`）补出：
  - `observed_at`：来源里的告警发生时间，例如 CloudWatch 的 `StateChangeTime`、Alertmanager 的 `startsAt`；
  - `hints`：`{account, region, cluster, namespace, workload, pod, service}`，按来源已有的维度或标签填，缺的就留空。

  `SignalInput` 新增 `observed_at` 和 `hints` 两个字段，fingerprint-v2 不变。
- **令牌校验**：配置了 `webhook_secret` 时，`POST /api/webhooks/alert` 和 `POST /api/webhooks/alert/{source}`：
  - 从 `APIAuthMiddleware` 的 Bearer 校验中豁免；
  - 改为要求令牌：可以放在 `Authorization: Bearer <secret>`、`X-AIOps-Token` 或 `?token=` 中，用 `hmac.compare_digest` 比较；

  没有配置 `webhook_secret` 时行为不变，启动时打印一条 WARNING。
- settings.yaml 新增 `webhook_secret: ""`。chaos lab 的 e2e 客户端（`infra/eks-chaos-lab/e2e/client.py`）从 `AIOPS_WEBHOOK_SECRET` 读取令牌并发送。

### 3.C RCA 定位闭环与评测（计划 C）

#### 3.C.1 工具 `get_topology_evidence(issue_id, depth=None, window_minutes=None)`

**深度**：默认 1 跳。锚点是集群、Namespace、VPC 这类容器时默认 2 跳，因为它们 1 跳内只有子容器，看不到工作负载。
显式传入时以传入值为准，最大 `graph_query_max_depth`。

**时间窗**：以 `observed_at or first_seen` 为中心，向前取 `rca_topology_window_before_minutes`（默认 30），向后取 `…_after_minutes`（默认 10）。

**返回**：
- `anchor`：ref、类型、名称、`anchor_status`。
- `edges[]`：双向邻域，边上带 `direction_label`（upstream / downstream）、relation_type、provenance、evidence。
- `neighbors[]`：每个邻居在窗口内自己的 signal / Issue，以及变更。变更包括：
  - K8s 的 `creationTimestamp` 落在窗口内；
  - 结构内容哈希在窗口内变过；
  - 本系统在窗口内对它的执行记录。
- `candidates[]`：确定性排序，每个候选带 `reasons[]`。排序键依次为：
  1. 自身处于异常状态（pod_summary 里有等待 / 终止原因、ready < desired、未关闭 Issue）；
  2. 窗口内有变更；
  3. 自身信号发生得更早；
  4. 跳数更少；
  5. 最后按 ref 升序打破平局。
- **修订（2026-10-01，Plan C 终审 M-2）：** 锚点是容器（集群 / 命名空间 / 网络）时，锚点本身排在所有候选之后；锚点的原因里，本 Issue 写作 "this issue #N"，不算佐证。排序函数 `rank_key` 不变（它也服务 `/api/graph/focus`），这一步只在证据包里做。
- `build_id`、`truncated`、`freshness`（`fresh` / `stale` + 原因）。

**缺数据时**：没有锚点（`unanchored` / `ambiguous`）或没有已发布的构建，返回 `available:false` 加原因。
`ambiguous` 时同时列出候选，**绝不说成"没发现问题"**。

**注入**：`rca_topology_context_enabled` 控制是否把这个工具注入 RCA，并同步修改 RCA 提示词。
提示词里写的是概念类别，不写 AWS 专名（云中立）。

#### 3.C.2 RCA 时的定向重采

**触发条件**：锚点是 EKS 集群或 K8s 实体，且该集群上一次成功采集早于 `rca_k8s_recollect_min_age_seconds`（默认 120）。

**执行**：
1. 同步做一次有上限的 `collect`，只采该集群，超时 `rca_k8s_recollect_timeout_seconds`（默认 60）。
2. `ingest(trigger="rca")`。
3. 有变化时做一次 rule-only 刷新。
4. 然后再组装证据包。

**失败处理**：`freshness: stale` 并写明原因，然后用已有数据继续，不中断 RCA。
`min_age` 同时起限流作用，防止同一集群的多个 RCA 反复重采。
- **修订（2026-10-03，T10 联调 E2E）：** 触发条件加一条：集群上一次成功采集早于本 Issue 的故障起点（`observed_at`，缺省 `first_seen`）时，即使不到 `min_age` 也重采。故障前的采集再新也看不到故障：联调里每个用例 RCA 后的手动刷新，让下一个用例的 RCA 落在 120 s 内，重采被跳过，证据包里没有刚注入的对象，定位落到上一个用例的对象上。真实环境同样会发生（发现调度刚跑完、告警来得快）。`min_age` 仍限流同一故障的多次 RCA。

#### 3.C.3 `save_rca_result` 的定位参数与 fail-closed 校验

- 证据类型新增 `graph`：引用 `get_topology_evidence` 返回的边或候选，evidence check 可以 grounding。
- 新增可选参数：

```json
location = {
  "candidates": [ {"ref": 123, "rank": 1, "supporting": ["E2","E5"], "refuting": ["E7"]}, … ],  // 最多 3 个
  "path": [ {"src_ref": 123, "dst_ref": 88, "relation_type": "routes_to"}, … ]                    // 根因 → 症状锚点
}
```

- **代码校验（fail-closed）**：
  - 每个候选的 ref 必须存在于 `cloud_resources`，且与 Issue 同账户，否则丢弃该候选。
  - `path` 的每条边必须在 `location_build_id`（取本次调用拿到的 `build_id`）的 `resource_relations` 里存在，
    且 provenance ∈ {rule, observed}，否则丢弃整条 path。
  - `supporting` / `refuting` 里的引用必须是本次 RCA 的证据条目，否则丢弃该引用。
  - Issue 未锚定时 `path` 必须为空，非空则丢弃。
- **`location_status` 的判定**：
  - `valid`：全部保留；
  - `partial`：有部分被丢弃，但至少还剩 1 个候选；
  - `invalid`：给了 location，但一个候选都没剩下；
  - `absent`：没给 location。

  RCA 结果本身照常保存。
- **`RCAResult` 新增列**：`location`（JSON，存校验后的候选和内联 path，每条边带两端名称，不依赖构建是否还在）、
  `location_status`、`location_build_id`、`location_verdict`（correct | partial | incorrect）、`location_verdict_by`、`location_verdict_at`。
- **只观察**：critic、置信度门槛、auto-fix 全部不变。

### 3.D Issue / Change 逻辑（计划 D）

#### 3.D.1 方案版本与内容哈希

- **`fix_plans` 新增列**：`plan_version`（int，默认 1，每次更新草稿 +1）、`content_hash`、`approved_hash`、`approved_version`。
- **`content_hash`**：对 `steps / rollback / pre_checks / post_checks / account / risk` 的规范 JSON（`sort_keys`、紧凑分隔符）做 sha256，每次写入都重新计算。
- **approve API**：
  - `PUT /api/fix-plans/{id}/approve` 和 `POST /api/changes/{id}/approve` 的请求体必须带 `content_hash`（后者校验的是该变更单当前的实施方案）。
  - 缺失时返回 422，与当前值不一致时返回 409。
  - 批准时写入 `approved_hash` 和 `approved_version`，自动审批也同样写。
- **执行前比对**：`get_approved_fix_plan`（`metadata_tools.py:1238`）比对当前哈希和 `approved_hash`。
  不一致时拒绝执行，本次执行记录为 `aborted`（`FixExecution` 已有这个状态，`models.py:690`），并附原因 `content changed after approval`。之后：
  - **fix**：方案 `approved → rejected`（即撤回，合法），Issue `fix_approved → root_cause_identified`（新增转换，见 §3.D.5），可以重新出方案。
  - **change**：沿用 2.6.0 的映射，`on_execution_result` 把 aborted 记为 `failed` 并写明原因。
- **迁移**：已批准的方案用当前哈希回填 `approved_hash` / `approved_version`，保证它们仍能执行。
- 不做幂等键，已有的 CAS 够用。
- **命名**：一律写成 "I#12 修复方案 v2" / "C#3 实施方案 v1"，不再单独出现 "Plan #N"。Main 的提示词同步修改。

#### 3.D.2 变更单自带步骤与外部引用

- **`change_requests` 新增列**：
  - `proposed_steps`（JSON，与 `fix_plans.steps` 同形）；
  - `external_ref`（JSON `{system, ticket_id, url, requested_by?}`）；
  - `external_system` / `external_ticket_id`（String，从 external_ref 拆出，建联合索引，只用于去重查询；SQLite 上 JSON 字段不便建索引）；
  - `steps_diff`（JSON）；
  - `needs_review_reason`（Text：进入 needs_review 时写入，页面顶部直接读它）。
- **来源**：`request_change` 工具（agent 把 Chat 里说出的步骤映射成 proposed_steps）、Web 的 NewChangeDialog、intake。
- **SRE Mode C 的校验模式**：有 `proposed_steps` 时，SRE 不再自己编步骤，只做校验：
  - 目标能否实证；
  - 命令是否符合申请意图；
  - 风险和策略判定；
  - 补上缺少的 rollback / post_checks。

  命令被判为 blocked 的，变更单直接 rejected。
- **差异由代码计算**：`submit_change_review` 时对比"申请步骤"和"实施方案步骤"，算出新增、删除、修改的步骤，存入 `steps_diff`，不交给 LLM。
- **不变量**：外部来源只能创建变更单，之后同样走 SRE 审核 → 策略 → 人工审批。

#### 3.D.3 外部入口 `POST /api/changes/intake`

**认证**：
- 配置项 `change_intake_secret`。为空时返回 404，即默认关闭。
- 需要 `X-AIOps-Signature: sha256=HMAC(timestamp + "." + body)` 加 `X-AIOps-Timestamp`，时间窗 ±300s。签名错误或超出时间窗返回 401。
- 这个路径从 Bearer 中间件豁免，HMAC 就是它的认证。

**请求体**：`title, description, justification?, account（账户名）, target_hints?, proposed_steps?, external_ref（必填）, requested_by`。
`requested_by` 是外部系统里的申请人，只是声称的名字，不作为身份，存进 `external_ref.requested_by`。

**身份与流程**：`change_requests.requested_by` 写 actor key `webhook:<external_ref.system>`，`source=webhook`，创建后异步开始审核。

**去重**：同一 `(external_system, external_ticket_id)` 已有未终结的变更单时，返回原变更单（200）。新建时返回 201。

**权限**：rbac.yaml 新增一条 `enforce: always` 规则：`webhook:*` 永远不能 approve / execute，影子模式下也返回 403。

#### 3.D.4 统一的执行后验证（`services/verification.py`）

- **`fix_executions` 新增列**：`verification_status`、`verification_reason`、`accepted_by`、`accepted_at`、`acceptance_note`。
- **`evaluate(execution) -> (status, reason)`**：纯函数，fix 和 change 共用。

  | 结论 | 条件 | Incident | Change |
  |---|---|---|---|
  | `passed` | 执行 succeeded，且 post_checks 非空并全部通过 | 关闭 Issue（遵守 `executor_auto_resolve`，否则停在 `fix_executed`） | `completed` |
  | `failed` | 执行 failed / rolled_back，或任一 post_check 失败 | Issue 回到 `root_cause_identified`，RCA 标记 `disputed_by_execution` | `failed` / `rolled_back`（维持 2.6.0 的映射），post_check 失败时为 `needs_review` |
  | `pending_acceptance` | 执行 succeeded，但有 warning、缺少 post_checks 或结果缺失 | 停在 `fix_executed`，等人工验收 | `needs_review`，`needs_review_reason = verification_reason` |

- **`save_execution_result` 不再自己关 Issue**（删除 `:1427-1430`），改为调用 `evaluate` 再调用 `transition_issue`。
  Change 一侧继续由 `on_execution_result` 写终态，它内部改为调用 `evaluate`。
- **人工验收** `POST /api/fix-executions/{id}/accept {decision: accepted|rejected, reason}`：
  - 理由必填，身份取认证会话；`webhook:*` 返回 403。
  - accepted 时：Issue 转为 resolved，或变更单转为 completed。
  - rejected 时：Issue 转为 `root_cause_identified`，或变更单转为 failed。
  - 变更单一侧复用现有的 `resolve_review`，保证终态仍然只由它和 `on_execution_result` 写。
- **三个维度各有唯一来源**：业务状态看 Issue / 变更单，执行状态看 `fix_executions.status`，验证状态看 `verification_status`。
  `failed` 不代表已经回滚，回滚结果单独展示。
- 进入 `pending_acceptance` 时发出通知 `execution_pending_acceptance`，带原因和深链。

#### 3.D.5 `transition_issue()`：唯一的状态写入口

- **`services/issue_state.transition_issue(session, issue_id, new_status, *, actor, reason, expected=None)`**：
  1. 先经过 `validate_status_transition`；
  2. 再做 `UPDATE … WHERE id=:id AND status=:expected` 的 CAS，0 行时抛 409 类异常；
  3. 最后写 pipeline event。
- §0.1 第 15 条列出的 18 处全部改走它。有一个 grep 测试守住：`src/` 里除 `issue_state.py` 以外不得出现对 HealthIssue 的 `.status =` 赋值。
- **执行开始**时写 `fix_approved → fix_executing`。
- **`_ISSUE_TRANSITIONS` 新增三条转换**，目标都是 `root_cause_identified`：

  | 起点 | 触发场景 |
  |---|---|
  | `fix_approved` | 执行前被中止（哈希不一致） |
  | `fix_executing` | 执行失败 |
  | `fix_executed` | 验证失败或验收被拒 |

- **`mark_fix_failed`**：不再无条件写回 `fix_approved`，改为经 `transition_issue` 转到 `root_cause_identified`。
  这样修掉 §0.1 第 15 条的死路，Issue 可以再走一次 `fix_planned`。

#### 3.D.6 dismissed 语义统一

- `signal_gate.py` 把现有集合拆成两个：
  - `SUPPRESSING_ISSUE_STATUSES`：等于现在的 `ACTIVE_ISSUE_STATUSES`，含 dismissed。继续用于 ② resolution 更新和 ③ 精确 fingerprint 合并。
    合并进 dismissed 是有意的压制，保留。
  - `OPEN_ISSUE_STATUSES`：同样的集合去掉 dismissed。用于 L2 灰区候选、未关闭计数、节点上色、重新锚定。
  - `ACTIVE_ISSUE_STATUSES` 这个名字保留为 `SUPPRESSING_ISSUE_STATUSES` 的别名，`metadata_tools` 的现有导入不受影响。
- false-positive 反馈（`web/app.py:5001`）改为经 `transition_issue` 写入 `dismissed`。
- 历史上被写成 resolved 的误报不改。

#### 3.D.7 只读工具（注入 Main）

## 6. 失败模式（统一 fail-closed）

| 情况 | 处理 |
|---|---|
| 锚定不上 / 有歧义 | `unanchored` / `ambiguous`，记录候选，绝不取第一条；RCA 照常跑 |
| 图没有已发布的构建 / 锚点缺失 | `get_topology_evidence` 返回 `available:false` 加原因，不当作"没发现问题" |
| LLM 阶段失败 | 构建为 failed，但规则关系已发布、可读 |
| K8s 某类采集失败或超上限 | 该 kind 为部分，不做缺席判定；运行记为 partial |
| 凭证解析失败 / kubeconfig 生成失败 | 显式报错，不退到 ambient；该目标的运行记为 failed |
| RCA 定向重采失败 | `freshness: stale` 加原因，用已有数据继续 |
| 定位的候选、路径或引用不合法 | 丢弃不合法部分，`location_status` 取 partial / invalid |
| 审批时哈希对不上 | 409 |
| 执行前哈希 ≠ 批准哈希 | 拒绝执行，执行记为 aborted 并附原因，Issue 转为 `root_cause_identified` |
| 缺少验证结果或 post_checks | `pending_acceptance`，永远不算 passed |
| 告警 webhook 已配置令牌但请求没带 | 401 |
| intake 未配置 / 签名错误或过期 | 404 / 401 |
| `webhook:*` 尝试 approve / execute / accept | 403，影子模式下也是 |

## 8. 验收标准

1. **锚定率**：有 `resource_id` 的未关闭 Issue 在回填后，`(anchored + account_level) / 总数` ≥ 95%。
   达不到时报告原因分布，**不放宽规则去凑数**。36 组跨账户重复 id 一次都不错配账户。
2. **查询性能**：2 跳邻域查询的 SQL 条数 ≤ 5；本地库上 p95 < 200ms。
3. **图召回率 ≥ 12/13**：确定性判定，硬门槛。
4. **定位有效率**：on 批次中 `location_status ∈ {valid, partial}` 的比例 ≥ 90%；无效引用绝不会被记成 valid。
5. **定位准确率**：AC@1 / AC@3 / MRR 的 off / on 对照如实报告，**不设门槛**（样本只有 13 个）。
6. **连接器安全**：Secret 行里没有 data 字段；部分采集不会产生 absent；kubectl 子进程 env 里没有任何非目标账户的 `AWS_*`。
7. **webhook**：配置令牌后，不带令牌的 webhook 返回 401；6 个解析器在样例数据上都能取到 `observed_at`。
8. **审批与状态写入**：过期哈希审批返回 409；执行器遇到哈希不一致时拒绝执行；HealthIssue 状态写入只在 `transition_issue` 里（grep 测试）。
9. **图展示**：dismissed / resolved 的 Issue 不给节点上色；没有 Issue 的节点显示 `unknown`；UI 上三层爆炸半径的数字与 API 一致。
10. **规则关系行数** = `rule_graph` 中资源到资源的边数；方向测试通过，锁反向的旧测试已删除。
11. **验收原因一致**：`pending_acceptance` 时，IssueDetail 和 ChangeDetail 顶部显示同一条原因。
12. **intake**：签名错误 401、未配置 404、同一工单重复提交得到同一个变更单；`webhook:*` 批准在影子模式下也返回 403。
13. **收尾**：全量测试通过；前端 tsc / vitest / build / locale-parity 通过；和用户一起跑完联合 live E2E，经用户确认后才 `git push --no-verify`。

## 10. 风险与开放问题

1. **锚定率 95% 可能达不到。** 基线只有 111/901 能精确匹配，大量安全发现是账户级或指向未扫描的资源。
   对策是如实报告原因分布，**不为达标放宽规则**。
2. **策略影子模式。** 打开 `policy_graph_impact_enforce` 之后，两条休眠规则会开始升级风险。需要看过 E2E 统计再由用户决定何时打开。
3. **多进程。** 规则写入的串行锁在进程内；多个 uvicorn worker 会各有一把。当前部署是单进程；多 worker 时需要换成 DB 级锁，与 2.6.0 遗留的"迁移跨进程锁"是同一类问题。
4. **K8s 采集规模。** 大集群上 `kubectl get -A` 可能超出字节上限，被判为部分采集。这是安全的方向，代价是缺席判定会延后。
5. **图召回率的前提。** 13 个场景的根因都在 chaos-lab / kube-system 命名空间内，与集群锚点相距 2 跳。
   如果某个场景的告警里带 Namespace 维度，锚点会变成命名空间，距离反而更短，不影响门槛。
6. **评测样本少。** 每组只有 13 个场景 × 1 遍，AC@k 只能作参考，所以不设门槛。
7. **L2 故障脚本是否会发出与声明一致的真实告警**，要在计划 C 里对照 `faults-l2/l2-faults.sh` 逐条确认。
   对不上时，以 ground_truth.yaml 里声明的告警为准，由 harness 直接发送。
