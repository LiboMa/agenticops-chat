## A3. 设计要点

### ① 一份「等谁」规则，两种语言

- 新增 `services/work_phases.py`，逐输入移植前端的 `issuePhases`、`currentFixPlan`、`changePhases`、`inFlightAutoRun`、`notQueuedFrom`。
- 宽限常量 `AUTO_RUN_START_GRACE_SECONDS = 30`，与前端 `AUTO_RUN_START_GRACE_MS` 同值。
- 新增两份共用夹具，pytest 和 vitest 读同一份，两边无法走偏：
  - `tests/fixtures/work_item_phase_cases.json`：输入 → sub / waitingFor / primary。
  - `tests/fixtures/auto_run_cases.json`。
- 输入约定：键缺失 = 未知（列表模式）；`null` = 已知没有。
- `pipeline_service.plan_run_in_flight` 改为调用这里的纯函数，并新增批量版 `runs_in_flight`。
- 修死角（前后端一起改）：
  - `issuePhases` 新增 sub `planRejected`：`fix_planned` 且当前方案已被驳回 → 等你 → 生成方案。`generate-fix-plan` 在这个状态下可用（已核实：只要有 RCA、且没有锁定状态的方案）。
  - 撤回已批准方案（reject-from-approved）时，经 `transition_issue` 把事件从 `fix_approved` 回退到 `root_cause_identified`。这条回退边 2.6.1 已有。

### ② CAS

- `transition_plan` 改为 `UPDATE fix_plans SET status, updated_at WHERE id = ? AND status = <旧值>`；0 行时抛 `PlanStatusConflict`。
  - `PlanStatusConflict` 是 `InvalidStatusTransition` 的子类，现有的 409 映射全部照常生效，包括 `change_service._transition_plan`。
  - 尚未持久化、或不在 session 里的对象，保持原来的直接赋值（单元测试和新建方案走这条路）。
- 所有入口自动受保护：Web 批准 / 驳回 / 执行、CLI、agent 自动批准、变更服务。

### ③ 动作评估无副作用（新增 `services/ui_actions.py`）

- 只调用 `RbacPolicy.decide()`，**绝不调用 `authz.check()`**——后者每次拒绝都写审计行，会抬高 `/api/plans/stats` 的拒绝计数。
- `allowed` = 路由实际会怎么做。影子模式下仅靠宽容放行的动作，照样 `allowed: true`，`reason_code="policy_shadow"`。
- 待办的「该谁做」另用 `strictly_allowed()` 判断。
- 修复方案的动作：
  - approve / reject（draft、pending_approval）；reject 也可用于 approved（撤回）。
  - execute（approved）。顺序与路由一致：执行器关闭 → `executor_disabled`；无权限 → `forbidden`；正在运行 → `run_in_flight`。
- 变更的动作：approve / reject（planned）、execute（approved）。
- 效果（effect）：
  - 修复方案：`auto_fix_enabled and executor_enabled` → `approve_and_queue_execution`，否则 `approve_only`。
  - 变更：`executor_enabled` 且批准人在路由层面被允许 `change.execute` → 排队，否则 `approve_only`。
- `GET /api/fix-plans`（列表和详情）和 `GET /api/changes/{id}` 都带 `available_actions`（契约里的 `UiAction` 形状）。

### ④ 读接口与编辑防过期

- 修复方案列表和详情：
  - 改为普通 `def`（S1 规则），新增 actor 依赖。
  - 每行带来源事件的 `issue_title`、`issue_status`，以及 `target`（`resource_id` / `resource_ref` / `anchor_status` / `resource_type` / `region`）。
  - `status` 接受逗号分隔的多个值（未知值返回 422）；新增 `q`，按编号、标题、资源搜索。
  - 批量查询，不会出现 N+1。
- `PUT /api/fix-plans/{id}`：只要改内容字段，就必须带读取时的 `content_hash`。缺失 → 422，过期 → 409，与批准一致。`status: "rejected"` 这个别名不受影响。

### ⑤ 待办 `GET /api/ui/attention`（`routers/ui.py`，普通 `def`）

- 执行者用 `current_actor`，与写操作同一身份；同时要求已登录（`signed_in_user`）。
- 约 6 个批量查询拼出结果：
  - 候选状态的事件，以及它们的方案、最新 RCA、最新执行；
  - `fix_approved` 事件的执行事件；
  - 候选状态的变更，以及它们的活跃方案。
- 每个工作项一行，行 `id` 形如 `I12` / `C3`。
- 只收两类工作项：`waitingFor ∈ {you, approver, requester, acceptor}` 且有主按钮。

- 谁看得见（严格按 `decide()`）：
  - 批准和验收：要有 `plan.approve` / `change.approve`，SoD 生效，所以申请人看不到自己变更的审批。
  - 「批准后未执行」：要有 `plan.execute` / `change.execute`。
  - 变更草稿和澄清：只给申请人（`requested_by == actor.key`）；申请人不是 `user:` 时，交给管理员。
  - 事件上「等你」的那几步：后端本身没有权限检查（生成方案、重跑 RCA、标记解决、RCA 评价），所以对所有登录用户显示。这记为已知缺口。
- **配置不过滤行**：执行器关闭时行照样保留，但对应动作 `allowed: false`、`reason_code` 为 `executor_disabled`。
- `total` = 全部匹配数；`limit` 默认 25，上限 100；`cursor` = 偏移量。终态的工作项自然不会出现。不调模型，不访问云。
- **契约补充**（写进 RELEASE）：
  - reason 多两个值：`review_required`、`execution_not_started`。
  - 每行多 `ref`（`I#12` / `C#3`）和 `reason_detail` 两个字段。
- bootstrap 的 `features.attention` 改为 true；`revision_guards` 仍为 false（防过期靠 content_hash，不是 If-Match）。
