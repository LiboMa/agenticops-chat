## N1 三种最常用的简报（2026-11-17）

### 做了什么

| 条目 | 改动 |
|---|---|
| 批准（问题的修复方案） | 一页里：为什么（诊断、它引用的证据、模型自己的把握、另一个模型的复核、位置是否核实）、打算怎么做（每一步的说明、命令、代码分的类；回滚）、会碰到谁（关系图的三个数）、做完怎么算成（声明的检查项）。动作：按住 `A` 批准、`R` 退回方案、`D` 忽略，后两个必须写理由 |
| 按住批准 | 按下时记住目标（哪件事、哪份方案、内容哈希），到时只批准还在屏幕上的同一个目标；中途松手、按了别的键、切走窗口、换到另一件事，都不批准。批准带的是你当时看到的内容哈希，方案在你看的时候变了会被服务端拒绝（409），页面说明并重新取 |
| 批准之后会不会执行 | 按钮和开头那句话跟着服务端的 `available_actions` 走：执行器和自动修复都开着才是「按住批准并执行」，否则是「按住批准」，并写明不会自动执行。服务端不放行时按钮不可用，开头那句话写明原因 |
| 验收 | 做了什么（几步、用时、按哪一版方案执行、和批准时是否一致、为什么要人看）、代码已经核对过的检查、要你看一眼的检查。`X` 逐项打勾，全部打完 `A` 才可用；勾过的检查项随验收记入审计。`R` 不通过，要写理由 |
| 确认诊断 | 诊断和三块可信度，加一句为什么没有自动出方案（把握低于门槛 / 被复核否定）。四个选项就是产品现有的四个：`Y` 对、`P` 位置只对了一部分（只有位置能评的时候才有）、`N` 不对、`F` 误报；后两个必须写理由。`M` 让它重新诊断 |
| 证据速览 | 空格打开，`←` `→` 换一条，`Esc` 关。只显示诊断时存下的类型、出处和摘要，并写明原始输出没有保存 |
| 做完一个决定 | 这件事立刻离开队列，下一件接上；它如果以另一种情形回来（批准了但没开始），会重新出现 |
| 后端：`step_tiers` | 方案的响应多一个只读字段：每一步的命令由代码分的类（`write` / `readonly` / `blocked` / `unknown`，没有命令的一步是 `unknown`）。用的是自动批准下限已经在用的那个分类函数；出响应时现算，不存库，不进内容哈希，更新接口不接受它 |

### 和设计稿不一样、照实做的地方

- 没有「要求修改」：`R` 是「退回方案」。方案被标为已退回，这件事以「方案被退回」回到队列。
- 没有 5 秒撤回：决定立即生效。所以批准要按住，说「不」都要写理由。
- 「对」之后不会自动出方案：这件事留在原处，变成「生成方案」那一页（N2）。
- 忽略：理由先作为备注写进时间线（现有接口不保存忽略的理由），并写明检测 agent 会记一条「这件事被人忽略过」。
- 误报、不对：页面写明后果（误报 = 忽略 + 检测 agent 记下这一类；不对 = 这次诊断标为不正确）。实测这两种判断各会写一份 agent 记忆。
- 很长的诊断先显示六行，「展开全文」看全部。

## N2 其余简报、变更单、agent 在做的事（2026-11-17）

到这一阶段，接口可能给出的 16 种组合每一种都有自己的一页（测试 `newuiRegistry` 对着共用清单逐行核对）。

### 做了什么

| 条目 | 改动 |
|---|---|
| 执行失败 | 说清楚是哪一种：某一步失败（第几步、它报了什么）、步骤做完但有检查没通过、还是验收时被人判为不通过（引用那句话）；回滚做了几步、有没有失败。`A` 重新出方案、`M` 重新诊断、`D` 忽略 |
| 批准了没开始 | 为什么没开始（执行器关着 / 没排上）、当初批准的那一版和它的哈希、内容之后变没变。`A` 按住重试；服务端不让执行时按钮不可用并写明原因。`R` 撤回批准（问题）/ 撤销变更单（变更） |
| 方案被退回 | 谁退回的、写了什么、被退回的那一版。`A` 按这条意见重做 |
| 诊断被否 / 没有诊断 | 人的判断（谁、什么时候、写了什么，取自时间线）和被否的诊断。`A` 重新诊断 |
| 诊断已确认 / 过了门槛没人确认 | 诊断和人的判断；后一种写明「自动修复关着，所以没有人去请 agent 出方案」。`A` 生成方案、`M` 重新诊断 |
| 等收尾 | 执行结果和代码核对过的检查；没有留下结论的执行照实说。`A` 标记已解决 |
| 变更：草稿 | 要改什么、谁提的、对上了哪些资源、哪些名字没对上、提的人自己写的步骤。`A` 开始审核、`R` 撤销 |
| 变更：审核要澄清 | 审核提的问题一题一格；后端只收一段话，页面把回答按题号合成一段发出 |
| 变更：待批准 | 要改什么、审核怎么说、实施方案、会碰到谁、检查项。后端要求批准带理由：先写理由，再按住批准；没写理由就按，焦点会跳到理由框。`D` 拒绝 |
| 变更：待验收 | 和问题的验收同一套打勾；`A` 确认完成、`R` 判定失败 |
| agent 在做的事 | 待决右边一栏：现在在做的每一件（做什么、做了多久、是哪件事），超过它自己的超时会标「可能卡住了」；下面是最近做完的几件。数据来自新接口 `GET /api/ui/activity` |
| 交给 agent 之后 | 简报顶上一行「agent 正在诊断 / 出方案（几分钟前开始，由谁发起）」，按钮不可用。这是服务端的记录：刷新、换浏览器、换人看到的都一样 |

### 核对卡片抓到的一个真问题

用只读账户检查时，卡片变红了：「亮着的资源应为 1,654，画出来是 1,928；不见了的应为 274，画出来是 0；环应为 275，画出来是 0」。原因：页面把结果交给画布的时刻比图本身到画布早一步，图到了之后把结果清掉了，画布就把所有资源都画成亮的、一个环都没有。另一个账户看不出来，是因为它的待决列表晚一点到、顺手又交了一次。已经在测试里重现并改掉：结果带着它所属的那张图，只在这张图上画；换图不再清结果。

为了看一眼变红的样子，另外做过一次**故意画错**的构建（视野外的环不画），核对卡片写的是「环应为 275，画出来是 12」；看完立刻用干净的源码重新构建，源码里没有留下任何开关。

### 后端：自动流程请来的出方案 agent 也留记录

N3 里写过：诊断过了门槛、自动修复开着时，流程会自己把这件事交给出方案的 agent——这是默认配置下最常走的一条路——但那几分钟里没有任何记录说它已经开始，状态也不变：现场页什么都没有，经过页只能说「轮到 agent 了，记录里没有它已经开始的迹象」，人这时再点「生成方案」会起第二个 agent。

| 条目 | 改动 |
|---|---|
| 占用 | `services/pipeline_service.trigger_auto_sre` 在起线程前占住这件事（`services/agent_runs.take`，发起者记为 `agent:auto-pipeline`），线程结束时释放，线程没能起来也当场释放。和人请的不同，流程的占用**不会被拒绝**：它直接接过上一步（刚存下诊断、正在收尾的 RCA）手里的占用；上一步随后释放的是它自己的那一个，不会碰到新的 |
| 时间线 | 开始时记 `fix_plan_requested {trigger: auto}`，agent 出错时记同一个事件的 failed |
| 现场 | `GET /api/ui/activity` 里这一条的 `basis` 是 `pipeline`（`requested_by` 为空）。现场页写「诊断过了门槛，自动流程把这件事交给了出方案的 agent，这个进程还在做」；经过页说「agent 在处理」并可以去看现场 |
| 不会重复开始 | 这期间人再请出方案或重新诊断，得到 409 `agent_run_in_flight`（和人请的 agent 在做时一样） |
| 只是记账 | 占用或事件写不进去时，方案照常去写——记录是给看的人的，不能反过来拦住流程。流程原有的判断（自动修复关着、已经有一份没结束的方案）不变，这两种情况不占用、不记事件 |

没有做的：流程自己发起的**诊断**（自动诊断）不占用。它在状态上看得见（诊断中），但人在它进行中再请一次诊断，仍然会起第二个——原来就是这样，列在下面的缺口里。

### 一处行为变化：自动批准的下限更严了

批准简报上每一步的「只读 / 会改动」是代码分的类，自动批准的下限用的是同一个分类。原来它只看一行命令**怎么开头**，所以这些都被当成「只读」：

- `find /var/log -name '*.gz' -mtime +7 -delete`
- `df -h && rm -rf /var/lib/docker/overlay2/*`
- `kubectl get pods -n web -o name | xargs kubectl delete -n web`
- `cat > /etc/nginx/conf.d/limit.conf <<EOF`
- 根本不是命令的一句话：`Find the stale pods and delete them`
- 一条读的命令，后面的注释里写着要再做一件写的事：`aws guardduty get-findings … # If 'False' run: aws guardduty archive-findings …`（副本库里真有这样的步骤）

现在只有**一条命令、一行、不会被 shell 拆开、重定向或做替换、后面不带 `#` 注释、并且照命令本来的写法（小写）写的**才算「只读」（引号里的内容不算拆开：`--query` 里的表达式是数据；`2>/dev/null`、`2>&1` 不改变什么；注释对 shell 没有影响，但它是写给执行的 agent 看的一句话，代码没法给它分类；`Free up disk by deleting old logs`、`Kubectl get pods and delete the stuck ones` 是句子，不是 `free` 和 `kubectl get`）；在主机上还要求这条命令是「不论带什么参数都写不了东西」的那一类（`ls`、`df`、`ps`、`stat` 这样的；`find`、`tee`、`xargs`、`curl`、`journalctl` 不算）。其余看起来像只读的，一律是「分不了类」——要人看。运行时放行主机命令的那张清单（`skills/security.SHELL_READONLY_COMMANDS`）**没有动**，那是另一道闸，改它要主人定；这里只把它的每一项分进「写不了」和「可能写」两组，以后清单里多一项而没分组，测试会失败。

在副本库上量过：166 份方案的 1,755 步（连同回滚步骤）里，**180 步从「只读」改判成「分不了类」**——169 步是因为会被 shell 拆开或重定向（其中 147 步是带 `&&`、`;`、`>`、`<`、`$(` 的 `aws` 命令，有几步在读的后面藏着一个写），11 步是因为带着注释（其中 3 步的注释在叫执行的 agent 接着做一件写的事——归档一条发现、收回一条安全组规则；2 步是别的指示——「每 15 秒重复一次直到在线」「之后另出一份方案」；6 步是「应该返回 1」这样的预期）。**21 份方案因此不再自动批准**，改为等人（被下限拦住的方案从 133 份变成 154 份）。只会让更多的方案等人看，不会反过来。

还留着的一个口子，照实写在这里：全小写、不带任何符号、又恰好以一个只读命令的词开头的句子（比如 `ping the owner before deleting the bucket`）仍会被当成那条只读命令。照字面执行它只会报错，但它毕竟不是一条命令——根本的办法是让执行器只照字面执行 `command`，不去理解它，这要另外做。

## N8 每一次执行都有一条记录；取消是真的（2026-11-18）

只有后端。叫停一次执行（N9）和看到执行的每一步（N10）都要先有这一层。

### 原来是什么样

一次执行有三种起法，只有一种在执行期间留有记录：

| 怎么起的 | 执行期间的记录（`fix_executions` 一行） | 超时、没结果时有人收尾 | 能取消 |
|---|---|---|---|
| 在网页上批准、或自动批准之后，流程起一个线程 | 没有，结束时才写 | 没有 | 不能 |
| 排队：`POST /api/fix-plans/{id}/execute`、CLI `/execute`、所有变更 | 有 | 有 | 只改了记录（见下） |
| 对话里让 Main 调执行器 | 没有 | 没有 | 不能 |

由此有四个口子：

1. **取消不是真的。** `POST /api/fix-executions/{id}/cancel` 把记录改成「已中止」，执行器的线程照样往下跑；之后的写命令只要不在「必须有批准的方案才能跑」的那张清单里，照样会执行。
2. 被取消或超时的**修复**，问题停在 `fix_executing`，时间线上没有一条记录——它不在任何人的队列里。
3. 流程起的执行如果没有存结果就结束了（模型出错、拒绝），方案在 30 分钟（`executor_total_timeout`）内一直读成「执行中」。
4. 批准之后马上撤回，和线程启动抢跑时，只有模型自己去调 `get_approved_fix_plan` 才会被拦下。

### 做了什么

| 条目 | 改动 |
|---|---|
| 开一条记录 | 三种起法都经过 `agents/executor_agent.executor_agent()`。它过了原有的几道闸之后，如果这次运行还没有记录，就自己开一条（`services/run_tickets.open_ticket`）：一个事务里，方案 `approved → executing`、问题 `fix_approved → fix_executing`、插入一行 `running`。和排队那条路在入队时做的事一样，所以下游都认 |
| 开不了就不跑 | 方案不是 `approved`、或者这份方案已经有一条在跑的记录：直接拒绝，不建模型。口子 4 和「同一份方案同时跑两个执行器」都在这里关上 |
| 结果就地关上这条记录 | `save_execution_result` 本来就会把排队那种的记录就地关上；现在三种起法都走这一条，一次执行一行。`executed_by` 是开记录时的发起者，不再是模型自己填的 |
| 没有结果也收尾 | `executor_agent()` 返回时，自己开的记录如果还是 `running`，按「执行器没有留下结果就结束了」关掉。自己开的记录也有 `executor_total_timeout` 的看门狗（原来只有排队的有） |
| 关记录只有一个出口 | `services/run_tickets.close_ticket`（原来是 `ExecutorService` 的私有方法）。取消、超时、崩溃、收尾都走它，谁先关谁算数。对修复，它现在把问题 `fix_executing → root_cause_identified`，并在时间线记一条 `execution_completed failed`——这件事以「执行失败」回到某个人的队列里。**不把诊断判成「有争议」**：取消和超时说明不了诊断对不对 |
| 记录一关，执行器就停 | 新的钩子 `agents/run_guard.RunGuard`（Strands `BeforeToolCallEvent` / `BeforeModelCallEvent`）。执行器每次调工具之前读一次这条记录：不是 `running` → 这次工具调用取消（命令根本不会跑），下一次调模型也取消，循环结束。已经在跑的那一条命令会跑完——它停不了。读不到记录时放行并记日志：这个钩子是用来停一次已经关掉的运行的，不能反过来拦住一次正常的 |
| 一条一条跑 | 执行器用 `SequentialToolExecutor`。SDK 默认把模型一轮里写的几条命令并发跑；方案的步骤是有先后的 |
| 删除方案 | `DELETE /api/fix-plans/{id}`：执行中的方案 409；跑过的方案 409（它的执行记录指着它；原来这种情况回的是 500） |
| 运行时打开执行器 | `PATCH /api/settings` 把 `executor_enabled` 从关改成开时，启动排队的轮询。原来只改了开关，之后入队的执行要等到下次重启 |
| 变更的时间线 | 一次变更的执行只记一条 `execution_completed`（原来 `save_execution_result` 和变更的状态映射各记一条） |

### 行为上的变化

- 流程起的执行**在进行中**：方案是 `executing`、问题是 `fix_executing`（原来直到结束都是 `approved` / `fix_approved`）。旧界面的问题页、列表这时显示「执行中」；新界面的现场上有这一条。
- 被取消、超时、或者没留下结果就结束的修复：问题回到 `root_cause_identified`，以「执行失败」出现在「在等我」里（原来停在 `fix_executing`）。
- 让执行器跑一份不存在的、或者不是 `approved` 的方案：在代码里被拒绝（原来要等模型自己去读方案才发现）。
- 取消之后：执行器在当前这一条命令做完后停下。

### 六个面

| 面 | N8 |
|---|---|
| CLI | 非目标，没有新命令。CLI 的 `/execute` 入队的执行同样受 `RunGuard` 看着（它查的是数据库，另一个进程关掉的记录也算） |
| Web API | 做：`DELETE /api/fix-plans/{id}` 多两种 409；`POST /api/fix-executions/{id}/cancel` 的接口不变，效果变成真的；`PATCH /api/settings` 打开执行器时启动轮询 |
| Web UI | 非目标（没有改页面）。两个界面读到的状态变了，见上面「行为上的变化」 |
| Agent 工具 | 做：`executor_agent` 自己开、自己收尾运行记录；构建时加 `RunGuard` 和顺序执行。没有新工具 |
| 定时任务 | 非目标 |
| 通知 | 非目标（关记录时不发新的通知；变更的通知照旧由状态映射发） |

## N9 叫停一次执行并回滚（2026-11-18）

设计稿里现场的「按住叫停并回滚」。N8 让每次执行都有一条记录、记录一关执行器就停；N9 在这条记录上加一个「有人叫停了」，并规定叫停之后还能跑什么。

### 后端

| 条目 | 改动 |
|---|---|
| 叫停的请求 | `POST /api/fix-executions/{id}/stop`（`{reason?}`，普通 `def`）。先 404，再查权限（修复 `plan.execute`、变更 `change.execute`——和取消、重试执行同一个权限；拿着 API key 的请求被拒绝，这是人的决定），再 409：`not_running`（这次执行不在进行中）、`already_stopping`（已经有人叫停了）。写在运行记录的三个新列上：`stop_requested_at / stop_requested_by / stop_note`，比较并设置——两个人同时叫停只有一个成功。时间线一条 `execution_stop_requested`，审计一条 `plan.execution_stop_requested` |
| 叫停不关记录 | 记录仍然是 `running`。关了它，结果就存不进去，回滚也跑不了（N8：记录一关，执行器的每一步都被拒绝）。所以叫停和取消是两件事：取消 = 到此为止，什么都不再做；叫停 = 停下来，把做了的撤回 |
| 叫停之后还能跑什么 | 由代码判断，不靠模型自觉。`RunGuard` 在执行器每次调工具之前读记录；有叫停时只放行三样：只读命令（评审之后那条更严的规则：一条不会被 shell 拆开、不带注释、照原样写的只读命令）、读和记录结果的工具、**和这份方案 `rollback_plan` 里某一步的命令逐字相同的命令**（只把连续的空白折成一个）。别的调用一律取消——命令根本不会跑——取消的回话告诉模型：有人叫停了，只用这份方案的回滚步骤把已经做了的撤回，然后记下结果 |
| 回滚没有写成命令的方案 | 回滚只是一段话：没有哪条命令能被放行（只读除外）。结果里不会有回滚的记录，页面照实说 |
| 结果和去向 | 存结果时记录上有叫停、而这次执行没有成功：原因里写明是谁叫停的；**不把诊断判成「有争议」**——是人叫停的，说明不了诊断对不对。修复回到 `root_cause_identified`，以 `execution_failed` 加新的细分 `run_stopped` 回到「在等我」（前后端共用的简报清单 16 → 17 行，还是「执行失败」那一页）。变更按原有的规则结束（`rolled_back` / `failed`），不回到待决 |
| 叫停之后没留下结果 | 执行器没有记结果就结束了：收尾时关记录，原因写明「被 … 叫停；执行器没有留下结果——没有回滚的记录」 |
| 现场的数据 | `GET /api/ui/activity` 里执行的那一条带上它的运行记录 `execution {id, status, stop_requested_at, stop_requested_by}`（修复和变更都带）；执行记录的接口（`FixExecutionResponse`）多三个字段 |

### 前端（新界面）

- **现场**：一条正在进行的执行（有运行记录、记录是 `running`、还没有人叫停）下面是红色的「按住叫停并回滚」，键 `A`。和批准是同一套按住的规则：按满 900 毫秒才发出；只认按下时页面上的那一条运行记录——换到另一条、同一件事起了新的一次执行、窗口失去焦点、按了别的键，都作废。只读账户不显示。按钮上面有一句话，说叫停之后会怎样。
- **叫停之后**：这一条的边变红，状态写「执行 · 已叫停」；页面写明谁、什么时候叫停的，并说「回滚做了没有，以它结束时记下的结果为准」。按钮收起（不能叫停第二次）。
- **被拒绝**：`not_running` →「这次执行已经结束了，没有可叫停的」；`already_stopping` →「已经有人叫停了这次执行」；别的原因照实显示服务端的话。人已经换到别的一条时，在底部的提示里说——失败一定说出来。
- **待决**：被叫停的执行回来时还是「执行失败」那一页，换了说法。问句：「{谁}叫停了这次执行。决定下一步：让 agent 重新出方案，还是重新诊断。」「停在哪一步」：谁、什么时候、叫停之前有几步报告做完。「现在是什么状态」按回滚的记录说：做了几步、其中几步失败；没有回滚记录时分三种——「叫停之前报告做完的 N 步，改动还在」「叫停之前也没有哪一步报告做完」「执行器没有留下每一步的结果，所以叫停之前做了什么，这里不知道」。
- **经过页、验收页、等收尾页**：执行记录里多一行「{谁}在 {时间} 叫停了这次执行」。如果这次执行仍然记成了成功，那一行是红的：「叫停过；这次执行仍然记成了成功」。
- **旧界面**：页面不改。「在等我」里多一种细分 `run_stopped`：「执行被人叫停了，需要新方案」。

### 和设计稿不一样、照实做的地方

- **只有一个状态「已叫停」。** 设计稿分「这一步做完就停」和「正在回滚」。运行记录上只有「叫停了」这一个事实，回滚开始了没有，N9 分不出来。N10 记下每一步之后，回滚的命令会一条一条出现在现场上。
- **不说「已经回滚」。** 代码能保证的是：叫停之后**只有**这份方案的回滚命令和只读命令跑得了。回滚**有没有做**，取决于执行器照不照做，以它记下的回滚结果为准。所以页面说的是回滚的记录，而不是「已经回滚」。
- **「来不及了」只说事实。** 设计稿：「最后一步已经在做，照常做完了」。页面不知道叫停的那一刻在做哪一步，只说「叫停过；这次执行仍然记成了成功」。
- **「这一步」是一条命令。** 停不下来的是执行器正在跑的那一条命令（一次工具调用）；代码看得到命令，看不到「方案的第 N 步」。
- **不用写理由。** 按住就叫停（接口接受 `reason`，写了会显示在记录里）。

### 没有在真实的执行上看过

预览实例的执行器全程关着（它的账户是真实的云账户）。叫停之后放行什么、拒绝什么，是用**真的** `strands.Agent` 加一个按脚本回答的模型测的：第一条命令执行期间叫停，同一轮里的第二条没有跑，随后回滚命令放行、别的命令被拒绝、结果记成 `rolled_back`。页面上的各个状态是在浏览器里把服务端的回答换掉来看的。要看一次真的，需要主人点名一个账户。

| CLI | 非目标：没有 `/stop` 命令。CLI 的 `/execute` 起的执行可以在网页上叫停（`RunGuard` 查的是数据库，另一个进程写的叫停也算） |

## N10 现场的每一步（2026-11-18）

第一轮的现场页只能说「有一个 agent 在做」：诊断看了什么、执行跑到哪一条命令，要等它做完才知道——诊断和出方案则永远不知道。N10 让代码在 agent 做的时候把每一步记下来。

### 后端

| 条目 | 改动 |
|---|---|
| 记录 | 新表 `agent_steps`，一行一步。新的钩子 `agents/step_recorder.StepRecorder`（Strands `BeforeToolCallEvent` / `AfterToolCallEvent` / `MessageAddedEvent`）：工具调用**开始时**插一行，结束时补上结束时间和结果；模型在两次调用之间说的话各记一行（前 300 字） |
| 一行有什么 | 哪一次运行（`run_key`）、哪个 agent、属于哪件事（`I12` / `C3`）、执行的运行记录号；工具名、输入的一行摘要、结果的前 200 字；开始、结束；结果 `ok` / `error` / `refused`（被钩子取消——命令没有跑）。摘要和结果都先过显示用的脱敏（`chat/tool_steps`，和对话的工作记录同一套） |
| 是事实还是动作 | `look`：`read` = 代码取到的事实（名字是 `get_` / `describe_` / `list_` / `search_` 这类只读的工具，或命令的分类是只读）；`act` = agent 做的动作（其余的：改东西、记结果）。带命令的调用按命令判断，用的是方案页上每一步旁边的那个分类 |
| 和方案对上 | 执行器的每条命令和它的方案逐字比（只把连续的空白折成一个）：`step:3`、`rollback:1`、`pre:1`、`post:2`；不是只读、又哪一条都对不上的标 `off` |
| 挂在哪 | 诊断（`rca_agent`）、出方案（`sre_agent`）、审核变更（`sre_agent_review_change`）、执行（`executor_agent`，排在 `RunGuard` 之后——被拒绝的调用也记下来，记成 `refused`）。对话里的临时查询（`sre_query`）不记：它不属于哪件事 |
| 不能拖累 agent | 每一次写都包着：写不进去只记一条调试日志，agent 照常往下做（测试里把数据库换成一律报错，运行照常结束） |
| 读密钥的命令 | 这张表每个登录的账户都能读，只读账户也能。只读账户自己的 kubectl 被拒绝读 Secret 和原始 kubeconfig（`skills/execution._reveals_secret_material`）；同一条规则下，这类命令的结果不留在记录里（留下的是命令本身和「没有保留」） |
| 取 | `GET /api/ui/activity/steps?item=I12&agent=rca|sre|executor`，再加一个说明「哪一次」的参数：`execution`（运行记录号）、`since`（在进行的那一条开始的时刻——比它早开始的那一次不算）、`before`（留下某个结果的那一次）；`after` = 页面已有的最后一步。任何登录的账户；普通 `def` |
| 保留多久 | 新设置 `agent_steps_retention_days`（默认 30，写在 `config/settings.yaml`；0 = 一直留着）。每个进程每天清一次，在新的一次运行开始时触发，每个事务最多删 500 行 |
| 回滚能做多少 | 方案的回答多一个 `rollback_outlook {steps, commands, as_written}`：回滚有几步、几步带命令、其中几条是「能原样执行的一条命令」（不是一行里连着几条，不带占位符、管道、替换、注释）。和 `step_tiers` 一样是读的时候算的，不存、不进内容哈希、更新接口不收 |

### 前端（新界面）

- **现场**：打开一条正在做的（诊断、出方案、审核、执行），下面是「一步一步的记录」，每 3 秒只取页面还没有的部分。每一行前面的记号：◆ 代码取到的事实、▸ agent 做的动作、◇ 模型自己的话；正在做的那一步在闪，失败的是红点，被拒绝的画了删除线并写着为什么。页面跟着最新的一步往下走，人往上翻去读就不再跟。
- **执行**：方案的每一步旁边有记号——做完、正在做、失败、被拒绝——来自记录里和这一步的命令**逐字相同**的那一条。记录上面有一句：「其中会改动的命令 N 条，M 条和方案里的命令逐字相同」；对不上的那几条各带一个标签「不是方案里的原文」。
- **叫停之前**：方案下面一句话说这份方案的回滚能做多少——「可以原样执行 N 条回滚命令」「另外 M 条原样执行不了，改写后会被拒绝」「回滚没有写成命令：叫停之后不会有自动回滚」。
- **做完的**：最近一天做完的诊断和方案，打开后在结果下面有「它是怎么做的：一步一步的记录」。经过页、验收页、执行失败页的每一次执行下面多一个可以展开的「代码记下的每一步」——和执行器自己报告的每一步并排，可以对着看。
- 原来现场上那几句「后端不记录它的每一步」去掉了。在开始记录之前就做完的运行，写的是「这一次没有逐步的记录」。

### 量出来的两件事（副本库，只读）

**执行器跑的命令，大多不是方案里的原文。** 副本库的历史里，在某份方案之下跑过的、会改动的命令一共 214 次（17 份方案）：

| 和方案里的命令比 | 次数 |
|---|---|
| 逐字相同 | 21 |
| 是方案里连着写的一行中的一条 | 3 |
| 很像（八成以上相同：换了参数、编号、引号） | 90 |
| 一半像 | 32 |
| 和方案里任何一条都不像 | 68 |

批准绑定的是方案的内容；执行器照着方案自己写命令。这不是 N10 造成的，也不是 N10 能解决的——N10 做的是把它摆出来：每一次执行写着有几条命令是原文、哪几条不是。要不要把「只许跑方案里的原文」变成规则，是要主人定的事（现在的方案大多是写给 agent 看的指引，不是能原样跑的脚本，直接收紧会让大多数执行跑不下去）。

**叫停之后的回滚，多数方案做不了。** 叫停之后只放行方案自己的回滚原文（N9）。副本库的 166 份方案里：99 份的回滚一行都没有；67 份有，一共 270 行。这 270 行里，是「代码认得出、能原样执行的一条命令」的只有 **33 行**；154 行是一行里连着几条、带着管道或替换、注释，或者带着 `<…>` 这样的占位符；6 行的占位符藏在引号里（`'…CidrIp=<OWNER_APPROVED_IP>/32…'`）；另外 77 行根本不是命令——是一句话（「Start instance and verify status checks」），或者命令前面带着一句说明（「Re-enable key: aws iam update-access-key …」）。这 67 份里，每一行回滚都能原样执行的 **5 份**，一部分能的 **10 份**，一行都不能的 **52 份**。所以现在的「叫停并回滚」，166 份方案里有 151 份只有叫停。页面在叫停**之前**就照实说这份方案能回滚多少。要让它名副其实，得让出方案的 agent 把回滚写成一条一条能原样执行的命令——N14 用一次真的重做量过：审核的人写一句话就够了（见 N14 一节），要不要写进它的提示词，列在「之后」里。

> **N14 的更正。** N10 提交时这一段写的是「116 条能原样执行；8 份全部能、49 份一部分能、10 份都不能」。那个数多算了：当时的规则只看「shell 会不会把这一行拆开」，一句不带符号的话、引号里带着占位符的命令也算「能原样执行的命令」。N14 用真数据核对时发现，改成「shell 不会拆开，**并且**不带占位符，**并且**代码认得出它是一条可以执行的命令（只读或者会改动；被禁止的不算）」。页面在叫停之前说的那句话（「可以原样执行这份方案的 N 条回滚命令」）在大约 50 份方案上说多了，现在不会了。

### 和设计稿不一样、照实做的地方

- **一步写的是「它跑了什么」，不是一句人话。** 设计稿每一步有一句人话（「05:52 UTC 有一次发布」）。真的记录里没有这句话——那是模型没有说出来的东西。页面每一步先写它调的工具和输入，下面是返回的开头（前 200 字，最多显示两行）；模型自己说的话单独成行，标 ◇。在真的那一次诊断里，模型在工具调用之间没有说话，只有最后的结论是一行 ◇。
- **「后面还有 N 步」没有。** 代码不知道 agent 接下来要做什么。
- **「正在回滚」仍然不是一个状态**（N9 说过 N10 会补）：现在能看到的是回滚的命令一条一条出现在记录里，标着「回滚第 N 步」；这一条的状态仍然是「已叫停」。

## N11 诊断没有结果的事回到人手里；每一种起法都占用这件事（2026-11-18）

第一轮留下的两个缺口（下面「已知的缺口」原来的第 1、2 条），这一阶段补上。

### 原来是什么样

- 一件问题的诊断失败、超时，或者结束了却没有留下结果：状态留在「诊断中」（或「新发现」），而「谁在等」的规则对这几个状态一律回答「在等 RCA agent」。没有 agent 在做它，它也不在任何人的「在等我」里。
- 只有人在页面上请的诊断和出方案占用这件事（同一件事同时只有一个 agent）。流程自己发起的诊断、对话里让 Main 去诊断或出方案，都不占用——这期间人再请一次，会起第二个。
- 占用过了 15 分钟（诊断的时限）就当作没有：线程可能还活着，第二个 agent 一声不响地起来了。

在副本库上量了一下（只读）：还在等诊断的问题 784 件。781 件从来没有诊断过；1 件的诊断结束了、没有结果；**1 件的诊断开始了、再也没有结束——它「诊断中」已经 79 天**（跑它的那个进程早就不在了）；还有 1 件是诊断过、出过方案、被忽略之后又重新打开的，它回到了「新发现」。

### 做了什么

| 条目 | 改动 |
|---|---|
| 规则 | 一件问题还在等诊断（`open` / `investigating` / `acknowledged`），而它最新的一次诊断**不会再有结果了**：要么已经结束（失败、超时，或者结束了状态没动——存下诊断会先挪状态，所以留在这里的结束都是没结果的），要么开始之后再没有结束、并且早就过了时限。这时没有在时限之内的 agent 占着它 → 它在等人，主要动作是「重新诊断」。那次诊断之后状态又动过的不算（比如被忽略之后重新打开的问题：它以前的诊断不是它现在停在这里的原因）。`services/work_phases.rca_stopped_at` 一个函数，待决队列、问题列表、问题页、现场页都用它 |
| 从来没诊断过的、重新打开的 | **不动**。那 781 件从来没诊断过的 `open` 问题，和被忽略后重新打开的问题，仍然是「在等 RCA agent」——它们要不要等人，是要主人另外定的事 |
| 队列 | 多一行 `review_required` / `rca_stopped`（前后端共用的清单 17 → 18 行）。新界面用「重新诊断」那一页，换了话：「上一次诊断没有留下结果——它失败了、超过了时限，或者开始之后再没有结束。从 … 起它就停在这里」；如果那一次是在 N10 之后跑的，下面是它做到了哪一步。「等了多久」从它停下的那一刻算起 |
| 问题的回答 | `GET /api/health-issues`、`GET /api/health-issues/{id}` 多一个 `rca_stopped`；`waiting_on` 这时是 `you`。旧界面的问题页、问题列表、「在等我」跟着变：状态「诊断没有结果」，主按钮「重新运行 RCA」 |
| 自动诊断占用 | `rca_service` 开始前占用这件事，结束时释放；已经有 agent 在做（并且在时限之内）就**让开**，不起第二个，也不在时间线上写「开始」。超时之后占用不随看门狗释放，而是等诊断的线程自己结束——它停不掉，可能还在跑 |
| 对话里起的也占用 | `rca_agent` / `sre_agent` 开始时：调用它的线程已经占着这件事（页面上请的、流程请的——占用放在 Run Context 里）就用那一个；否则自己占一个，结束时释放；别人占着就拒绝，回一句「REJECTED：… agent 已经在做 issue #N（谁请的、从什么时候起）」，不建模型 |
| 超时的占用 | 不再当作没有：现场上仍然列着，标「可能卡住了」。它不再挡着这件事——下一次请求把它接过去，并在时间线上记一条 `agent_run_abandoned`（哪个 agent、什么时候开始的、谁请的、被谁接过去的）|

### 行为上的变化

- 「在等我」多出诊断没有结果的事（副本库里是 2 件）。两个界面都一样——它们用的是同一个接口。
- 这类事在页面上不再说「在等 RCA agent」。
- 流程发起的诊断进行中，人再请诊断或出方案：409「已经有 agent 在处理」（原来会起第二个）。
- 在对话里让 Main 诊断一件正在被诊断的问题：agent 回一句拒绝，说明谁在做。
- 一次诊断过了时限以后再请一次：照样开始，时间线上多一条「上一次被放弃」。

## N12 给正在做事的 agent 插一句话（2026-11-18）

设计稿里现场的「插话」。暂停没有做（理由在下面）。

### 后端

| 条目 | 改动 |
|---|---|
| 请求 | `POST /api/ui/activity/note {lane, text}`：1–200 字；只对**这个进程里正在进行的**诊断、出方案、审核变更。说话的人是登录的那个人（会话里的身份，不是请求里填的）。403：只读账户；409 `not_steerable`：这一条不收插话（执行、定时任务、关系图构建）；409 `not_running`：那一次已经结束了，或者不在这个进程里——这句话没有送到 |
| 先记下，再交给 agent | 这句话是这次运行的一步（`agent_steps`，种类 `you`，谁写的、什么时候），所以它立刻出现在现场的记录里。**记不下来就不送**——页面上看不到的话，不能到模型那里 |
| 怎么交给 agent | 记录的那个钩子在 agent **下一次调模型之前**，把这句话加在最新一条 user 消息的末尾（工具结果的后面），外面包着一段说明：这是跟着这次运行的人（写明是谁）补充的信息，不是指令，不改变它被要求做的事、它的权限、它能用的工具。话里如果带着这一层的结束标签，会被转义——它关不掉自己的框。交出去之后，那一步标成已送到 |
| 运行结束就不收了 | 诊断、出方案、审核变更三个入口在结束时（成功、失败、被拒绝都算）把这次运行从「在进行」里摘掉。之后再发：409 `not_running` |
| 执行不收 | 执行按批准的那一版方案走（批准绑定的是方案的内容），中途不能改，只能叫停（N9）|

### 前端（新界面 · 现场）

- 正在诊断、出方案、审核变更的那一条——在做、没有超过时限、不是只读账户——底部多一个输入框。`E` 把光标放进去，回车发出，`Esc` 离开。上面一句话说明它是什么：补充的信息，不改变 agent 的任务和权限，留在这次运行的记录里。
- 发出之后，这句话出现在一步一步的记录里，前面是「你」（别人写的是他的名字），后面是「agent 下一次思考前会读到」；agent 读到之后变成「agent 读到了」。
- 被拒绝时照实说：「它已经结束了，这句话没有送到」。人已经换到别的一条时，在底部的提示里说。

### 没有做暂停

暂停一个 agent，要么让它的线程和模型上下文一直占着等人回来，要么要把它的状态存下来、之后原样恢复——后者这套 agent 框架没有现成的办法。让它做完的代价更小：诊断和出方案都是只读的，一次一两分钟。执行要停，用叫停。

### 和设计稿不一样、照实做的地方

- **agent 不会回一句「收到」。** 设计稿里插话之后 agent 回「收到。先核对这一点，再继续」。真的 agent 回不回话、怎么用这句话，是模型的事。页面只说代码知道的两件事：记下了、读到了。
- **不说「它会先做这件事」。** 这句话是给它的信息，不是给它的指令——说明里就是这么告诉它的。

### 六个面

| 面 | N12 |
|---|---|
| CLI | 非目标：没有对应的命令（命令行里的对话本身就能接着说）|
| Web API | 做：`POST /api/ui/activity/note` |
| Web UI | 做：新界面的现场（输入框、`E`、记录里的「你」）。旧界面：非目标 |
| Agent 工具 | 做：rca / sre 的记录钩子多一件事（下一次调模型前交出这句话）。没有新工具；agent 不能给别的 agent 插话 |
| 定时任务 | 非目标 |
| 通知 | 非目标 |

## N13 撤回：每个决定 5 秒后才发出（2026-11-18）

设计稿里的「撤回」。只有前端：后端没有改。

### 做了什么

- 新界面里的每一个决定——批准、退回方案、忽略、验收通过 / 不通过、标记已解决、重试执行、撤回批准；变更的开始审核、回答澄清、批准、拒绝、撤销、标记完成 / 判为失败；对诊断的判断；请 agent 重新诊断 / 出方案——都走同一个出口：**立刻显示，5 秒后才把请求发出去**。
- 这 5 秒里，底部是一行「{哪件事}：{做了什么}——5 秒后生效」和一条在缩短的线，右边是「撤回」，键 `Z`。撤回 = 这个请求**根本没有发过**，服务端什么都没有发生；页面回到那件事上，提示「已撤回，什么都没有发生」。
- 待决队列里的决定：那件事立刻离开列表，页面换到下一件。别的两种（对诊断的判断、请 agent 做事）那件事不离开，简报在这 5 秒里是「正在处理」的样子。
- 只有最后一个能撤回：做下一个决定，上一个就立刻发出。
- 5 秒到了才发的请求如果被服务端拒绝（比如方案在这期间变了）：那件事回到列表里，底部提示写明是哪件事、为什么没有成功。**不把人拉回去**——他可能正在看别的事、正在写理由。（批准被拒绝时原来说的是「这一页已经重新取过」；现在人已经不在那一页上，改成「它回到了列表里，内容重新取过了」。）
- 这 5 秒里在新界面里去别处（现场、全景、另一件事的经过）：那个决定接着等，底部那一行跟着走；在哪里按 `Z`，页面都回到被撤回的那件事上。
- 关掉页面、刷新、回到旧版：还在等的那个决定这时立刻发出（人已经做了决定）。关页面和刷新时发出的请求带着 keep-alive，浏览器会让它发完。
- 文字照实写：是「5 秒后生效」，不是「已批准」——这 5 秒里服务端还什么都不知道。
- 系统开着「减少动态效果」时，那条缩短的线照样走：它是剩下的时间，不是装饰。手机上「撤回」是提示条右端一整块（56 × 44），因为手机没有 `Z` 键。

### 不在这个窗口里的

- **叫停一次执行**（现场上按住 `A`）：按住到底就立刻发出。叫停不能再等 5 秒。
- 经过页上写备注、重新打开一件被忽略的问题；现场上给 agent 插话。

### 和设计稿不一样、照实做的地方

- 设计稿在这 5 秒里写的是「已批准 I#12，5 秒后开始执行」。这时什么都还没有批准，所以写的是「批准——5 秒后生效」；真的批准之后，提示才换成服务端回答的那一句（「已批准。它不会自动执行」或「已批准，执行已经排队」）。
- 设计稿的现场上有「还可以撤回」的状态。没有做：这 5 秒里服务端没有这件事，现场页列的是服务端的记录。

### 六个面

| 面 | N13 |
|---|---|
| CLI | 非目标 |
| Web API | 非目标（没有改）。同一个决定的请求比原来晚 5 秒到 |
| Web UI | 做：新界面的待决（每一种决定）、外壳（提示条、`Z`、离开页面时发出）。旧界面：非目标，照旧立刻发出 |
| Agent 工具 | 非目标 |
| 定时任务 | 非目标 |
| 通知 | 非目标 |

### 测试

- `newuiPending`（12）：用一只测试自己拨的钟。5 秒到了才发、之前不发；撤回之后永远不发；发出之后不能撤回；新的决定让上一个立刻发出、只有最后一个能撤回；页面要走时立刻发出；等的东西每变一次都通知画提示条的人；一个发的时候抛错的决定不挡住下一个。队列里的决定：立刻藏起来、5 秒后才请求；撤回——放回去并回到那件事上、从不请求；服务端拒绝——放回去（不把人拉回去）并说出来；还没发出去就抛错也算失败。
- 前端 `tsc` 0 个错误，`vitest` 113 个文件、1,275 个通过。浏览器里的检查（包括副本库上一次真的批准：按住之后 2 秒刷新页面，服务端收到了）见 [E2E 报告](MVP-2.9.0-E2E-REPORT.md#第二轮n8n15)。

## N14 要求修改、和上一份方案的差别、稍后（2026-11-18）

设计稿里的三个控件：批准页的 `R`「要求修改」、新方案回来时的「和上一版的差别」、`S`「稍后」。做的过程中用三次真的重做核对，量出两件事不对，一并改了。

### 要求修改

- **一步，两件事都做或者都不做。** 批准页按 `R`，写一句要改什么，回车：`POST /api/fix-plans/{id}/request-changes {reason}`。服务端在同一个事务里把方案退回（记下是谁、什么时候、这句话），并替出方案的 agent 占住这件事、把它请出来。有一样做不成（没有权限、方案已经不在等批准、这件事已经关了、已经有 agent 在处理这件事），另一样也不发生——不会出现「方案退回了，却没有人重做」或者「旧方案还在等批准，agent 已经在旁边写新的」。
- 原来是两步：先「退回方案」，这件事再以「方案被退回」回到队列里，再按一次「按这条意见重做」。两步的做法还在（旧界面的拒绝、接口都没有变），新界面的批准页只留下这一步。
- 权限和一次拒绝相同（`plan.reject`）：只读账户不能，经 API Key 不能（这是人的决定），职责分离的规则照旧。和其他决定一样等 5 秒才发出，`Z` 能撤回。
- 方案的回答里多一个可用动作 `request_changes`（和 `approve`、`reject` 并列），页面按它决定显不显示 `R`。
- 时间线上这一条写的是「退回了方案 #N，并请 agent 按意见重做」（原来只有「已请 agent 出修复方案」，看不出它前面退回过方案）。新界面的经过页和旧界面的问题页都这样写。

### 被退回的方案原样交给 agent（做的过程中量出来的）

第一轮就做了「agent 会读到退回的理由」。这次用真的模型走了三次，发现只给理由不够：

| 第几次 | 审核的人写的话 | 回来的方案 |
|---|---|---|
| 1 | 每一步只写一条能原样执行的命令；回滚也写成不带占位符的单条命令 | 照做了。步骤的分类从「分不了类、会改动、只读、分不了类」变成「只读、只读、会改动、只读、只读」；回滚从 2 行里 0 行能原样执行，变成 3 行里 3 行都能 |
| 2 | 在第 1 步前面加一步只读命令；其余步骤和回滚都不要改 | **没有照做。** 步骤改了 3 步、删了 1 步、加了 1 步，回滚 3 步全部重写——上一次改好的又丢了（回滚又是 3 行里 0 行能原样执行） |
| 3 | 和第 2 次同样的要求（改了下面这一条之后） | 照做了。步骤只改了 1 步，其余 4 步一字未动；回滚 3 步一字未动 |

第 2 次的原因：agent 收到的只有那句话，**没有那份方案**。「第 1 步」「其余不要改」对它来说没有所指，它每次都是从头写一份。它结束时自己说了出来：「I had no tool to read the v1 plan, so I may not have left steps 1–4 and the rollback unchanged as you asked」。

改法：退回的理由后面，把被退回的那份方案（步骤、回滚、检查、风险等级）作为数据一并交给它，写明「按理由要求的改；理由没有要求改的部分保持原样，除非那部分是错的——那样的话在摘要里说明另外改了什么、为什么」。和理由一样放在定界的块里，块的结束标记被转义；超过 8,000 个字符的方案截断并写明截断了。只在「人写了理由」的时候才给（代码撤下的方案、别的诊断的方案都不给——和理由的规则相同）。

三次都是同一件事、同一份诊断；n = 1，不是统计结论。它说明的是：没有那份方案，「要求修改」做不到它名字说的事。

### 和上一份方案的差别

- 批准页在「为什么」和方案之间多一节「和上一份方案（#N）的差别」——只在这件事有过上一份方案时出现。
- **先说上一份方案怎么了**：人退回的，引用那句话，署名和时间；代码撤下的（比如批准之后内容变了），写明是代码撤下的、理由是代码写的，不放在人的名下；执行失败了、执行过了，各有一句。两份方案出自不同的诊断时说明。
- **再说差别**，步骤和回滚各一行数字：「步骤：改了 3 步，新加 1 步，1 步没有变」。改动不多于 4 处时逐条展开——新加的、删掉的、改了的（现在的写法和原来的写法，原来的划掉）；多于 4 处时先折起来，点开再看（一份从头改到尾的方案，要读的是方案本身，不是差别）。
- **按「要执行的内容」比**：有命令的步骤比命令，没有命令的步骤比它的文字。只改了说明、命令没变的步骤算没变——页面上写着这条规则。
- **「没有改动的行」不等于「没有改」**，分开说：两份方案的内容指纹相同 →「这一份和上一份一字不差」（琥珀色，这通常说明 agent 没有理会意见）；命令都没变但指纹不同 →「要执行的命令都没有变；别的内容有改动（说明、检查或风险等级）」；两边都没有分成步骤的回滚 →「比不了」，不说「没变」。风险等级变了单独写一行。
- 不需要新存任何东西：方案被退回后重做是新的一行，被退回的那一行内容还在。所以说的是「和上一份方案（#N）」，不是「v2 → v3」——版本号在新的一行上从 1 重新算。
- 接口：`GET /api/fix-plans/{id}/previous-diff`。「上一份」= 同一件事上编号更小的最新一份修复方案，不管它后来怎么了。变更单的方案没有上一份（它属于变更单）。

### agent 在做的事，不留在人的队列里

- 设计稿：「一个决定之后轮到 agent 做事：这件事离开队列，出现在 agent 在做的事里；做完了再回来。」第一轮没有做到——请 agent 重新诊断、出方案之后，这件事还留在队列里，简报上多一行「agent 正在处理」，按钮灰着，顶上的数字也不减。
- 要求修改让这一点很显眼：刚按完「要求修改」，同一件事立刻以「方案被退回」又出现在队列里，而这时人没有任何事可做。
- 现在的规则（一处，所有地方都读它）：**一件问题上有 agent 正在做事、而且没有超过时限 → 它在等这个 agent，不在等人。** 不出现在「在等我」里（新旧界面都是），不计数；问题列表和问题页的「在等谁」写的是这个 agent。agent 做完（或者超过时限），按它留下的状态重新判断：有了新方案就是「等你批准」，没有就回到原来那一行。N11 对「诊断没有结果」这一种做了同样的事，现在对每一种都一样。
- 它在 agent 手里的时候打开它的地址：「{这件事} 现在在 agent 手里」和一个去现场的按钮（N11 做的页面）。
- 没有改的：旧版问题页自己那条状态栏。它是页面按问题的状态算的，不知道有没有 agent 在做事，这几分钟里仍然写「等你」；同一页上服务端给的「在等谁」写的是 agent。列在已知的缺口里。

### 稍后

- 待决页按 `S`（或者简报第一行的「稍后」）：这件事排到**同一严重度**的最后，页面换到原来排在它后面的那一件。`POST /api/ui/attention/snooze {item}`。再按一次 `S`（这时写的是「取消稍后」）回到原位，`DELETE`。
- 它不改这件事本身：仍然在等你，仍然计数，别人看到的顺序不变。只对自己有效。
- 多久：设置 `attention_snooze_minutes`（默认 60）。页面不写「一小时后」，写服务端给的那个时刻（「13:00 UTC 回到原来的位置」）——改了设置，字还是对的。到点之后不用做任何事，下一次刷新它就在原位。
- **只在它还在等同一件事的时候有效。** 放到稍后的是「批准方案 #5」；后来方案被换成了 #6——这是一件新的事，立刻回到原位。服务端记的是放到稍后的那一刻它在等什么。
- 排序只对新界面生效：`GET /api/ui/attention?snoozed=last` 是新界面自己带的参数。旧界面的「在等我」不带它，顺序和原来完全一样（每一行多一个它不读的字段 `snoozed_until`）。
- 写理由写到一半时按 `S` 不会生效（换到下一件会丢掉写了一半的话）。只读账户没有这个键。
- 不走 5 秒撤回：它不是一个决定，再按一次就是撤回。
- 没有提醒这回事——不发通知，所以不写「提醒你」。

### 和设计稿不一样、照实做的地方

- 设计稿的「和上一版的差别（v2 → v3）」：没有 v2、v3——重做是新的一份方案。写的是「和上一份方案（#N）」。
- 设计稿的差别是一份写好的示例；真的差别可能很长，所以多了「先说数字、多了就折起来」。
- 设计稿的验收页没有「稍后」。做成了每一页都有：它是待决页的键，不是某一种简报的，少一个特例。
- 设计稿的提示写「1 小时后再提醒你」。没有提醒，写的是回到原位的时刻。
- 变更单没有「要求修改」（设计稿上有）：后端的状态机不允许变更从「等批准」回到审核，重做要另提一张。变更的批准页仍然是 `D` 拒绝。

## N15 过去 24 小时：事件带和按时间回看（2026-11-18）

设计稿里最后两样：顶栏的「过去 24 小时」和全景的「回到过去」。后端没有存过资源健康状态的历史，所以先说清能回放什么、不能回放什么。

### 能说的和不能说的

对过去 24 小时里的某一个时刻 T：

| | 能不能算出来 | 怎么算 |
|---|---|---|
| 那时哪些资源上有未结的问题 | 能 | 一件问题从被发现（`detected_at`）起算在册；它在 T 的状态 = T 之后第一次状态变动的「从哪个状态来」，T 之后没有变动过就是现在的状态。每一次状态变动都有一条记录（MVP-2.6.1 起只有一个写入口） |
| 那时哪些资源已经不见了 | 一部分 | 现在不见了、而且在 T 之前就不见了的（`absent_since ≤ T`）。那时不见了、后来又回来的资源，看不出来 |
| 那时每件问题的严重度 | 不能 | 严重度是原地改写的，用的是现在的 |
| 那时问题挂在哪个资源上 | 不能 | 同上，用的是现在的 |
| 那时资源之间的关系 | 不能 | 图是最近一次构建的；关系只保留最近若干次构建 |

页面在回看的时候把这张表的意思写在三个地方：顶上一行、回看条下面一行、「数据核对」卡片里。

### 顶栏的事件带

- 「过去 24 小时」一条线，每一件事一个点：发现了问题（红）、agent 开始或结束一件工作（绿）、人做了一个决定（琥珀色的菱形）、变更单的进展（紫）。越近的时间占的位置越多，线上标着 12h / 6h / 3h / 1h。
- 鼠标停在一个点上，是那件事在自己时间线上的那一句话（「11:55 UTC　I#12　退回了方案 #7，并请 agent 按意见重做」）——和经过页、旧版问题页用的是同一句。
- 点只是画；这条带子的名字里带着数字（「发现问题 0 件，agent 开始或结束 14 次，人的决定 65 个，变更的进展 0 次」），读屏软件读到的是这个。用键盘逐件看：全景的 `[` `]`。
- 跟着顶栏的账户范围。每分钟重读一次。宽度不够（手机）时不显示。
- 接口：`GET /api/ui/events?hours=24[&account_id]`。直接读已有的时间线记录（`pipeline_events`），不新存任何东西。
- **不在带子上的**：流程内部的事（另一个模型的复核、证据检查、信号被并进已有的问题、策略规则、通知），和代码自己推动的状态变动（它旁边那条事件已经说了原因）。一条备注的内容不会发出来（它在那件事自己的页面上）。
- 「人的决定」按**是谁做的**算：时间线上写着人的账号的，都是人的决定——人请 agent 诊断、出方案也算。自动批准（流程自己批的）算 agent 的事，不算人的决定。
- 一天最多 500 条，超过了保留最新的，并写明「更早的没有列出」。

### 全景的回看

- 全景底部一条「回看」：现在的时刻或者你选的时刻、一条 5 分钟一格的滑块、滑块上面是这一天每件事的位置。
- `[` 到上一件事发生的时刻，`]` 到下一件（最新一件之后就是「现在」），`P` 把这一天从头放一遍（每 0.9 秒一个时刻，最多 60 个，一分钟之内放完；再按一次停在那里），`0` 回到现在。拖滑块、用方向键也行。
- 回到过去时：图上的环（哪些资源上有未结的问题）和虚线圈（哪些已经不见了）按那个时刻画；顶上一行「你在看 … UTC 的样子。连线用的是现在的关系图。按 0 回到现在。」；左边「现在」那一栏的标题换成那个时刻，数字是那个时刻的；它和待决的对应收起来，写「队列是现在的」；资源卡片上没有「去处理」，并写明下面列的问题是现在未结的、不是那个时刻的。
- 回看条上列出那一分钟里发生的事（最多 3 件，写明还有几件）。
- 平面和 3D 都一样，切过去时刻不变。「数据核对」照常每秒核对一次——回看时画的东西也得和数据对得上。
- 离开全景就回到现在：别的页面背后的那张图永远是现在的。时刻不写进地址（刷新就是现在）。
- 接口：`GET /api/galaxy/health?at=<时刻>`，和现在的健康接口同一个形状，多一个 `as_of`。只接受过去 24 小时之内的时刻；将来的、更早的、不是时间的，都是 422。
- 每个时刻只读一次（过去不会变）。回看的时候不再每 30 秒重读——重读的是「现在」。

### 顺带修的一个旧缺陷：步骤里带着密钥编号的方案，永远批准不了

检查期间，预览上有人两次批准同一份方案，两次都被拒绝：「方案在你读到之后变了，重新加载再看」。这份方案没有人动过。

原因在 MVP-2.6.1 就有了：方案的内容指纹是在 agent 写下方案的那一刻算的；紧接着写库时，库会把所有文字里的密钥、访问密钥编号抹掉（安全红线）。存进去的步骤里是「[REDACTED-SECRET]」，指纹却是按抹掉之前的原文算的。页面拿到的永远是那个存着的指纹，批准的时候服务端按存着的内容重新算一遍，对不上——重新加载多少次都一样。

副本库里在等批准的 80 份方案，有 4 份是这样（都是处理访问密钥的方案）。已经批准的 47 份不受影响（批准的时候指纹是按存着的内容重新盖的）。

改了三处：

- 指纹改成按**存下来的样子**算（算之前先做同样的抹除；抹除是幂等的，所以存着的内容算出来不变，不带密钥的内容算出来和以前**完全一样**——测试钉住了这一点，否则所有已有的批准都会失效）。
- 已经存着的错指纹：启动时把还在等批准的方案核对一遍，对不上的重新盖（版本号加一）；已经批准的不动。
- 万一还有漏的：批准、编辑、变更的批准被拒绝时，如果存着的指纹和内容对不上，当场重新盖，这样页面重新加载之后就能批准（以前只对「完全没有指纹」的方案这样做）。

修完重启之后，那份方案被批准成功了（副本库，执行器关着，没有执行）。
