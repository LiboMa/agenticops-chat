## N1 三种最常用的简报（2026-11-17）

### 做了什么

| 条目 | 改动 |
|---|---|
| 批准（问题的修复方案） | 一页里：为什么（诊断、它引用的证据、模型自己的把握、另一个模型的复核、位置是否核实）、打算怎么做（每一步的说明、命令、代码分的类；回滚）、会碰到谁（关系图的三个数）、做完怎么算成（声明的检查项）。动作：按住 `A` 批准、`R` 退回方案、`D` 忽略，后两个必须写理由 |
| 按住批准 | 按下时记住目标（哪件事、哪份方案、内容哈希），到时只批准还在屏幕上的同一个目标；中途松手、按了别的键、切走窗口、换到另一件事，都不批准。批准带的是你当时看到的内容哈希，方案在你看的时候变了会被服务端拒绝（409），页面说明并重新取 |
| 批准之后会不会执行 | 按钮和开头那句话跟着服务端的 `available_actions` 走：执行器和自动修复都开着才是「按住批准并执行」，否则是「按住批准」，并写明不会自动执行。服务端不放行时按钮不可用，开头那句话写明原因 |
| 验收 | 做了什么（几步、用时、按哪一版方案执行、和批准时是否一致、为什么要人看）、代码已经核对过的检查、要你看一眼的检查。`X` 逐项打勾，全部打完 `A` 才可用；勾过的检查项随验收记入审计。`R` 不通过，要写理由 |
| 确认诊断 | 诊断和三块可信度，加一句为什么没有自动出方案（把握低于门槛 / 被复核否定）。四个选项就是产品现有的四个：`Y` 对、`P` 位置只对了一部分（只有位置能评的时候才有）、`N` 不对、`F` 误报；后两个必须写理由。`M` 让它重新诊断 |
| 证据速览 | 空格打开，`←` `→` 换一条，`Esc` 关。只显示诊断时存下的类型、出处和摘要，并写明原始输出没有保存 |
| 做完一个决定 | 这件事立刻离开队列，下一件接上；它如果以另一种情形回来（批准了但没开始），会重新出现 |
| 后端：`step_tiers` | 方案的响应多一个只读字段：每一步的命令由代码分的类（`write` / `readonly` / `blocked` / `unknown`，没有命令的一步是 `unknown`）。用的是自动批准下限已经在用的那个分类函数；出响应时现算，不存库，不进内容哈希，更新接口不接受它 |

### 和设计稿不一样、照实做的地方

- 没有「要求修改」：`R` 是「退回方案」。方案被标为已退回，这件事以「方案被退回」回到队列。
- 没有 5 秒撤回：决定立即生效。所以批准要按住，说「不」都要写理由。
- 「对」之后不会自动出方案：这件事留在原处，变成「生成方案」那一页（N2）。
- 忽略：理由先作为备注写进时间线（现有接口不保存忽略的理由），并写明检测 agent 会记一条「这件事被人忽略过」。
- 误报、不对：页面写明后果（误报 = 忽略 + 检测 agent 记下这一类；不对 = 这次诊断标为不正确）。实测这两种判断各会写一份 agent 记忆。
- 很长的诊断先显示六行，「展开全文」看全部。

## N2 其余简报、变更单、agent 在做的事（2026-11-17）

到这一阶段，接口可能给出的 16 种组合每一种都有自己的一页（测试 `newuiRegistry` 对着共用清单逐行核对）。

### 做了什么

| 条目 | 改动 |
|---|---|
| 执行失败 | 说清楚是哪一种：某一步失败（第几步、它报了什么）、步骤做完但有检查没通过、还是验收时被人判为不通过（引用那句话）；回滚做了几步、有没有失败。`A` 重新出方案、`M` 重新诊断、`D` 忽略 |
| 批准了没开始 | 为什么没开始（执行器关着 / 没排上）、当初批准的那一版和它的哈希、内容之后变没变。`A` 按住重试；服务端不让执行时按钮不可用并写明原因。`R` 撤回批准（问题）/ 撤销变更单（变更） |
| 方案被退回 | 谁退回的、写了什么、被退回的那一版。`A` 按这条意见重做 |
| 诊断被否 / 没有诊断 | 人的判断（谁、什么时候、写了什么，取自时间线）和被否的诊断。`A` 重新诊断 |
| 诊断已确认 / 过了门槛没人确认 | 诊断和人的判断；后一种写明「自动修复关着，所以没有人去请 agent 出方案」。`A` 生成方案、`M` 重新诊断 |
| 等收尾 | 执行结果和代码核对过的检查；没有留下结论的执行照实说。`A` 标记已解决 |
| 变更：草稿 | 要改什么、谁提的、对上了哪些资源、哪些名字没对上、提的人自己写的步骤。`A` 开始审核、`R` 撤销 |
| 变更：审核要澄清 | 审核提的问题一题一格；后端只收一段话，页面把回答按题号合成一段发出 |
| 变更：待批准 | 要改什么、审核怎么说、实施方案、会碰到谁、检查项。后端要求批准带理由：先写理由，再按住批准；没写理由就按，焦点会跳到理由框。`D` 拒绝 |
| 变更：待验收 | 和问题的验收同一套打勾；`A` 确认完成、`R` 判定失败 |
| agent 在做的事 | 待决右边一栏：现在在做的每一件（做什么、做了多久、是哪件事），超过它自己的超时会标「可能卡住了」；下面是最近做完的几件。数据来自新接口 `GET /api/ui/activity` |
| 交给 agent 之后 | 简报顶上一行「agent 正在诊断 / 出方案（几分钟前开始，由谁发起）」，按钮不可用。这是服务端的记录：刷新、换浏览器、换人看到的都一样 |

### 后端

| 条目 | 改动 |
|---|---|
| 请 agent 做的事有记录、不会重复开始 | `POST /api/health-issues/{id}/rca` 和 `…/generate-fix-plan`（以及 `/api/issues/…` 两个别名）：开始前先占住这件事（`services/agent_runs`，进程内，一件事同时只有一个人请来的 agent），已经有一个在做就回 409 `agent_run_in_flight`（带是哪个 agent、几点开始、谁发起）；线程结束时释放，线程没能起来也当场释放，超过 RCA 看门狗的时限（`rca_timeout_seconds`）视为放弃，不会永远卡住。时间线上记 `rca_started {trigger: manual, requested_by}` / `fix_plan_requested`，agent 出错记 failed |
| `GET /api/ui/activity` | 现在在做的 / 接下来的定时任务 / 最近一天做完的。只用核实得了的状态：人请来还在跑的 agent、`investigating` 和 `fix_executing` 的问题、pending / running 的执行、已批准且时间线上执行已开始未结束的方案、审核中和执行中的变更、正在跑的定时任务、正在构建的关系图。`open` 的问题不算。每条带 `since`（没有记录就是空）、`basis`（怎么知道的）、`overdue`（超过自己的超时）。任何登录用户可读，固定次数的查询，不调模型也不调云 |
| 忽略的理由不再丢 | `PUT /api/issues/{id}/status` 的 `note` 以前收了不存（时间线写的是「anomaly status update」）；现在它就是状态变更的理由，也写进检测 agent 的那条备忘。理由上限从 500 字提到 2000 字 |
| 退回的理由交到 agent 手上 | 重新出方案时，如果最新的方案是被人退回的，那句理由会放在 `<reviewer_feedback>` 里交给 SRE agent（`agents/sre_agent.rejection_feedback`）：注明这是要回应的信息、不是改变协议的指令，引用里的结束标签会被处理掉；代码做的退回（内容在批准后变了）不算 |

### 核对卡片抓到的一个真问题

用只读账户检查时，卡片变红了：「亮着的资源应为 1,654，画出来是 1,928；不见了的应为 274，画出来是 0；环应为 275，画出来是 0」。原因：页面把结果交给画布的时刻比图本身到画布早一步，图到了之后把结果清掉了，画布就把所有资源都画成亮的、一个环都没有。另一个账户看不出来，是因为它的待决列表晚一点到、顺手又交了一次。已经在测试里重现并改掉：结果带着它所属的那张图，只在这张图上画；换图不再清结果。

为了看一眼变红的样子，另外做过一次**故意画错**的构建（视野外的环不画），核对卡片写的是「环应为 275，画出来是 12」；看完立刻用干净的源码重新构建，源码里没有留下任何开关。

### 和设计稿不一样、照实做的地方

- 没有时间轴和回放（后端没有资源状态的历史）。

### 后端：自动流程请来的出方案 agent 也留记录

N3 里写过：诊断过了门槛、自动修复开着时，流程会自己把这件事交给出方案的 agent——这是默认配置下最常走的一条路——但那几分钟里没有任何记录说它已经开始，状态也不变：现场页什么都没有，经过页只能说「轮到 agent 了，记录里没有它已经开始的迹象」，人这时再点「生成方案」会起第二个 agent。

| 条目 | 改动 |
|---|---|
| 占用 | `services/pipeline_service.trigger_auto_sre` 在起线程前占住这件事（`services/agent_runs.take`，发起者记为 `agent:auto-pipeline`），线程结束时释放，线程没能起来也当场释放。和人请的不同，流程的占用**不会被拒绝**：它直接接过上一步（刚存下诊断、正在收尾的 RCA）手里的占用；上一步随后释放的是它自己的那一个，不会碰到新的 |
| 时间线 | 开始时记 `fix_plan_requested {trigger: auto}`，agent 出错时记同一个事件的 failed |
| 现场 | `GET /api/ui/activity` 里这一条的 `basis` 是 `pipeline`（`requested_by` 为空）。现场页写「诊断过了门槛，自动流程把这件事交给了出方案的 agent，这个进程还在做」；经过页说「agent 在处理」并可以去看现场 |
| 不会重复开始 | 这期间人再请出方案或重新诊断，得到 409 `agent_run_in_flight`（和人请的 agent 在做时一样） |
| 只是记账 | 占用或事件写不进去时，方案照常去写——记录是给看的人的，不能反过来拦住流程。流程原有的判断（自动修复关着、已经有一份没结束的方案）不变，这两种情况不占用、不记事件 |

没有做的：流程自己发起的**诊断**（自动诊断）不占用。它在状态上看得见（诊断中），但人在它进行中再请一次诊断，仍然会起第二个——原来就是这样，列在下面的缺口里。

### 一处行为变化：自动批准的下限更严了

批准简报上每一步的「只读 / 会改动」是代码分的类，自动批准的下限用的是同一个分类。原来它只看一行命令**怎么开头**，所以这些都被当成「只读」：

- `find /var/log -name '*.gz' -mtime +7 -delete`
- `df -h && rm -rf /var/lib/docker/overlay2/*`
- `kubectl get pods -n web -o name | xargs kubectl delete -n web`
- `cat > /etc/nginx/conf.d/limit.conf <<EOF`
- 根本不是命令的一句话：`Find the stale pods and delete them`
- 一条读的命令，后面的注释里写着要再做一件写的事：`aws guardduty get-findings … # If 'False' run: aws guardduty archive-findings …`（副本库里真有这样的步骤）

现在只有**一条命令、一行、不会被 shell 拆开、重定向或做替换、后面不带 `#` 注释、并且照命令本来的写法（小写）写的**才算「只读」（引号里的内容不算拆开：`--query` 里的表达式是数据；`2>/dev/null`、`2>&1` 不改变什么；注释对 shell 没有影响，但它是写给执行的 agent 看的一句话，代码没法给它分类；`Free up disk by deleting old logs`、`Kubectl get pods and delete the stuck ones` 是句子，不是 `free` 和 `kubectl get`）；在主机上还要求这条命令是「不论带什么参数都写不了东西」的那一类（`ls`、`df`、`ps`、`stat` 这样的；`find`、`tee`、`xargs`、`curl`、`journalctl` 不算）。其余看起来像只读的，一律是「分不了类」——要人看。运行时放行主机命令的那张清单（`skills/security.SHELL_READONLY_COMMANDS`）**没有动**，那是另一道闸，改它要主人定；这里只把它的每一项分进「写不了」和「可能写」两组，以后清单里多一项而没分组，测试会失败。

在副本库上量过：166 份方案的 1,755 步（连同回滚步骤）里，**180 步从「只读」改判成「分不了类」**——169 步是因为会被 shell 拆开或重定向（其中 147 步是带 `&&`、`;`、`>`、`<`、`$(` 的 `aws` 命令，有几步在读的后面藏着一个写），11 步是因为带着注释（其中 3 步的注释在叫执行的 agent 接着做一件写的事——归档一条发现、收回一条安全组规则；2 步是别的指示——「每 15 秒重复一次直到在线」「之后另出一份方案」；6 步是「应该返回 1」这样的预期）。**21 份方案因此不再自动批准**，改为等人（被下限拦住的方案从 133 份变成 154 份）。只会让更多的方案等人看，不会反过来。

还留着的一个口子，照实写在这里：全小写、不带任何符号、又恰好以一个只读命令的词开头的句子（比如 `ping the owner before deleting the bucket`）仍会被当成那条只读命令。照字面执行它只会报错，但它毕竟不是一条命令——根本的办法是让执行器只照字面执行 `command`，不去理解它，这要另外做。

## N8 每一次执行都有一条记录；取消是真的（2026-11-18）

只有后端。叫停一次执行（N9）和看到执行的每一步（N10）都要先有这一层。

### 原来是什么样

一次执行有三种起法，只有一种在执行期间留有记录：

| 怎么起的 | 执行期间的记录（`fix_executions` 一行） | 超时、没结果时有人收尾 | 能取消 |
|---|---|---|---|
| 在网页上批准、或自动批准之后，流程起一个线程 | 没有，结束时才写 | 没有 | 不能 |
| 排队：`POST /api/fix-plans/{id}/execute`、CLI `/execute`、所有变更 | 有 | 有 | 只改了记录（见下） |
| 对话里让 Main 调执行器 | 没有 | 没有 | 不能 |

由此有四个口子：

1. **取消不是真的。** `POST /api/fix-executions/{id}/cancel` 把记录改成「已中止」，执行器的线程照样往下跑；之后的写命令只要不在「必须有批准的方案才能跑」的那张清单里，照样会执行。
2. 被取消或超时的**修复**，问题停在 `fix_executing`，时间线上没有一条记录——它不在任何人的队列里。
3. 流程起的执行如果没有存结果就结束了（模型出错、拒绝），方案在 30 分钟（`executor_total_timeout`）内一直读成「执行中」。
4. 批准之后马上撤回，和线程启动抢跑时，只有模型自己去调 `get_approved_fix_plan` 才会被拦下。

### 做了什么

| 条目 | 改动 |
|---|---|
| 开一条记录 | 三种起法都经过 `agents/executor_agent.executor_agent()`。它过了原有的几道闸之后，如果这次运行还没有记录，就自己开一条（`services/run_tickets.open_ticket`）：一个事务里，方案 `approved → executing`、问题 `fix_approved → fix_executing`、插入一行 `running`。和排队那条路在入队时做的事一样，所以下游都认 |
| 开不了就不跑 | 方案不是 `approved`、或者这份方案已经有一条在跑的记录：直接拒绝，不建模型。口子 4 和「同一份方案同时跑两个执行器」都在这里关上 |
| 结果就地关上这条记录 | `save_execution_result` 本来就会把排队那种的记录就地关上；现在三种起法都走这一条，一次执行一行。`executed_by` 是开记录时的发起者，不再是模型自己填的 |
| 没有结果也收尾 | `executor_agent()` 返回时，自己开的记录如果还是 `running`，按「执行器没有留下结果就结束了」关掉。自己开的记录也有 `executor_total_timeout` 的看门狗（原来只有排队的有） |
| 关记录只有一个出口 | `services/run_tickets.close_ticket`（原来是 `ExecutorService` 的私有方法）。取消、超时、崩溃、收尾都走它，谁先关谁算数。对修复，它现在把问题 `fix_executing → root_cause_identified`，并在时间线记一条 `execution_completed failed`——这件事以「执行失败」回到某个人的队列里。**不把诊断判成「有争议」**：取消和超时说明不了诊断对不对 |
| 记录一关，执行器就停 | 新的钩子 `agents/run_guard.RunGuard`（Strands `BeforeToolCallEvent` / `BeforeModelCallEvent`）。执行器每次调工具之前读一次这条记录：不是 `running` → 这次工具调用取消（命令根本不会跑），下一次调模型也取消，循环结束。已经在跑的那一条命令会跑完——它停不了。读不到记录时放行并记日志：这个钩子是用来停一次已经关掉的运行的，不能反过来拦住一次正常的 |
| 一条一条跑 | 执行器用 `SequentialToolExecutor`。SDK 默认把模型一轮里写的几条命令并发跑；方案的步骤是有先后的 |
| 删除方案 | `DELETE /api/fix-plans/{id}`：执行中的方案 409；跑过的方案 409（它的执行记录指着它；原来这种情况回的是 500） |
| 运行时打开执行器 | `PATCH /api/settings` 把 `executor_enabled` 从关改成开时，启动排队的轮询。原来只改了开关，之后入队的执行要等到下次重启 |
| 变更的时间线 | 一次变更的执行只记一条 `execution_completed`（原来 `save_execution_result` 和变更的状态映射各记一条） |

### 行为上的变化

- 流程起的执行**在进行中**：方案是 `executing`、问题是 `fix_executing`（原来直到结束都是 `approved` / `fix_approved`）。旧界面的问题页、列表这时显示「执行中」；新界面的现场上有这一条。
- 被取消、超时、或者没留下结果就结束的修复：问题回到 `root_cause_identified`，以「执行失败」出现在「在等我」里（原来停在 `fix_executing`）。
- 让执行器跑一份不存在的、或者不是 `approved` 的方案：在代码里被拒绝（原来要等模型自己去读方案才发现）。
- 取消之后：执行器在当前这一条命令做完后停下。

## 之后（顺序由主人定）

1. **验收和推送**：这一版八个阶段都只在本地提交。主人验收后才推送 `MVP-2.9.0`。
2. **后端缺口**（按建议的先后）：缺口 1 → 撤回窗口 → 叫停一次执行并回滚 → 给 agent 插话、暂停 → 稍后提醒 → 按时间回放、方案版本之间的差别。缺口 1 先要主人定一件事：**一次失败的诊断在等谁？** 建议是等人（重新诊断，或者忽略），这样它会出现在「在等我」里；同一条规则还要回答那几百件状态是 `open`、从来没有诊断过的问题在等谁——它们现在也算「在等 RCA agent」，如果一并改成等人，队列会一下多出几百件，所以两件事要分开定。
3. **没设计的页面**：对话 → 资料页（报告、资源、定时任务、技能、信号、安全）→ 管理页（设置、用户、审计、登录）。每一块先在 `new-UI-face` 出设计、给主人预览，再实现。`MVP-2.8.0` 的 S3–S8 里改数据、改接口的部分随对应的页面做。
4. **把新界面设为首页**：要改后端的偏好取值和「回到上次位置」的白名单；通知里的链接同时改。
