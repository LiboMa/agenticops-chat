01 · 背景与定位

一支 AI 智能体团队，把云运维做成闭环

AgenticOps 是什么

Agent-first 云运维平台：AI 智能体团队扫描 AWS、发现问题、定位根因、规划修复；低风险问题自主修复，每次运维都在学习。

解决谁的问题

SRE / 平台 / 云运维团队：要「告警 → 根因 → 修复」全闭环的 on-call 副驾，不是又一个看板；有风险的操作留人在环。

三种入口，同一批智能体

CLI aiops chat · Web 看板 · IM 机器人

出处：README_CN.md 开篇、「适合谁」、入口框图

落地意义
交付诊断结论 + 修复方案 + 执行记录；低风险问题自主闭环，on-call 精力留给要判断的事。（→ 总结 ①）
一句话定位：一支 AI 智能体团队，从巡检到修复把云运维做成闭环，并且越用越好。目标用户是 SRE、平台和云运维团队，他们要的是 on-call 副驾，不是又一个看板。注意「低风险自主、有风险留人在环」这条线，后面架构都围绕它展开。

03 · 架构 / 总体架构

三入口 → Main Agent（纯路由）→ 6 个专家 → AWS

出处：README_CN.md 架构框图、「7 个智能体」表；CLAUDE.md 凭证安全铁律（账号寻址、解析失败即报错、无 ambient 回退）

控制流从三个入口进来，只经过 Main；Main 不持有运维工具，只决定把请求交给哪个专家。注意右侧箭头：读的专家都是只读，唯一会改基础设施的是 Executor，而且只执行已审批的方案。所有共享层，包括记忆、技能、安全引擎和元数据库，都在下面这一层。
03 · 架构 / 设计原则

六条原则，落成七个权限分明的智能体

Main 纯路由，专家之间不对话

02读 / 规划 / 执行隔离

L0/L1 自动 · L2/L3 人工审批

03分层模型控成本

强模型用在判断上，按调用计成本

04智能体安全地学习

草稿 → 安全门禁 → 发布

05配置单一真源

config/settings.yaml

06默认从简

本地 SQLite + 文件；cloud 才上 PG + S3

智能体默认模型职责权限
MainOpus 5路由 / 编排，唯一与用户对话无运维工具
ScanSonnet 4.6跨账号 / 区域清单发现，20+ 种 AWS 服务类型只读
DetectSonnet 4.6CloudWatch + Z-score 异常检测、webhook 接入、主动巡检只读
RCAOpus 4.6CloudTrail + 拓扑证据 + KB + 技能 → 根因 + 置信度只读
SREFable 5.1RCA → L0–L3 分级方案，含步骤与回滚只规划
ExecutorOpus 4.6执行已审批方案：AWS CLI · SSM→SSH · kubectl唯一执行
ReporterSonnet 4.6日报 / 周报 / 事件报告，事件蒸馏为 KB SOP只读

出处：README_CN.md「设计原则」「7 个智能体」；模型为 config/settings.yaml 已提交默认值（agent_*_model_id，可按智能体覆盖），Haiku 4.5 为经济档

落地意义
提方案的动不了基础设施，动基础设施的只执行审批过的方案：敢把运维交给 Agent 的工程前提。（→ 总结 ②）
六条原则里最关键的是第二条：读、规划、执行相互隔离。下面这张表就是它的落地，只有 SRE 出方案，只有 Executor 动手，L2、L3 必须人工审批。模型分层是成本取舍：判断力最重要的路由和规划用 Claude 5 家族，高吞吐的扫描检测用 Sonnet。
03 · 架构 / 关键流程 I

自动修复流水线：每一步都有门，每次执行只有一个结论

9 态 HealthIssue 生命周期（状态机强制，非法转换 → 409）

三道开关：auto_fix_enabled · executor_auto_approve_l0_l1 · executor_enabled

  • 唯一写入口 transition_issue，CAS
  • 审批绑定内容哈希，执行前重算

出处：README_CN.md「自动修复流水线」；CLAUDE.md 状态机；rca_min_confidence_for_autofix: 0.6

落地意义
低风险问题自主闭环；证据不足的 RCA、证明不了成功的执行都回到人手里。（→ 总结 ①②）
这条流水线有三道门：RCA 后的质量门，置信度低于 0.6 或被 critic 驳回就进 needs_review，不自动修复；审批门按 L0 到 L3 分级；执行后只给一个结论，证明不了成功就等人工验收。下面是 9 态生命周期，所有状态写入只走一个入口，失败会回到 root_cause_identified 重新出方案。
03 · 架构 / 关键流程 II

双告警入口 + Signal Gate：所有建单路径过同一道门

出处：README_CN.md「双告警入口」；web/routers/webhooks.py require_webhook_token（空 secret 直接放行，启动时告警）；config/settings.yaml

落地意义
告警风暴不会变成工单风暴：on-call 只看去重后的问题，原始信号仍可审计、可追回。（→ 总结 ①）
两条告警入口：Webhook 直接解析，没有 LLM 成本，token 或 HMAC 校验只在配置了 AIOPS_WEBHOOK_SECRET 后才生效，生产部署要记得设置。IM 里的人话先由 Main 核实再建单。不管从哪来，都过 Signal Gate：先确定性去重，灰区才交给廉价模型，而且模型只能判合并或新建，永远不能把信号判成噪声丢掉。
03 · 架构 / 关键流程 III

变更管理（ITSM）与自学习层：同一套门禁思路

变更流：日常变更不需要 HealthIssue 12 态状态机

自学习层：写入先落草稿，发布要过门

出处：README_CN.md 功能表「变更管理」「自学习层」；docs/MVP-2.6.0-RELEASE.md（12 态，executing → completed / failed / rolled_back / needs_review）；services/change_service.py on_execution_result

落地意义
变更有人审、有哈希、有两本账；经验经门禁沉淀成记忆与技能，成为组织资产。（→ 总结 ②③）
变更管理是事件修复的 ITSM 对应物：日常变更不需要先开问题单，走 SRE 审核、人工审批、Executor 执行，审批只能是人，并绑定方案哈希。执行结果按确定性规则落到四种结果状态：验证通过才 completed，执行成功但验证没过或待验收进 needs_review 由人裁定，回滚就是 rolled_back，其余失败是 failed。自学习层是同一个思路：智能体写的先落草稿，过安全门禁才发布，人写的知识永不被自动改。

06 · 总结

四个核心观点

01
Agent-first 的运维闭环可行
技术依据

第 6–7 页：Signal Gate → RCA 质量门 → 分级审批 → 一次 verdict。EKS 实验室 10 个故障场景闭环验证：自动修复 10/10（目标 ≥ 7/10）、检测 ~2 分钟、MTTR ~6.3 分钟、每轮 ~$2–3。

落地价值

低风险问题自主闭环，减轻 on-call 负担。

02
自主与安全不矛盾
技术依据

第 5 页读 / 规划 / 执行隔离 + L0–L3 分级；第 6 页单一写入口 + 内容哈希；第 8 页人工审批 + 两本审计账；凭证与校验 fail-closed。

落地价值

审批门与审计是企业敢把运维交给 Agent 的前提。

03
系统越用越好
技术依据

第 8 页自学习层：记忆、技能先落草稿，经安全门禁发布，人类知识固定、永不删除；第 5 页 Reporter 把已解决事件蒸馏为知识库 SOP。

落地价值

运维经验沉淀为组织资产，不随人员流失。

04
落地路径清晰
技术依据

第 9 页部署形态：本地、Docker、一键 AWS 沙箱已跑通；Terraform 生产栈仍为脚手架、待验证。第 3 页每个阶段有发布说明与 E2E 证据。

落地价值

按客户成熟度逐级交付，从评估到试点再到生产。

验证数据出处：README_CN.md「验证」表（EKS 实验室 10 个故障场景：OOM、坏镜像、网络策略、磁盘压力、Pod pending、目标不健康、CoreDNS 宕机、PVC pending、HPA 打满、服务被删）

最后用四句话收尾。第一，闭环可行，EKS 实验室 10 个故障场景自动修复 10 个；第二，自主和安全不矛盾，靠的是隔离、分级审批和 fail-closed；第三，系统越用越好，但所有学习都在门禁之内。第四，落地路径清晰，前三种部署已跑通，生产栈还待验证，可以按客户成熟度逐级交付。
