## 环境

- **代码**：工作区 `.worktrees/mvp-2.9.0`，分支 `MVP-2.9.0`。前端是这个工作区自己 `npm run build` 出来的 `dist/`。
- **实例**：一个独立的 uvicorn 进程，`127.0.0.1:8001`，`--workers 1`。数据目录、数据库、日志目录都指到 `/tmp/aiops-290-e2e/`；开着登录（`AIOPS_API_AUTH_ENABLED=true`）。
- **数据库**：本机 `data/agenticops.db` 的副本，用 sqlite 的在线备份接口从只读打开的源库复制（源库是 WAL 模式，直接拷文件可能漏掉还在 `-wal` 里的提交）。副本里的定时任务全部停用。
- **关掉的开关**：执行器、自动修复、自动诊断、通知。所以**批准只是批准**——这一轮没有任何一次执行真的去动资源。唯一的例外是 7.7 那一次检查：自动修复临时打开（执行器仍然关着，另外关掉了 L0 / L1 的自动批准），看完改回。
- **没有碰的**：主人的 `:8000`、真实的数据库、主检出、开发机。
- **账户**：`e2e-admin`（管理员）、`e2e-writer`（可写）、`e2e-viewer`（只读），用 `aiops users create` 建在副本库里。浏览器的登录由本机的一个小助手（`127.0.0.1:8002`）交给自动化脚本，脚本里没有密码，输出里没有令牌。
- **浏览器**：Playwright 驱动的 Chrome（有界面），Apple M3 Pro，WebGL2。宽度 1440 / 1024 / 390；昼夜两套；中文和英文。
- **副本库的规模**：在等人的事约 140 件；关系图最新一次构建有 1,928 个资源、36 个分组、2 个账户、3,191 条关系；274 个资源已经不见了。

## 对副本库写过什么

批准、退回、忽略、验收、验收不通过、三种诊断判断、标记已解决、变更的批准 / 验收 / 撤销、撤回批准、一条备注、重新打开一件被忽略的问题——各一次。评审修复之后的检查另外写过：为了看「诊断换了，判断被拒绝」，临时插入过两条诊断记录，看完删掉；一次被拒绝的诊断判断和一次成功的。按住「标记已解决」那一项，请求在浏览器里被拦下来核对内容，没有写库——那件事还留在「等收尾」，主人验收时可以自己按一次。为了走没有真数据的情形，造了 5 张变更单和 1 件等收尾的问题；N4 临时改过一条执行的结束时间和一个定时任务的下次时间，看完改回。这些都只在 `/tmp` 下的副本里。判「不对」「误报」和忽略会往工作区的 `agent-memory/` 写文件：每次检查后还原，没有提交。

第二轮写过的，记在各阶段自己的小节里（N13 的三次真的批准、N14 在一件事上三次真的「要求修改」、N15 期间别人在预览上做的批准）。第二轮评审之后的复查没有写库：每一个写请求都在浏览器里被拦下回答；重启预览时的启动清理也没有动任何记录。

**看到了、没有改的**

1. **把命名空间写在子命令前面的 kubectl 命令，代码分不了类**。`kubectl -n chaos-lab get pods`、`kubectl -n chaos-lab scale …`、连 `kubectl -n chaos-lab delete pod x` 都是「分不了类」（量过；写成 `kubectl get pods -n chaos-lab` 就是「只读」）。这一次 7 份方案里有 3 份是这样写的，每一步都显示「分不了类」，回滚「能原样执行」的是 0。偏向总是保守的一边（不会被当成只读、不会被自动批准），但方案因此看着不可信，叫停之后这样写的读命令也不放行。要不要让代码认得这种写法，是改分类的清单——记给主人定（发布说明「之后」第 20 条）。
2. **执行器拿到的「已批准的方案」可能只是一个开头**。Run B 的方案比较长，工具结果超过了「过长的结果只留开头」的上限，执行器先看到的是开头的一段，自己又按关键字把后面取了回来。它取了，所以这一次没有出事；但执行器照着做的那份方案不该靠它自己想起来去取（「之后」第 21 条）。
3. 同样的故障、同样正确的诊断，Run B 没过门槛（0.53）、Run C 过了（0.85）：差在证据核对有没有引用对不上。

5. 事后检查和某条前置检查一字不差时，记录里把它标成「前置检查 N」。
6. Run B 的验收简报写「You asked it to stop at 11-20 03:29 UTC, but its steps had already run and nothing was rolled back.」——那一次有两步是在叫停之后才执行的（修复之前）。

9. 被叫停的简报写「… UTC, 39s in. 2 steps had reported done by then」：39 秒是整次运行的时长，叫停是在开始后十秒左右发出的；「2 步」是运行结束时报告的数（叫停时第一步刚做完，第二步正在执行）。
