第一部 · 总 — 六条设计信条 · 系统的 DNA

几乎所有设计决策，都源自这六条

01

Agent 即工具

Main 是纯路由；每个专家都是可调用的工具，专家之间不直接对话。

02

读/规划/执行分离

SRE 只规划、绝不动手；只有 Executor 执行，且必须过审批门。风险分级：L0/L1 自动，L2/L3 等人。

03

分层模型控成本

最重的推理用 Opus，路由与高吞吐用 Sonnet，经济档用 Haiku。逐 Agent 可覆盖，token/成本实时可查。

04

安全地学习

记忆与技能在硬边界内自优化：Agent 写入只作草稿，发布须过安检，人写知识钉死不动。

05

配置单一真相源

config/settings.yaml 定义一切，环境变量覆盖它。代码绝不硬编码值。

06

默认从简

本地 SQLite + 文件记忆；只有选 cloud 档才上 Postgres + S3。没有当下需求，绝不引入依赖。

第二部 · 心路历程 — Skills 的诞生
2026.02.27 – 02.28

一次质变的扩展

RCA 和 SRE 查资源时，拿到的信息太不具体——全是资源层面的。于是想到了 Skills：把 SSH、网络、数据库这些能力，以 SKILL.md 包的形式原生挂给任意 Agent。

从此，整个应用有了质的扩展性：遇到新场景，加一个技能包就行，不用改管线。

  • 起步 9 个领域技能：linux / network / k8s / database / elasticsearch / monitoring / log / aws-compute / aws-storage
  • Python 层：loader（发现+解析）· security（三级安全分类）· execution（run_on_host / run_kubectl）
  • 渐进式加载：系统提示只花 ~636 token，用到才展开 ~3–5K token

这颗种子，后来长成了整个"自主进化的技能库"（见第三部）。

第二部 · 心路历程 — 删掉，也是进化
2026.03.08

删掉 305 行正则分类器

旧的告警分类器是 305 行正则——误报严重。新方案很"反直觉"：让 Main Agent 读全文、验证严重性、自己决定要不要建 issue。用推理替代规则堆砌。

有时候最好的代码，
是被删掉的那 305 行。

这正呼应了"信条一"：与其写死规则，不如把判断交给会推理的 Agent——只要给它足够的验证约束。

直面两个质量之痛

"同一个问题反复出现在 Issue 列表"、"RCA 结论没校验就直驱自动修复"——这两个痛点，逼出了一次信任层级的重构。

痛点 A

噪音

三条创建路径各有一套互不相通的去重；抖动告警每次 flap 都新建 issue + 触发一次完整 Opus RCA。

痛点 B

盲信

0.2 置信度的根因也能直驱自动修复——"言之凿凿的幻觉"是自动化最大的敌人。

这两块是全篇的高潮之一，第三部会逐层拆开它们的内部机制。

第三部 · 分 · 模块 A · 架构 — 03 三权分立

读 / 规划 / 执行，三权分立

这是整个系统的安全脊柱。把"看"、"想怎么改"、"真的改"拆成三种角色，任何一次基建变更都必须走完全部三关——且中间那关只出图纸，不动扳手。

读（Scan/Detect/RCA）
只读调查：盘点、检测、关联、根因。永不写基建。
→
规划（SRE）
出分级修复计划 + 回滚。只提议，不动手。
→
审批门
L0/L1 自动放行；L2/L3 拦下等人点头。
→
执行（Executor）
唯一动手者。前检→执行→后检，账户寻址凭证。

为什么值得这么麻烦？因为"能自动修复"的前提是"错了也不会失控"。分权，就是把失控的概率按住。

第三部 · 分 · 模块 B · 安全地基 — 06 凭证安全铁律

多账户环境里，绝不在错误的账户上执行

凭证一旦降级到进程默认（ambient），就等于在错号上动手。所以这条被写成不可协商的铁律，贯穿每一条业务/扫描/执行路径。

铁律 1–2

只走 Provider 层

禁止裸用 boto3.Session() 跨账户；解析失败＝显式报错，绝不静默回退 ambient。

铁律 3

账户寻址执行

业务工具都带显式 account；子进程注入前先 strip 所有 AWS_*，再只注入目标账户的冻结凭证。

铁律 4–5

缓存含账户 + 自动续期

缓存 key 双写含 account_id；AssumeRole 用 botocore 原生刷新器，长任务自动续期。

# 铁律 6 · 纵深校验：解析出的凭证必须真属于目标账户 if credentials.account_id: assert sts.get_caller_identity()["Account"] == credentials.account_id # 不匹配 → fail-closed
第三部 · 分 · 模块 B · 安全地基 — 07 一个被杀掉的缺陷

ContextVar 错号执行，连根拔除

早期用隐式 ContextVar 传"当前账户"，但 Strands 同步工具在 asyncio.to_thread + copy_context 里跑——工具内的写入跨不出工具边界。结果：可能在错误的账户上执行。

v2.0.0 把它连根拔除，改为账户寻址：显式 account → 按目标资源反查库存 → 单账户默认 → fail-closed 列出账户名。

# 统一入口，无"无上下文回退 ambient"分支 credentials/resolver. get_subprocess_env_for_account(account, region) # 主机访问降级阶梯 run_on_host(method="auto") SSM → 分类失败 → SSH

安全不是加一层校验，而是把不安全的路径从代码里删掉——没有回退分支，就没有降级风险。

第三部 · 分 · 模块 D · 技术自动化 — 15 云安全审查 · 研发宪法

四条精确度原则（★ 不可协商）

目标函数只有一个：拿到最准确的数据、给出最精确的结果。成本与覆盖广度都让位于此。任何违反其一的实现，无论多"智能"，都视为降低准确度。

原则 1

采集零 LLM

GuardDuty/Security Hub/Inspector/Config 的 findings 原样采集——让 LLM 重判"CVE 算不算 critical"只会引入幻觉。

原则 2

精确来自关联

单看一条 SG 开放 22 判不了真实风险；降误报的杠杆在跨源关联，不在采集更多。

原则 3

可达性用确定性图算法

LLM 只叙事、不定论；数据不全时标"未确定"而非"安全"——保守偏报。

原则 4

评分对标基线，建议须接地

CIS 客观 pass/fail，不自创权重；LLM 建议须 grounded + 过 critic，refuted 即丢。

第三部 · 分 · 模块 F · 平台与体验 — 24 配置架构

唯一真相源：settings.yaml

config.py 只定义 schema 与加载逻辑，绝不硬编码任何配置值。207 个字段，从模型档位到安全轮询间隔，一处可调、可审计、可版本化。

  • 优先级：环境变量(AIOPS_*) > .env > settings.yaml > Field 默认
  • 运行时改动落盘：CLI 与 Web 的模型变更都写回 YAML 并清缓存立即生效
  • 每个新功能都带回滚阀（如 signal_gate_enabled=false 回退旧行为）
env AIOPS_* # 最高（部署覆盖） ↓ .env # 本地开发 ↓ settings.yaml # 单一真相源 ★ ↓ Field default # 代码兜底

第四部 · 证据与信念 — 28 我们的信念

保守偏报

03

Fail-Closed

拿不准宁可少做、不乱做；异常一律收敛到安全态。

人在环内

高危动作永远停在审批门前，等一个人点头。
