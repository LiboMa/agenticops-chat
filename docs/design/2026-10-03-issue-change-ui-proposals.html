方案 A ·「统一工单模板」

核心理念：一张工单，一条线

问题和变更都是「工单」：都要从「搞清楚该做什么」走到「做完并确认」。详情页只回答三件事：现在在哪一步、为什么停在这里、下一步谁做什么。走过的阶段折叠成一句话，当前阶段展开，没到的阶段置灰。整页只有一个主按钮。

关键观察：问题和变更的后三段完全一样。「方案 → 审批并执行 → 验收」就是同一张 fix_plans 表的生命周期，只有前段不同：问题从「诊断」（RCA）开始，变更从「申请 → 审核」（SRE 合法性审核）开始。所以模板是「各自的前段 + 共享的后三段」，后三段由同一组组件渲染（解决 L-f）。

服务谁

主要：一线值班 SRE / 运维工程师，也就是点开一张具体工单、要把它推进到底的人。
次要：审批人，在详情页的当前阶段里直接「批准并执行」。

阶段划分（对简报的细化）

问题① 诊断 → ② 方案 → ③ 审批并执行 → ④ 验收
变更① 申请 → ② 审核 → ③ 方案 → ④ 审批并执行 → ⑤ 验收

简报里问题有「审批」「执行」两段。修复方案本来就是批准后自动执行，变更现在也是，所以两者都合成「审批并执行」一段。问题因此是 4 段，后三段与变更逐字对齐。

方案 B ·「待办驱动」

核心理念：人只做决定，每个决定只给必要的信息

大部分工作由智能体推进（RCA、生成方案、L0/L1 自动批准、执行、自动验证）。人真正要做的是少数几个身份绑定的决定：批准或拒绝、验收、复核根因、回答澄清、重试。B 给这些决定一个统一入口「待我处理」。每个决定在一个右侧抽屉里完成，抽屉里只放做这个决定必需的信息。详情页保留给深度调查，只做瘦身（公共修复 + 少量结构调整）。

服务谁

主要：审批人、值班负责人、变更经理。
次要：SRE 每天第一眼该看的地方。

「我」是谁

系统里没有指派（assignee）模型，所以「待我处理」= 我的权限和职责分离规则允许我做的决定，判定方式和写端点完全一致（同一个 authz.check）。例如 rbac.yaml 的 sod-change-approver-not-requester：我自己提交的变更不进我的「待审批」（影子模式下照样显示，但带提醒）；「待澄清」只给申请人和管理员（requester-or-admin）。

推荐

推荐：以方案 A 为底座，把方案 B 的「待我处理」做成仪表盘上的入口卡；方案 C 暂不做。

理由

  1. 主人说的「乱」主要在详情页。现状诊断 23 条里有 15 条在两个详情页（I-a…I-i、C-a…C-f）。只有 A 正面重构了详情页；B 和 C 都把详情页留给公共修复，C-a（5000 px）和 I-d（线性流程拆成 tab）只能缓解。
  2. A 最经济。不新增端点（只给 settings 加一个只读字段），复用度最高，符合「简约、经济、不加没用的功能」。
  3. A 贴合领域的真实结构。两种工单的后三段是同一个 FixPlan 生命周期：一套 PlanView、一套阶段卡就消掉了 L-f，以后加第三种工单（比如安全建议转工单）也能直接套用。
  4. B 的价值真实，但先用最小形态验证。「什么在等我」（L-g）A 回答不了，但 B 要新增一个聚合端点，还要保证 RBAC 过滤一致。先做仪表盘卡片和侧栏计数，看实际使用频率，再决定要不要做完整的 /app/inbox 页。抽屉里的决定组件（复核、审批、验收）和 A 的阶段卡是同一批，届时几乎零成本。
  5. C 不划算。它引入第三套状态模型，规模化差，对「做决定」帮助最小。以后需要全局视图时，在 A 的列表里加一个「按阶段分组」视图就够了，不必做看板。
