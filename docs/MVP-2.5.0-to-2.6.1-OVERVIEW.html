32.5.0 基线（简述）

一句话：把散落在云厂商各服务里的安全信号收敛成一份准实时、可复现、消除误报的安全态势。它是本文的起点，所以只列要点。

四条精确度原则（研发宪法）

  1. 采集只采信官方判定，采集层零 LLM。
  2. 精确度来自跨源关联，不来自单点告警。
  3. 可达性用确定性图算法，保守偏报：数据不全标 undetermined，不标「安全」。
  4. 评分对标 CIS 客观基线；LLM 建议必须证据接地并过 critic，被驳回即丢弃。

4.1 Claude 5 家族（5308856，09-03）

  • Opus 5 / Sonnet 5 / Fable 5.1 只能通过 INFERENCE_PROFILE 调用，id 为 global.anthropic.*。
  • 版本号只有一段（claude-opus-5，没有小版本）。计费 key 和模型选择器标签的正则、MODEL_WINDOW_DEFAULTS 都已覆盖这种 id。漏掉一个家族，它会静默按 $0 计费，并回落到全局窗口。
  • MODEL_WINDOW_DEFAULTS 取第一个匹配的子串，所以具体家族必须排在它的前缀前面（claude-fable-5-1 在 claude-fable-5 前）。tests/test_claude5_bedrock_models.py 钉住了这个顺序。
  • 仓库里提交的默认模型：main Opus 5、sre Fable 5.1、rca / executor Opus 4.6、scan / detect / reporter Sonnet 4.6。

52.6.0：变更管理（ITSM）

5.3 两个状态机

5.4 RBAC 影子模式与审批人身份绑定

  • 只有一个入口 authz.check(actor, permission, subject=…)。actor 取自认证会话，不取请求体。config/rbac.yaml 把权限项映射到已有的 users.permissions（read / write / admin），不建 Role 表。
  • actor 有六类：user:<email> / web:anonymous（认证关闭时，全权）/ cli:<user> / agent:<name> / im:… / webhook:…。
  • 影子模式（rbac_enforce=false，默认）：照常判定，拒绝只写一条 audit_logs(authz.denied_shadow) 然后放行；true 时返回 403。
  • 审批人绑定：approve 接口一律把 Run Context 里的 actor 写入 approved_by。认证关闭时，请求体里的名字只作为 details.claimed_name 记进审计。
规则含义影子模式下引入
approver_must_differ_from_field（SoD）审批人不得等于申请人只审计，放行；匿名 web actor 跳过2.6.0
actor_must_match_field_unless_admin只有申请人或 admin 可 change.cancel / change.clarify只审计，放行2.6.0

62.6.1：五个计划

2.6.1 之前存在这些问题：Issue 指向哪个资源，靠模糊匹配取第一条；RCA 拿到的拓扑只是提示词里的一段文字，说不清根因在哪个资源，也没人能判它对不对；审批批的是方案 id，不是方案内容；执行完没有统一的验证；Issue 状态散在二十多处直接赋值。2.6.1 把这些接成一个闭环。

6.1 架构与数据流

修复 / 变更两条流的共同骨架：

plan_version + content_hash→ approve(content_hash)→ 执行前比对批准哈希→ Executor→ verification.evaluate()→ passed / failed / pending_acceptance→ transition_issue / on_execution_result→ 人工验收
三条不变量：锚定不上就明说（unanchored / ambiguous / account_level），绝不取第一条；缺验证结果永远不算 passed；HealthIssue 状态只由 transition_issue 写（有 grep 测试守着）。

6.2 五个计划

A · 图事实层

  • IdentityResolver（services/identity_resolver.py）：确定性规则按顺序执行，依次是 resource_id（含 ARN ↔ 短 id）、elb_arn、name、account_level、k8s_hints、alarm_name，第一条命中的规则说了算。同一规则命中多个物理资源时记为 ambiguous，并写下候选。锚不上时写明原因（none / unknown_account / account_conflict / account_unknown）。跨账户同 id 不会锚错账户。
  • HealthIssue 新增 resource_ref、anchor_status、anchor_candidates、observed_at。issue_account_claim 用来找回 Issue 当初声明的账户，找不到就不跨账户去猜。
  • 新增规范关系表 resource_relations，以及关系注册表 graph/relations.py（每种关系的故障传播方向）；UI、RCA、策略读的是同一份。
  • Galaxy：规则关系在 LLM 阶段之前发布（rules_published_at），LLM 失败不再遮住规则层；新增 rule-only 刷新 build_graph(trigger, llm=False)；每次构建完成都重新锚定。健康叠加改为四值：unknown / notice / warning / critical，从不显示「健康」。
  • GraphQueryService（graph/query_service.py）：有方向、有上限、按 build 版本读；旧的 graph/context.py（上下游方向是反的）已退役。
实测（本地库只读副本，09-30）：2 跳邻域 SQL 最多 4 条；p50 4.1 ms、p95 6.1 ms、最大 43.3 ms（457 个锚定资源 × 3 轮 = 1371 次调用，截断 0 次）。锚定率 66.1%，未达标。36 组跨账户重复 id 错配 0；resolve() 探测 72/72 都锚到持有账户。

B · 拉取式连接器、缺席判定、告警鉴权

  • 契约在 connectors/base.py，唯一写入口是 connectors/ingest.py：实体写进 cloud_resources（provider=kubernetes），每次运行写一行 connector_runs（complete / partial / failed）。部分采集不做缺席判定；缺席只记 absent_since，从不删除。
  • K8s 连接器（connectors/k8s.py）：每种 kind 一次只读 kubectl get（12 种 kind，裸 Pod 记为 K8s_Pod）。env 只来自 kubectl_env_for_cluster：目标账户的凭证加一份私有 kubeconfig，从不碰 ~/.kube/config。Secret 只保留 type。单次输出有字节上限，超出则该 kind 记为部分采集。
  • 墓碑规则：W2 扫描证明一个集群已经不在了，下一次发现运行就把它下面的 K8s 行标为缺席；这个墓碑目标不调 kubectl，也不取凭证。
  • AWS 缺席判定：W2 扫描完整列出某个 (type, region) 之后，把这次没看到的 provider="aws" 行标为缺席。新的 resource-scan 调度（默认每 60 分钟）定时跑这个扫描。所有计数和列表都用同一个「存在」定义 inventory.PRESENT（absent_since IS NULL）。
  • 告警 webhook：配置 webhook_secret 后，必须带令牌（Authorization: Bearer / X-AIOps-Token / ?token=）或 HMAC，否则 401；6 个解析器补全 observed_at。
实测（chaos-lab）：每次运行都是 partial（实验集群的 RBAC 有意不给读 secrets），创建 129 个 K8s 对象，absent 0；库里没有 K8s_Secret 行；计数不变式 /api/stats 167 = /api/resources 167 = 各类型计数之和 167。webhook 不带令牌 / 令牌错 → 401，令牌正确 → 201。

C · RCA 定位闭环与评测

  • 证据工具 get_topology_evidence(issue_id, depth, window_minutes)（graph/evidence.py）返回：锚点周围有方向的边；邻居在时间窗内的未关闭 Issue、信号和变更；确定性的根因候选和理由；证据引用 graph:edge:… / graph:node:…。这个工具不用 LLM。没有已发布构建或缺少锚点时，返回 available:false 并写明原因。
  • K8s 锚点重采：集群上次成功采集早于 rca_k8s_recollect_min_age_seconds（120 s），或者早于故障起点，就先重采一次；「早于故障起点」这个条件是联合 E2E 中补上的（fe7e9fd）。重采失败记为 stale，RCA 继续。
  • 结构化定位 save_rca_result(location=…)：最多 3 个排序候选 + 一条路径；services/rca_location 做 fail-closed 校验，结果为 valid / partial / invalid / absent。存下的路径应读作「一组逐条校验过的边」，不是验证过的因果链（C-1）。
  • 人工判定 + 统计：location_verdict 取 correct / partial / incorrect，判定人取会话 actor；统计走 GET /api/rca/location-stats，显示在 AgentMetrics 定位卡片上。
  • 策略影子模式：estimate_blast_radius 计算已发布图上的潜在影响（下游、只走 rule 关系、≤ 3 跳），结果记为 shadow_blast_radius，策略规则看不到它。
  • 证据门变严（C-M6）：证据检查不再拿 save_rca_result 自己的输入当依据。
  • 评测：infra/eks-chaos-lab/e2e/ground_truth.yaml（13 个场景的真值）+ location_eval.py（AC@1 / AC@3 / MRR、图召回率）。
实测见第 8 节：AC@1 off 0.00 → on #1 0.38 → on #2 0.77；located 15% → 100%；图召回率 13/13。

D · Issue / Change 逻辑

  • 审批绑定内容：fix_plans 新增 plan_version / content_hash / approved_hash / approved_version。哈希覆盖 steps、rollback、前后检查、账户和风险，不含说明文字。审批必须带上看过的哈希：缺哈希 422，方案已变 409。执行门会重算哈希，内容漂移就拒绝执行、撤回方案，Issue 回到 root_cause_identified。
  • 变更单自带步骤：proposed_steps（≤ 50 步）+ external_ref。SRE 负责校验，steps_diff 由代码计算；含 blocked 命令的单直接 rejected。
  • 外部入口 POST /api/changes/intake：HMAC 签名；change_intake_secret 为空时接口返回 404。同一外部工单再次提交，返回仍在进行中的那张单（新建 201 / 已有 200）。申请人记为 webhook:<system>，永远不能批准、执行或验收。
  • 统一的执行后验证 services/verification.evaluate：每次执行只给一个判定。缺 post-check、结果不全、有 warning、某一步没报告成功，都判为 pending_acceptance，永远不算 passed。人工验收走 POST /api/fix-executions/{id}/accept 或 CLI /accept。
  • 唯一的状态写入口 services/issue_state.transition_issue：校验边 + CAS + 写 status_changed 事件。tests/test_issue_status_writes.py 扫描 src/，发现别处写状态就失败。
  • dismissed：抑制同指纹的重复，但不算「未关闭」；dismissed → open 可重开。HealthIssue 因此是 10 态。Main 新增 get_plan / get_execution_result。

9Galaxy 收敛情况

主人的问题：「Galaxy 的图是否已经收敛完成？」以下是 chaos-lab 集群上 2026-10-03 的实测，构建 #1–#14 全部 completed。
